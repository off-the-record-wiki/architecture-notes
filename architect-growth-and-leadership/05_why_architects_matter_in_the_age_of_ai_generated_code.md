# AI 코드 생성 시대의 아키텍트: 일을 정의하고 결과를 검증하기

## 1. 구현을 맡겨도 설계와 검증의 책임은 남는다

- **AI를 활용하는 개발에서도 무엇을 만들고 어떤 조건을 지켜야 하는지 정하며 실제 결과를 확인하는 일이 필요하다.**
- 코드 생성은 개발 활동의 일부이며 생성된 코드가 업무 목표와 품질 요구를 충족하는지는 별도로 판단해야 한다.
- AI가 구현과 분석을 지원하더라도 중요한 결정의 책임자와 검토할 담당 역할은 명확해야 한다.
- 아키텍트의 역할은 요구 정의, 제약 설정, 설계 판단과 결과 검증으로 나누어 살펴볼 수 있다.

| 역할 | 수행할 일 | 확인할 내용 |
| :--- | :--- | :--- |
| 정의한다. | 모호한 요구를 기능, 품질 목표와 책임 경계로 구체화한다. | 어떤 문제를 누구를 위해 해결하며 무엇을 성공으로 판단하는가? |
| 제약한다. | 기술 선택, 보안 경계와 개발 기준의 허용 범위를 정한다. | 반드시 지켜야 할 조건과 조정 가능한 선택은 무엇인가? |
| 판단한다. | 맥락에 맞춰 대안을 비교하고 중요한 설계를 결정한다. | 얻는 이점, 감수할 비용과 남은 위험은 무엇인가? |
| 검증한다. | 코드·테스트·운영 자료로 합의한 동작과 품질을 확인한다. | 어떤 조건과 범위에서 요구 충족을 확인했는가? |

- 이 활동을 아키텍트 혼자 수행할 필요는 없다. 개발·QA·운영·업무 담당자가 역할에 맞춰 함께 수행한다.
- 구현 결과나 검증에서 새로운 제약이 드러나면 요구와 설계도 다시 검토한다.

## 2. 프로젝트 맥락을 실행 가능한 작업 조건으로 바꾼다

- AI가 개발에 참여하면 사람이 이해하던 업무 배경과 개발 관례도 작업에 필요한 형태로 명시해야 한다.
- 목표만 전달하기보다 변경 범위, 지켜야 할 계약과 완료를 판단할 근거를 함께 전달한다.

| 구분 | 전달할 내용 | 가상 사례 |
| :--- | :--- | :--- |
| 맥락(Context) | 업무 목적, 현재 구조와 관련 요구사항이다. | 회원가입과 로그인에서 사용하는 계정 상태와 기존 인증 흐름을 설명한다. |
| 규칙(Rules) | 코드 규약, 의존 방향과 유지해야 할 계약이다. | 기존 응답 계약과 오류 처리 방식을 유지하도록 한다. |
| 실행 제한(Guardrails) | 접근 권한과 허용된 변경·실행 범위이다. | 작업에 필요한 저장소와 환경만 접근할 수 있게 한다. |
| 평가(Evaluation) | 요구 충족을 판단할 시나리오와 확인 방법이다. | 정상 로그인뿐 아니라 실패·접근 거부 동작도 확인한다. |

- 설명 문서, 작업 지침, 도구 권한과 자동 검사 등으로 조건을 전달하거나 실행에 반영할 수 있다.
- 문서에 금지 사항을 적는 것과 실제 도구 권한으로 제한하는 것은 보장 범위가 다르다.
- 규칙이 존재한다는 사실만으로 준수가 보장되지는 않으므로 결과를 확인한다.
- 모든 상세 행동에 승인을 추가하기보다 영향이 큰 경계와 되돌리기 어려운 작업을 중심으로 통제한다.

## 3. 요구사항과 검증 기준을 함께 정의한다

- “회원가입과 로그인을 만든다”는 요청만으로는 허용할 동작과 실패 처리를 충분히 알기 어렵다.
- 기능 요구사항, 품질 요구사항과 제약조건을 구분하고 판단이 필요한 빈틈을 확인한다.
- 구현 방법을 먼저 고르기보다 업무 규칙과 검증할 조건을 정한다.

| 구분 | 구체화할 질문 |
| :--- | :--- |
| 기능 | 어떤 사용자가 어떤 절차로 가입하고 로그인하는가? |
| 업무 규칙 | 중복 계정, 계정 상태와 인증 실패는 어떻게 처리하는가? |
| 품질 | 어떤 부하와 실패 조건에서 어느 수준의 응답과 복구를 기대하는가? |
| 보안·개인정보 | 어떤 정보에 누가 접근할 수 있고 어떻게 보호해야 하는가? |
| 제약조건 | 기존 시스템의 계약, 조직 정책과 적용 의무는 무엇인가? |
| 검증 | 어떤 시나리오와 증거로 완료를 판단할 것인가? |

- 품질 목표에는 대상, 적용 조건, 측정 방법과 합격 기준을 포함한다.
- 확인된 사실, 미확인 가정과 합의된 요구를 구분해 전달한다.
- 확인이 필요한 항목은 확인할 내용과 담당 역할을 정하고, 결과에 따라 설계가 달라지는 항목부터 살펴본다.

## 4. 기준을 적용할 요구와 확인 근거로 연결한다

- 기술 용어를 아는 것과 결과를 판단할 기준을 갖추는 것은 다르다.
- 품질·운영·보안 기준을 검토해 현재 기능에 적용할 요구를 선정하고 구현 및 검증 근거와 연결한다.
- 기준마다 목적과 적용 범위가 다르므로 한 목록으로 모든 요구를 대신하지 않는다.

| 검토 영역 | 참고할 수 있는 기준의 예 | 작업에 연결할 내용 |
| :--- | :--- | :--- |
| 품질 | ISO/IEC 25010 | 놓친 품질 관심사를 찾고 시스템에 맞는 측정 목표로 구체화한다. |
| 운영 | SRE 접근법, Well-Architected 관점 | 신뢰성, 관측, 복구와 운영 부담을 검토한다. |
| 보안 | OWASP ASVS 등 | 기능에 적용할 보안 요구와 확인 방법을 구체화한다. |
| 적용 의무 | 관련 법령, 계약과 조직 정책 | 해당 업무와 데이터에 적용되는 의무를 담당 역할과 확인한다. |

- 기준의 명칭만 지시하기보다 적용할 버전과 항목, 범위 및 판정 조건을 명확히 한다.
- 법령과 인증 요구의 적용 여부는 업무·조직·데이터 조건에 따라 확인해야 한다.
- 다음은 회원가입·로그인 작업에 요구와 증거를 연결하는 가상 예시이다.

> 인증, 개인정보 보호와 접근통제 요구 중 이 기능에 적용할 항목을 먼저 정리한다. 항목별 구현 위치, 검증 방법, 확인한 결과와 미적용 사유를 제시하고, 아직 검증하지 못한 내용은 별도로 표시한다.

- 미적용 사유가 있다는 사실만으로 필수 요구 위반이 허용되지는 않는다.
- AI가 작성한 요구 목록과 결과 표도 누락이나 잘못된 해석이 없는지 검토한다.

## 5. 기술의 깊이와 넓이로 생성 결과를 판단한다

- 직접 구현하고 운영해 본 기술의 깊이는 생성 코드의 동작과 한계를 이해하는 데 도움이 된다.
- 다른 접근법과 위험을 아는 넓이는 AI가 제시한 해법 외의 대안을 검토하는 데 필요하다.
- 생성 결과가 자연스럽게 설명된다는 이유만으로 최선의 선택이라고 판단하지 않는다.

| 지식의 상태 | 판단에 활용할 방법 |
| :--- | :--- |
| 알고 있는 것 | 실제 코드와 실행 결과를 바탕으로 구현의 적절성을 확인한다. |
| 모른다는 것을 아는 것 | 필요한 정보를 조사하고 전문가 검토나 작은 실험으로 보완한다. |
| 모르는 줄도 모르는 것 | 다른 분야의 사례와 협업을 통해 빠진 질문과 선택지를 발견한다. |

- AI가 빠르게 대안을 생성해도 비교할 품질 시나리오와 필수 조건은 분명해야 한다.
- 기존 구조 유지와 부분 개선을 포함해 효과, 성립 조건과 개발·운영 비용을 비교한다.
- 익숙하지 않은 기술의 세부 동작을 추측해 채택하지 않고 위험에 맞는 근거를 확보한다.

## 6. 생성된 코드와 테스트를 요구사항에 비춰 검증한다

- 코드가 실행되거나 테스트가 통과하는 것은 확인 근거의 일부이다.
- 구현과 같은 가정을 공유하는 테스트만 있으면 요구사항의 누락을 발견하지 못할 수 있다.
- 요구에서 검증 시나리오를 도출하고 실제 확인한 조건과 범위를 남긴다.

| 검증 관점 | 확인할 내용 |
| :--- | :--- |
| 정상 동작 | 합의한 입력과 업무 흐름에서 기대한 결과가 나오는지 확인한다. |
| 실패 동작 | 잘못된 입력, 권한 부족과 외부 의존 실패에서 허용한 방식으로 동작하는지 확인한다. |
| 변경 영향 | 인터페이스, 데이터와 다른 모듈의 기존 동작에 미치는 영향을 확인한다. |
| 품질 목표 | 합의한 부하와 운영 조건에서 응답, 오류와 복구 목표를 충족하는지 확인한다. |
| 설계 제약 | 책임 경계, 접근 권한과 데이터 처리 규칙을 지키는지 확인한다. |

- 테스트의 존재나 생성된 보고서만으로 실제 실행 결과를 대신하지 않는다.
- 테스트 환경과 운영 환경의 차이, 실행하지 못한 검증과 남은 가정을 구분한다.
- 실패 영향이 큰 가정부터 확인하고, 채택 후 추적할 내용은 담당 역할과 확인 시점을 정한다.
- 발견한 위험은 발생 조건, 영향과 근거를 남기고 필요한 후속 작업으로 연결한다.

## 7. 코드 생성 속도와 검토·운영 역량을 함께 관리한다

- AI로 구현 속도가 빨라질 수 있어도 코드 검토와 운영 준비의 처리 능력이 함께 늘어나는 것은 아니다.
- 변경량이 늘면 인터페이스 충돌, 중복 구현과 운영 대상 증가를 살펴볼 필요가 있다.
- 코드 생산량만으로 개발 성과를 판단하면 검증 부족이나 유지보수 부담을 놓칠 수 있다.

| 살펴볼 변화 | 함께 확인할 내용 |
| :--- | :--- |
| 구현 시간이 줄어든다. | 검토 대기와 재작업까지 포함한 완료 시간이 개선됐는지 확인한다. |
| 코드와 대안이 늘어난다. | 선택 근거, 복잡성과 유지보수 부담을 확인한다. |
| 변경이 자주 반영된다. | 결함, 장애와 복구 비용이 늘지 않는지 확인한다. |
| AI에 맡기는 범위가 넓어진다. | 맥락의 누락, 실행 권한과 검증 책임이 명확한지 확인한다. |

- 중요한 결정은 배경, 대안, 선택 이유와 감수할 비용을 기존 기록에 남긴다.
- 요구나 운영 조건이 바뀌면 이전 결정의 전제와 관련 검증을 다시 살펴본다.
- **AI를 활용하는 개발에서도 해결할 일을 정확히 정의하고 결과의 적절성을 판단하는 역량이 중요하다.**
