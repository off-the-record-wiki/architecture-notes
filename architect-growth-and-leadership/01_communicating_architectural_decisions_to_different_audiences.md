# 아키텍처 결정 전달: 이해관계자의 관심사로 설명하고 합의하기

## 1. 결정을 설명하고 정당화하는 것도 아키텍트의 일이다

- **아키텍처 결정은 선택의 근거와 결과를 다른 사람이 이해하고 실행할 수 있을 때 의미가 있다.**
- 결정의 실행에는 개발팀뿐 아니라 운영, 경영진과 업무 담당자가 함께 관여한다.
- 무엇을 바꿀지만 전달하면 선택한 이유나 감수해야 할 위험을 놓칠 수 있다.
- 결정 → 설명 → 이해·합의 → 실행의 흐름에서 설명은 실행을 가능하게 하는 활동이다.
- 구현과 운영 과정에서 새로운 제약이 드러나면 결정도 다시 검토한다.

| 책임 | 전달할 내용 |
| :--- | :--- |
| 결정의 결과를 드러낸다. | 무엇이 달라지고 누구의 업무와 시스템에 영향을 주는지 설명한다. |
| 대가와 위험을 전달한다. | 얻는 이점, 포기하는 것과 남은 위험을 함께 말한다. |
| 근거를 남긴다. | 결정과 이유, 검토한 대안과 다른 결정과의 관계를 기록해 공유한다. |

- 설명의 목적은 선택을 무조건 받아들이게 하는 것이 아니라 판단에 필요한 정보를 공유하는 것이다.
- **좋은 설명에는 질문과 반대 의견을 받아 결정을 고칠 여지가 있어야 한다.**

## 2. 이해관계자마다 먼저 확인하는 것이 다르다

- 같은 결정이라도 상대가 책임지는 결과에 따라 관심사가 달라진다.
- 먼저 상대가 무엇을 중요하게 여기는지 확인하고 설명의 순서와 깊이를 조절한다.
- 아래 구분은 대표적인 관심사이며 실제 역할과 책임은 조직마다 다를 수 있다.

| 이해관계자 | 주요 관심사 | 상품 조회 캐시 사례에서의 질문 |
| :--- | :--- | :--- |
| 개발자 | 전체 구조에 미치는 영향, 컴포넌트·인터페이스와 기술 제약이다. | 캐시 갱신과 장애 대응은 누가 맡는가? 원본 데이터와 다르면 어떻게 처리하는가? |
| 경영진·사업·프로젝트 책임자 | 일정, 예산과 선택한 방식의 사업 위험이다. | DB 증설보다 비용과 효과가 나은가? 추가 인력과 일정이 필요한가? |
| 현업·업무 담당자 | 요구사항 충족 여부와 고객·업무에 생기는 변화이다. | 주문 단계에서 품절을 안내해도 되는가? 행사 상품과 고객 응대 정책은 어떻게 바뀌는가? |

- 개발자에게는 기술 근거와 검증 방법을, 경영진에게는 비용·일정과 사업 영향을 중심으로 설명한다.
- 현업에게는 고객이 겪는 변화와 함께 정해야 할 업무 정책을 먼저 설명한다.
- 요구가 충돌하면 관련 담당자가 의사결정에 참여하도록 하고 우선순위와 허용 범위를 확인한다.

## 3. 결론·이유·대가·대안·요청을 준비한다

- 설득에 필요한 내용은 다음 다섯 요소로 정리할 수 있다.
- 다섯 요소는 설명을 준비하는 틀이며, 모든 상대에게 같은 순서로 말할 필요는 없다.

| 요소 | 답해야 할 질문 | 설명에 포함할 내용 |
| :--- | :--- | :--- |
| 결론 | 무엇을 하자는가? | 적용할 결정과 범위이다. |
| 이유 | 어떤 목표와 문제 때문인가? | 업무 목표, 현재 문제와 판단 근거이다. |
| 대가 | 무엇을 포기하고 어떤 위험이 남는가? | 추가 비용, 기능·품질의 제약과 운영 부담이다. |
| 대안 | 무엇과 비교했고 왜 선택하지 않았는가? | 검토한 해법과 현재 조건에서의 선택 이유이다. |
| 요청 | 상대에게 무엇이 필요한가? | 필요한 결정, 협의, 자원이나 구체적인 후속 행동이다. |

- 결론·이유·대가·대안은 결정 기록에도 남길 수 있다.
- 요청에는 상대가 무엇을 판단하거나 함께 정해야 하는지 명시한다.
- 아직 검증하지 않은 기대 효과는 사실처럼 전달하지 않고 가정과 확인 계획을 구분한다.

## 4. 개발자에게는 기술 근거와 증거로 설명한다

- 다음은 행사 중 상품 조회 증가에 대비해 캐시를 제안하는 가상 사례이다.
- **조회량 10배, DB CPU 사용률 60% 안팎 등의 수치는 가상 사례의 조건이며 실제 측정값이나 권장 기준이 아니다.**

> 행사 때 상품 조회가 평소의 10배로 늘 것으로 예상합니다. 현재 피크 시간대 DB CPU 사용률은 60% 안팎입니다. 상품 조회 증가가 같은 DB를 사용하는 주문·결제에 미치는 영향을 확인해야 합니다. 상품 조회에 캐시를 적용하는 방안을 검토하고, 재고는 주문 단계에서 원본을 기준으로 확인하려 합니다. 적용 효과는 부하 테스트로 검증하고 갱신 방식과 장애 대응은 개발팀과 함께 정하겠습니다.

| 설명할 내용 | 함께 확인할 사항 |
| :--- | :--- |
| 문제를 수치로 제시한다. | 조회 증가의 예측 근거, 현재 부하와 주문·결제에 미치는 영향을 확인한다. |
| 대안을 비교한다. | DB 증설, 읽기 복제본이나 기존 쿼리 개선으로 목표를 달성할 수 있는지 검토한다. |
| 작은 시연과 실험을 준비한다. | 동일한 부하 조건에서 적용 전후의 응답 시간, 처리량과 오류율 등을 비교한다. |
| 구현 방법을 함께 정한다. | 캐시 갱신, 데이터 불일치, 장애 대응과 운영 책임을 정한다. |

- CPU 사용률과 조회량만으로 병목이나 캐시 효과를 확정할 수는 없다.
- 작은 실험은 확인한 조건과 범위를 밝혀 공유하고 운영 규모에서 추가로 확인할 내용을 남긴다.
- 주문 시 원본을 재조회하는 것만으로 초과 판매가 방지되지는 않는다. 동시 주문에서 재고 확인과 차감을 안전하게 처리하는 방식도 필요하다.
- 개발자가 제기한 구현·운영 우려는 설계와 검증 계획에 반영한다.

## 5. 경영진에게는 비용·일정·사업 위험으로 설명한다

- 기술 선택이 매출, 서비스 운영과 행사 일정에 어떤 영향을 주는지 연결해 설명한다.
- 실행하지 않았을 때의 사업 위험과 선택 이후의 비용을 함께 제시한다.

> 행사 기간에 상품 화면이 느려지면 매출 손실 위험이 있습니다. DB 증설, 읽기 복제본과 캐시를 운영비와 적용 기간까지 비교했습니다. 캐시를 우선 적용하는 방안을 제안하며, 개발·검증 일정과 운영비에 대한 결정이 필요합니다. 재고 표시 지연과 추가 운영 부담도 함께 검토해야 합니다.

- 아래 비용과 기간은 **가상 수치**이며 실제 견적이나 적용 기간이 아니다.

| 대안 | 월 운영비 증가 | 개발·테스트를 포함한 적용 기간 | 남는 위험과 부담 |
| :--- | :--- | :--- | :--- |
| DB 증설 | 약 800만 원 | 1주 | 증설한 용량을 유지하는 동안 운영비가 계속 든다. |
| 읽기 복제본 | 약 400만 원 | 2주 | 복제 지연과 조회 경로 변경을 다뤄야 한다. |
| 캐시 | 약 200만 원 | 3주 | 재고 표시 지연과 갱신·장애 대응 부담이 생긴다. |

- 이 사례는 행사 1주 전 운영 반영을 전제로 하며, 캐시 개발·검증 인력 비용은 표의 운영비와 별도이다.
- 실제 판단에서는 같은 목표 부하와 품질 조건으로 효과를 검증하고 인력 비용을 포함해 비교한다.
- 운영비가 낮아도 필수 품질 조건이나 행사 준비 기한을 지킬 수 없다면 그 이유만으로 채택할 수 없다.
- 필요한 예산, 일정과 결정할 범위를 명확히 요청한다.

## 6. 현업에게는 고객 경험과 업무 정책으로 설명한다

- 기술 용어보다 고객이 무엇을 보게 되고 업무 담당자가 무엇을 처리해야 하는지 설명한다.
- 아래의 최대 30초 지연도 가상 사례의 조건이며 실제 시스템의 보장값이 아니다.

> 상품 화면은 빨라질 수 있지만 품절 표시가 최대 30초 늦을 수 있습니다. 고객은 화면에서 구매 가능으로 본 상품의 품절을 주문 단계에서 안내받을 수 있습니다. 안내 문구와 고객 응대 기준, 이런 지연을 허용할 상품 범위를 함께 정해야 합니다.

| 함께 정할 내용 | 확인할 질문 |
| :--- | :--- |
| 고객이 겪는 변화 | 화면에서 구매 가능으로 표시된 뒤 주문 단계에서 품절을 안내해도 되는가? |
| 예외 처리 | 품절 안내 문구, 대체 상품 추천과 고객 응대 기준은 무엇인가? |
| 상품별 정책 | 일반 상품과 행사 상품에 같은 재고 표시 지연을 허용할 수 있는가? |

- 재고 표시 지연을 허용하는 것과 초과 판매를 허용하는 것은 별개의 요구사항이다.
- 초과 판매 방지는 주문 처리의 동시성 제어와 실패 처리까지 포함해 별도로 검증한다.
- 업무 정책은 영향을 받는 현업 담당자와 함께 정한다.

## 7. 대상과 판단에 맞는 자료를 준비한다

| 자료 | 준비할 내용 | 사용할 때 주의할 점 |
| :--- | :--- | :--- |
| 그림 | 경영진·현업에게는 시스템과 외부의 관계 및 업무 흐름을, 개발자에게는 컴포넌트와 실행 흐름을 보여 준다. | 판단에 필요한 상세 수준을 선택하고 구성요소와 화살표의 의미를 밝힌다. |
| 결정 기록 | 배경, 이유, 검토한 대안과 감수할 대가를 남긴다. | 나중에 합류한 사람도 같은 근거를 확인할 수 있어야 한다. |
| 작은 시연 | 캐시 적용 전후의 응답 시간 등 짧게 확인할 수 있는 증거를 준비한다. | 시연 조건과 운영 환경의 차이를 설명하고 결과를 과도하게 일반화하지 않는다. |

- 자료의 양보다 상대가 필요한 판단을 할 수 있는지가 중요하다.
- 같은 결정을 여러 자료로 설명할 때 구성요소 이름과 결정의 범위를 일관되게 유지한다.

## 8. 설득을 방해하는 네 가지 패턴을 피한다

| 실패 패턴 | 생기는 문제 | 바꿀 행동 |
| :--- | :--- | :--- |
| 기술 용어로 밀어붙인다. | 현업과 경영진에게 TTL·캐시 무효화·정합성만 설명해 업무 영향을 전달하지 못한다. | 상대가 책임지는 고객 경험, 비용과 업무 변화로 설명한다. |
| 대가를 숨긴다. | 재고 표시 지연 같은 부담을 적용 이후에 알게 된다. | 대가와 남은 위험을 먼저 공개한다. |
| 반대 의견을 이기려 한다. | 놓친 요구사항과 위험을 확인할 기회를 잃는다. | 반대의 근거와 상대가 지키려는 조건을 묻는다. |
| 일방적으로 설명한다. | 질문과 의견이 결정에 반영되지 않는다. | 질문을 받고 이해를 확인하며 재검토할 여지를 둔다. |

## 9. 반대 의견으로 결정을 개선하고 기록을 갱신한다

- 현업이 “일반 상품은 괜찮지만 행사 상품의 재고 표시 지연은 허용할 수 없다”고 말한다면 상품별로 다른 요구가 드러난 것이다.
- 설명을 반복하기보다 적용 범위와 데이터 조회 방식을 다시 검토한다.

| 구분 | 결정과 후속 검토 |
| :--- | :--- |
| 처음 제안 | 상품 정보와 재고 표시를 모두 캐시하고 최대 30초 지연을 허용한다. |
| 수정 제안 | 상품 정보는 캐시하되 행사 상품의 재고는 원본에서 별도로 조회한다. |
| 남는 대가 | 원본 DB 조회 부하가 늘어나므로 응답 시간과 DB 가용성을 다시 검증한다. |
| 검토한 다른 대안 | 재고 변경 시 캐시를 삭제하는 방식도 검토하지만 반영 시차와 실패 가능성을 평가해야 한다. |

- 원본 조회도 조회 직후의 재고 변경까지 막지는 못하므로 표시 최신성과 주문 확정의 정확성을 구분한다.
- 개발·운영 담당자는 변경된 조회 부하와 실패 동작을 적용 전에 확인하고, 현업 담당자는 상품별 허용 범위를 확인한다.
- 결정 기록에는 제안·채택 상태, 바뀐 요구와 이유, 새 대가와 검증할 내용을 남긴다.
- 이전 판단의 배경과 수정 결정의 관계도 보존한다.
- **설득은 같은 결정을 상대의 관심사로 설명하고, 그 과정에서 더 나은 결정에 합의하는 일이다.**
