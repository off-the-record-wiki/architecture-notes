# 개발자에서 아키텍트로: 결정과 책임의 범위를 넓히는 네 단계

## 1. 기술·사람·비즈니스를 함께 이해한다

- **아키텍트로 성장하려면 구현 역량을 바탕으로 사람과 업무까지 이해의 범위를 넓혀야 한다.**
- 기술적으로 가능한 구조라도 팀이 실행하거나 운영할 수 없으면 목표를 달성하기 어렵다.
- 업무 목표와 제약을 모르면 기술 선택의 우선순위도 정하기 어렵다.
- 기술, 사람과 비즈니스 역량은 서로 연결되어 설계 결정과 실행에 영향을 준다.

| 역량 | 수행할 일 | 확인할 질문 |
| :--- | :--- | :--- |
| 기술 | 설계 대안을 비교하고 구조를 분석하며 구현·운영 결과를 확인한다. | 이 결정은 어떤 품질을 개선하고 어떤 비용과 위험을 남기는가? |
| 사람 | 이해관계자의 우려를 듣고 설명하며 팀 사이의 의견을 조율한다. | 누가 영향을 받고 누구와 어떤 내용을 합의해야 하는가? |
| 비즈니스 | 업무 도메인, 고객 가치와 일정·예산 등의 제약을 이해한다. | 해결하려는 업무 문제는 무엇이며 반드시 지켜야 할 조건은 무엇인가? |

- 조직의 의사결정 구조와 각 역할의 책임을 이해하면 협의할 대상을 찾기 쉽다.
- 조직 안의 이해관계를 파악하되 판단의 근거와 감수할 대가는 투명하게 공유한다.
- 결정을 내린 뒤에도 실제 요구 충족 여부와 운영 부담을 확인한다.

## 2. 기술의 깊이를 유지하면서 선택지의 폭을 넓힌다

- 깊이는 직접 구현하고 운영하며 얻은 구체적인 지식이다.
- 넓이는 아직 깊이 다루지 않은 기술과 접근법의 존재, 적용 조건과 한계를 아는 것이다.
- 모든 기술을 같은 깊이로 익힐 필요는 없지만 필요한 순간에 조사하고 비교할 수 있어야 한다.

| 지식의 상태 | 의미 | 학습 방향 |
| :--- | :--- | :--- |
| 알고 있는 것 | 직접 다뤄 보며 동작과 한계를 설명할 수 있는 영역이다. | 구현·운영 경험으로 지식을 유지하고 변화한 조건을 확인한다. |
| 모른다는 것을 아는 것 | 존재는 알지만 판단에 필요한 이해가 부족한 영역이다. | 적용 조건을 조사하고 필요하면 전문가와 함께 평가하거나 실험한다. |
| 모르는 줄도 모르는 것 | 선택지나 위험으로 인식하지 못한 영역이다. | 다른 분야의 사례, 리뷰와 협업을 통해 새로운 질문과 대안을 발견한다. |

- 새로운 선택지를 알게 되는 것과 실제 요구를 충족한다고 검증하는 것은 다르다.
- 기술 이름을 많이 아는 것보다 현재 문제와 연결해 비교할 수 있는지가 중요하다.
- 익숙한 기술만으로 모든 문제를 해결하려 하지 않고, 새로운 기술도 유행만으로 채택하지 않는다.

## 3. 성장 단계는 직급보다 결정의 범위로 구분한다

- 다음 네 단계는 다루는 문제와 책임의 범위가 넓어지는 과정을 설명한다.
- 승진 순서나 반드시 거쳐야 하는 경력 경로를 뜻하지 않는다.
- 같은 직함으로 여러 범위의 일을 맡을 수 있고 조직과 업무에 따라 이동 순서도 달라질 수 있다.

| 단계 | 결정의 범위 | 넓혀 갈 질문 |
| :--- | :--- | :--- |
| 1단계 | 코드 | 이 기능을 왜 이 방식으로 구현해야 하는가? |
| 2단계 | 모듈·팀 | 이 결정이 다른 모듈과 팀에 어떤 영향을 주는가? |
| 3단계 | 시스템 | 품질 목표를 달성하고 남은 위험을 감당할 수 있는가? |
| 4단계 | 여러 시스템·조직 | 여러 시스템과 팀의 목표를 어떻게 조율할 것인가? |

- 범위가 넓어진다고 이전 범위의 이해가 불필요해지는 것은 아니다.
- 코드와 운영의 실제 제약을 이해해야 시스템 수준의 판단도 실행 가능한 결정으로 이어진다.

## 4. 코드 수준: 구현 방법의 이유와 변경 영향을 살펴본다

- 기능을 완성하는 것과 함께 현재 구조를 선택한 이유를 이해한다.
- 조건문, 인터페이스와 책임 분리가 변경 비용에 어떤 영향을 주는지 확인한다.
- 아래 주문·결제 사례는 질문을 구체화하기 위한 가상 사례이다.

| 질문 | 살펴볼 내용 |
| :--- | :--- |
| 결제 수단이 늘 때 조건문을 추가할까, 수단별 책임을 나눌까? | 현재 변형의 종류, 변경 빈도와 추상화 비용을 비교한다. |
| 결제 코드를 바꾸면 어디까지 영향을 줄까? | 호출 코드, 테스트와 다른 모듈의 의존을 확인한다. |
| 처음에는 왜 이 구조를 선택했을까? | 당시 요구사항과 제약, 지금 달라진 전제를 확인한다. |

- 맡은 코드의 설계 결정 하나를 골라 이유와 대안을 설명해 본다.
- 작은 변경이 퍼지는 경로를 추적하고 실제 코드와 테스트로 영향을 확인한다.
- 설계 리뷰에서 결론뿐 아니라 어떤 조건을 기준으로 결정했는지 살펴본다.
- 단순한 구조 유지와 부분 개선도 대안에 포함하고 변경의 이점과 비용을 함께 판단한다.

## 5. 모듈·팀 수준: 경계와 계약을 함께 정하고 기록한다

- 모듈 내부의 동작뿐 아니라 다른 모듈·팀과 공유하는 계약을 다룬다.
- 합의가 필요한 결정과 합의한 경계 안에서 팀이 정할 상세 설계를 구분한다.

| 질문 | 살펴볼 내용 |
| :--- | :--- |
| 결제 응답 형식을 바꾸면 주문 팀은 무엇을 수정해야 할까? | 호출 계약, 호환성과 변경 순서를 확인한다. |
| 결제 재시도 정책을 우리 팀만 정해도 될까? | 중복 요청·처리와 사용자 동작에 미치는 영향을 관련 팀과 확인한다. |
| 나중에 합류한 사람도 이 결정을 이해할 수 있을까? | 맥락, 대안과 선택의 결과가 기록에 남아 있는지 확인한다. |

- 팀의 설계 리뷰를 진행하며 책임 경계와 인터페이스 변경을 관련 팀과 협의한다.
- 중요한 결정은 기존 기록 형식에 맞춰 배경, 대안, 선택 이유와 대가를 남긴다. ADR도 사용할 수 있다.
- 적용 범위, 담당 역할과 변경 순서를 명확히 하고 제안과 채택 상태를 구분한다.
- 계약 안의 상세 설계까지 일률적으로 추가 승인을 요구하지 않는다.

## 6. 시스템 수준: 품질 목표와 위험을 검증한다

- 기능이 존재하는지에서 나아가 정상·실패·변경 조건에서도 필요한 동작을 유지하는지 판단한다.
- 개별 모듈의 성능과 시스템 전체의 사용자 경험을 구분한다.

| 질문 | 살펴볼 내용 |
| :--- | :--- |
| 행사 부하에서도 주문부터 결제까지 목표 응답 시간을 지킬 수 있을까? | 전체 요청 경로, 병목과 자원 경합을 확인한다. |
| 결제 장애가 주문 전체를 멈추게 하지 않을까? | 실패 전파 경로, 대기와 복구 방식을 확인한다. |
| 장애 대응 설계가 비용이나 고객 경험을 바꾸면 수용할 수 있을까? | 경영진·현업·개발·운영 담당자의 우려와 필수 조건을 확인한다. |

- 핵심 품질 목표에는 대상, 적용 조건, 기대 동작과 측정·판정 기준을 적는다.
- 목표 개수를 채우기보다 업무 영향이 크고 설계 선택을 바꾸는 조건을 우선한다.
- 같은 부하와 실패 시나리오로 대안을 비교하고 기대 효과와 남은 위험을 설명한다.
- 구현 후에는 테스트와 운영 자료로 효과를 확인하고 검증 범위와 운영 환경의 차이를 남긴다.
- 확인하지 못한 가정에는 담당 역할, 확인 시점과 재검토 조건을 정한다.

## 7. 여러 시스템·조직 수준: 공통 원칙과 목표를 조율한다

- 주문·결제·정산·물류처럼 여러 시스템이 연결되면 한 시스템의 개선이 다른 팀의 비용과 일정에 영향을 줄 수 있다.
- 공통 원칙을 정하는 일과 각 시스템이 상황에 맞게 선택할 범위를 함께 다룬다.

| 질문 | 살펴볼 내용 |
| :--- | :--- |
| 여러 시스템의 장애를 연결해서 추적할 수 있을까? | 오류 표현, 로그와 추적 정보의 공통 기준 및 담당 역할을 확인한다. |
| 결제 시스템을 교체하면 정산·물류는 언제 바꿔야 할까? | 시스템 간 계약과 데이터 의존, 전환 순서 및 각 팀의 일정을 확인한다. |
| 한 팀은 새 기능 출시를, 다른 팀은 안정화를 원하면 무엇을 먼저 할까? | 공동 업무 목표와 실패 영향을 기준으로 우선순위를 협의한다. |

- 시스템 간 의존 관계를 그릴 때 경계, 각 시스템의 책임과 화살표의 의미를 표시한다.
- 오류 처리·로깅·보안 등 공통 원칙은 여러 팀이 지켜야 하는 이유와 적용 범위를 함께 정한다.
- 모든 시스템을 같은 구현으로 통일하기보다 공통 계약이 필요한 부분과 자율적으로 정할 부분을 구분한다.
- 팀의 목표가 충돌하면 관련 책임자가 함께 선택할 수 있도록 대안과 영향을 정리한다.
- 필요하면 인프라, 정보와 전사 아키텍처 담당 역할과 협력해 더 넓은 제약을 확인한다.

## 8. 학습·기술 평가·구현 참여를 지속한다

- 일상 업무 안에서 학습 시간을 확보하고 관심 기술을 평가하며 구현 감각을 유지한다.
- 활동 자체보다 새로운 선택지를 발견하고 실제 판단에 연결하는 것을 목표로 한다.

| 습관 | 실행할 일 | 주의할 점 |
| :--- | :--- | :--- |
| 짧고 꾸준하게 학습한다. | 예를 들어 하루 20분을 정해 새 개념이나 다른 문제 해결 사례를 살펴본다. | 20분은 실천 예시이며 업무와 학습 목표에 맞춰 조정한다. |
| 개인 기술 레이더를 관리한다. | 관심 기술을 조사·실험하고 판단 이유와 다음 확인 사항을 기록한다. | 개인의 관심이나 평가를 조직의 도입 결정과 혼동하지 않는다. |
| 구현 감각을 유지한다. | PoC, 기술 부채 개선, 버그 수정, 자동화와 코드 리뷰에 참여한다. | 핵심 경로의 작업을 독점해 팀 전체가 기다리게 하지 않는다. |

- 기술 레이더는 기술 목록 작성 → 조사·실험 → 판단 기록 → 주기적 갱신의 흐름으로 관리할 수 있다.

| 상태 | 의미 |
| :--- | :--- |
| 도입 | 현재 적용 범위에서 실무에 사용하며 효과와 비용을 확인한다. |
| 시험 | 제한된 범위의 PoC로 가설과 적용 가능성을 확인한다. |
| 평가 | 해결할 문제와 적용 조건을 조사하며 검토한다. |
| 보류 | 현재 조건에서는 적용을 미루고 이유와 재검토 조건을 남긴다. |

- 작은 실험의 성공만으로 운영 규모에서도 같은 결과가 난다고 단정하지 않는다.
- 중요한 인터페이스와 위험에 우선적으로 참여하고 다른 사람이 이어서 구현·운영할 수 있도록 공유한다.

## 9. 현재 맡은 일에서 결정 하나부터 검토한다

| 실천 | 해 볼 일 | 확인할 결과 |
| :--- | :--- | :--- |
| 결정 하나를 기록한다. | 현재 작업의 설계 결정을 골라 이유, 대안과 대가를 적는다. | 다른 사람이 선택의 배경과 남은 가정을 이해할 수 있는지 확인한다. |
| 현재 구조를 그린다. | 맡은 모듈이나 시스템의 경계, 책임과 관계를 표현한다. | 구현과 일치하는지, 변경이 퍼지는 지점이나 위험을 놓치지 않았는지 확인한다. |
| 대안을 비교해 설명한다. | 동료에게 같은 조건으로 비교한 대안을 설명하고 의견을 받는다. | 피드백으로 달라진 판단과 추가로 검증할 내용을 반영한다. |

- 기록과 그림은 판단에 필요한 범위부터 만들고 기존 자료가 있으면 연결해 사용한다.
- 맡는 책임이 넓어질수록 혼자 결정하는 범위를 무조건 늘리기보다 함께 판단할 사람과 계약을 명확히 한다.
- **결정의 이유를 남기고, 영향을 설명하고, 실제 결과를 확인하는 습관으로 책임의 범위를 넓혀 간다.**
