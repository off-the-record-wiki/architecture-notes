# 아키텍처 갈등 관리: 상황에 맞는 다섯 가지 대응 전략

## 1. 기술적 판단을 실행하려면 갈등을 다룰 수 있어야 한다

- **갈등 관리의 목적은 자신의 의견을 관철하는 것이 아니라 사업 목표, 고객 가치와 필요한 품질을 함께 달성하는 것이다.**
- 아키텍트와 기술 리더의 결정은 일정, 비용과 다른 사람의 업무에 영향을 주므로 반대 의견이 생길 수 있다.
- 기술적으로 타당한 판단도 상대의 제약과 우려를 다루지 못하면 실행되기 어렵다.
- 결정을 계속 미루면 팀이 방향을 잃고, 일방적으로 강행하면 신뢰를 잃을 수 있다.
- 상황에 맞게 주장을 유지하거나 양보하고, 필요하면 함께 대안을 찾아야 한다.

| 반복되는 대응 | 생길 수 있는 문제 |
| :--- | :--- |
| 갈등이 생기면 결정을 미룬다. | 필요한 판단이 지연되고 해결되지 않은 문제가 쌓인다. |
| 항상 자신의 방식을 밀어붙인다. | 상대의 정보와 제약을 놓치고 협업 관계가 약해진다. |
| 기술적 논리만 설명한다. | 일정·조직·관계에서 생긴 우려를 다루지 못해 실행에 필요한 동의를 얻기 어렵다. |

- 사람에 대한 평가와 해결해야 할 쟁점을 구분한다.
- 장기적인 협업에서는 결정의 내용뿐 아니라 상대를 대하는 방식도 중요하다.

## 2. 자기주장과 협력성의 두 축으로 대응을 구분한다

- 자기주장은 자신의 관심사와 요구를 충족하려는 정도이다.
- 협력성은 상대의 관심사와 요구를 충족하려는 정도이다.
- 두 축을 기준으로 갈등 대응을 경쟁, 협력, 타협, 회피와 수용으로 구분할 수 있다.

| 전략 | 자기주장 | 협력성 | 대응 방식 |
| :--- | :--- | :--- | :--- |
| 경쟁(Competing) | 높다. | 낮다. | 자신의 판단이나 반드시 지킬 기준을 단호하게 유지한다. |
| 협력(Collaborating) | 높다. | 높다. | 양쪽의 중요한 요구를 충족할 대안을 함께 찾는다. |
| 타협(Compromising) | 중간이다. | 중간이다. | 양쪽이 일부를 양보해 수용 가능한 합의점을 찾는다. |
| 회피(Avoiding) | 낮다. | 낮다. | 논의를 잠시 멈추거나 해당 쟁점에 개입하지 않는다. |
| 수용(Accommodating) | 낮다. | 높다. | 자신의 선호를 내려놓고 상대의 요구를 따른다. |

- 다섯 전략 중 항상 우월한 전략은 없다. 문제의 중요도, 긴급성, 정보와 관계에 따라 선택한다.
- 협력도 충분한 논의 시간이 필요하므로 모든 상황에서 즉시 사용할 수 있는 것은 아니다.
- 특정 전략을 개인의 고정된 성격으로 보지 않고 상황에 따라 바꿀 수 있는 행동으로 다룬다.
- **익숙한 한 가지 방식만 반복하고 있지는 않은지 확인하는 것이 중요하다.**

## 3. 경쟁: 반드시 지킬 조건과 긴급한 대응을 분명히 한다

- 필수 조건이 위협받거나 피해 확산을 막기 위해 빠른 판단이 필요할 때 단호하게 대응한다.
- 자신의 취향과 반드시 지켜야 할 요구사항을 구분하고 판단의 근거를 설명한다.
- 아래는 대응 방식을 설명하기 위한 가상 사례이다.

| 상황 | 대응 | 확인할 조건 |
| :--- | :--- | :--- |
| 배포 전 SQL 인젝션 취약점이 발견됐지만 일정 때문에 배포를 요구한다. | 취약한 상태의 배포를 중단하고 수정과 검증을 우선한다. | 취약점의 영향과 배포 기준을 보안·개발 담당자가 확인한다. |
| 배포 이후 오류율이 급증했는데 일부는 더 지켜보자고 한다. | 정해진 장애 대응 기준에 따라 롤백 등 피해 완화 조치를 결정한다. | 롤백 가능 여부와 데이터 변경의 영향을 확인한다. |
| 사용 조건을 충족하지 못하는 외부 코드를 도입하려 한다. | 사용을 보류하고 제거하거나 대체할 방안을 정한다. | 정확한 사용 조건은 라이선스 담당 역할과 확인한다. |
| 긴급 수정이라는 이유로 검증을 전부 생략하려 한다. | 긴급 대응 절차에서 필요한 최소 검증과 복구 수단을 확보한다. | 현재 장애 피해와 변경 위험을 함께 고려한다. |

- 장애 대응에서 빠른 판단은 중요하지만 모든 오류에 롤백이 적합한 것은 아니다.
- 테스트에 필요한 시간은 변경 범위에 따라 달라지며 고정된 시간으로 단정하지 않는다.
- 결정 권한과 담당 역할에 맞춰 행동하고 조치 이후에 근거와 결과를 공유한다.
- 경쟁을 일상적인 의견 차이마다 사용하면 반대 의견이 숨겨지고 신뢰가 약해질 수 있다.

## 4. 협력: 서로의 중요한 요구를 충족할 대안을 찾는다

- 양쪽의 관심사가 모두 중요하고 함께 해결책을 찾을 시간이 있을 때 사용한다.
- 상대가 주장하는 해법보다 그 해법으로 달성하려는 목표와 제약을 먼저 확인한다.
- 기술 대안뿐 아니라 적용 범위, 출시 순서와 업무 방식의 변경도 검토한다.

| 진행할 일 | 확인할 내용 |
| :--- | :--- |
| 공통 목표를 정한다. | 고객에게 제공할 가치와 지켜야 할 품질은 무엇인가? |
| 충돌하는 요구를 구체화한다. | 일정, 기능 범위와 검증 중 어떤 조건이 충돌하는가? |
| 대안을 함께 만든다. | 단계적 출시나 기존 기능 활용으로 중요한 요구를 함께 충족할 수 있는가? |
| 같은 기준으로 비교한다. | 각 대안의 효과, 비용과 실패 위험은 무엇인가? |
| 실행 조건을 합의한다. | 누가 구현·검증하고 어떤 결과일 때 적용하거나 재검토하는가? |

- 협력은 무조건 상대를 설득하거나 모두의 요구를 그대로 더하는 활동이 아니다.
- 모든 필수 조건을 만족하는 대안이 없다면 범위, 일정과 자원을 다시 협의한다.
- 합의한 방향의 효과가 불확실하면 작은 실험으로 확인할 수 있다.

## 5. 타협: 조정 가능한 범위를 서로 양보한다

- 제한된 시간 안에서 수용 가능한 결론이 필요하고 양쪽이 일부 요구를 조정할 수 있을 때 사용한다.
- 기능 범위, 적용 시점이나 우선순위에서 무엇을 양보할지 구체적으로 정한다.
- 협력이 중요한 요구를 함께 충족하는 해법을 찾는 데 집중한다면, 타협은 서로 일부를 양보하는 데 집중한다.

| 가상 사례 | 가능한 타협 | 남겨야 할 내용 |
| :--- | :--- | :--- |
| 출시 전에 여러 추가 기능을 요구한다. | 고객 가치가 큰 일부 기능만 먼저 제공한다. | 제외한 기능과 후속 검토 시점을 남긴다. |
| 두 팀이 같은 시점에 제한된 작업 자원을 필요로 한다. | 우선 적용 범위와 작업 순서를 나눈다. | 각 팀이 감수하는 지연과 업무 영향을 확인한다. |
| 장기 개선과 단기 출시 준비가 충돌한다. | 출시에는 필수 개선을 반영하고 나머지는 후속 작업으로 정한다. | 남은 위험과 담당 역할, 확인 시점을 명시한다. |

- 필수 보안 조건이나 금지된 실패를 절반만 지키는 방식으로 타협하지 않는다.
- 임시 합의가 영구적인 기술 부채로 남지 않도록 후속 작업의 책임과 확인 시점을 정한다.

## 6. 회피: 논의할 시점과 개입할 범위를 선택한다

- 감정이 격해졌거나 판단에 필요한 정보가 부족할 때 논의를 잠시 멈출 수 있다.
- 결과에 영향이 거의 없는 취향의 차이라면 개입하지 않는 것도 선택이다.
- 해결이 필요한 문제를 미루는 경우에는 다시 논의할 조건과 시점을 정한다.

| 가상 사례 | 대응 | 다시 확인할 내용 |
| :--- | :--- | :--- |
| 회의가 감정싸움으로 번진다. | 논의를 중단하고 진정할 시간을 둔다. | 다음 회의 시점과 다룰 쟁점을 정한다. |
| 트래픽·예산·고객 요구 없이 클라우드 제품을 논쟁한다. | 제품 선택을 잠시 보류한다. | 요구사항과 비용 정보를 누가 언제 정리할지 정한다. |
| 개인이 사용할 IDE 취향으로 논쟁한다. | 공통 작업에 영향이 없다면 개인 선택에 맡긴다. | 보안 정책이나 공통 개발 절차에 제약이 있는지 확인한다. |
| 코드 리뷰로 두 개발자의 감정이 상한다. | 즉석에서 편을 가르기보다 시간을 두고 함께 이야기한다. | 리뷰 근거와 팀의 판단 기준을 확인한다. |
| 고객 요구가 계속 바뀐다. | 되돌리기 어려운 상세 설계를 잠시 보류한다. | 요구 정리 담당자와 결정 기한, 지연의 영향을 확인한다. |

- 기다리는 동안에도 정보 수집과 영향 분석 등 진행 가능한 일은 이어간다.
- 긴급한 장애나 명백한 필수 조건 위반을 방치하는 데 회피를 사용하지 않는다.
- **회피는 의도적인 시점 선택이어야 하며, 책임을 피하는 습관이 되어서는 안 된다.**

## 7. 수용: 영향이 작은 차이는 상대의 선택을 존중한다

- 자신의 선호보다 상대에게 중요한 요구이고 결과에 미치는 부담이 작을 때 사용할 수 있다.
- 상대가 더 많은 전문 지식이나 업무 맥락을 가지고 있다면 그 판단을 따르는 것도 가능하다.

| 가상 사례 | 수용할 수 있는 조건 |
| :--- | :--- |
| 디자이너가 버튼 색상과 글꼴 크기를 제안한다. | 접근성·가독성과 제품 기준을 충족하고 다른 필수 요구에 영향을 주지 않는다. |
| PM이 익숙한 진행 보고서 형식을 요청한다. | 필요한 정보를 전달할 수 있고 작성 부담이 수용 가능하다. |
| 팀원의 사정으로 회의 시간 변경을 요청한다. | 다른 참석자와 일정에 큰 지장이 없다. |

- 사소해 보이는 UI 선택도 접근성이나 사용성에 영향을 줄 수 있으므로 영향부터 확인한다.
- 관계를 유지하려고 핵심 품질 문제나 감당할 수 없는 업무를 계속 수용하지 않는다.
- 양보한 범위를 명확히 하고 자신의 의견을 말할 기회도 유지한다.

## 8. 일정 압박에는 목표와 품질 조건을 함께 놓고 대응한다

- 다음은 출시 3주 전에 PM이 경쟁사 대응을 이유로 기능 추가를 요청하는 가상 사례이다.
- 기능 구현은 가능하지만 테스트 기간이 줄어들고 기술 부채가 늘어날 것으로 예상한다.
- PM은 상위 의사결정자의 압박을 받고 있으며 장기적인 협업 관계도 중요하다.
- 3주는 사례의 조건이며 기능 추가 가능 여부를 판단하는 일반적인 기준은 아니다.

| 전략 | 가능한 행동 | 주의할 점 |
| :--- | :--- | :--- |
| 경쟁 | 필수 검증을 생략해야 한다면 현재 조건의 요청을 거절한다. | 불가능한 이유와 변경해야 할 전제를 설명한다. |
| 협력 | 고객 가치가 큰 최소 범위, 단계적 출시와 일정 조정안을 함께 찾는다. | 개발·QA·PM이 같은 조건으로 비용과 위험을 비교한다. |
| 타협 | 일부 기능만 이번 출시에 포함하고 나머지는 이후에 검토한다. | 축소 범위에서도 필수 품질을 만족하는지 확인한다. |
| 회피 | 영향 분석에 필요한 짧은 시간을 확보한 뒤 결정을 이어간다. | 출시가 임박한 요청을 기한 없이 미루지 않는다. |
| 수용 | 기존 검증과 품질 조건을 지킬 수 있을 때 요청을 받아들인다. | 관계 유지를 위해 위험을 숨기거나 무조건 수용하지 않는다. |

- 먼저 반드시 지킬 조건과 조정 가능한 목표를 구분한다.
- 추가 요구의 사업 가치, 개발·검증 비용과 출시 실패의 영향을 함께 비교한다.
- 일정·범위·자원 변경은 해당 책임자와 협의하고, 남은 가정은 담당 역할과 확인 시점을 정한다.
- 하나의 상황에서도 처음에는 논의를 멈추고 정보를 모은 뒤 협력하거나 타협하는 식으로 전략을 전환할 수 있다.

## 9. 일상적인 행동으로 장기적인 신뢰를 쌓는다

- 협업 관계의 신뢰는 약속과 배려가 쌓이거나 훼손되는 통장에 비유할 수 있다.
- 평소의 행동은 갈등이 생겼을 때 서로의 설명을 듣고 함께 문제를 해결할 수 있는 기반이 된다.

| 신뢰를 쌓는 행동 | 신뢰를 약화시키는 행동 |
| :--- | :--- |
| 약속을 지키고 변경이 필요하면 미리 알린다. | 약속을 어기고 설명하지 않는다. |
| 상대의 입장과 제약을 먼저 듣는다. | 상대의 우려를 무시하고 결정을 강행한다. |
| 성과에 기여한 사람을 인정한다. | 공을 독차지하거나 공개적으로 체면을 깎는다. |
