# 시니어 개발자의 판단력: 규칙 적용에서 맥락 이해로 성장하기

## 1. 경력이 쌓인다고 판단력이 자동으로 성장하지는 않는다

- **성장은 일한 시간뿐 아니라 어떤 문제를 경험하고 그 결과로 판단 방식을 어떻게 바꿨는지에 달려 있다.**
- 익숙한 일을 반복하면 처리 속도는 빨라질 수 있지만 낯선 문제를 이해하는 능력까지 같은 비율로 늘어나는 것은 아니다.
- 기술 지식을 많이 아는 것과 현재 상황에서 중요한 조건을 구분하는 능력도 다르다.
- 경력 연수만으로 시니어의 역량을 판단하기보다 문제를 바라보고 결정을 내리는 방식을 살펴본다.

| 살펴볼 내용 | 확인할 질문 |
| :--- | :--- |
| 경험의 범위 | 익숙한 기능 개발 외에 다른 도메인, 장애와 운영 문제를 다뤄 봤는가? |
| 맥락의 이해 | 구현 방법을 정하기 전에 목적과 제약을 확인하는가? |
| 판단의 변화 | 과거의 해법이 맞지 않는 조건을 구분할 수 있는가? |
| 피드백의 활용 | 예상과 실제 결과의 차이를 확인하고 다음 결정에 반영하는가? |

- 같은 일을 반복하더라도 결과를 비교하고 가정을 수정하면 학습으로 이어질 수 있다.
- 새로운 경험의 수보다 경험에서 무엇을 배웠고 다음 판단에 어떻게 반영했는지가 중요하다.

## 2. 다섯 단계로 규칙과 상황을 다루는 방식의 차이를 이해한다

- 드레이퍼스 모델은 기술 습득 과정에서 규칙 의존과 상황 인식이 어떻게 달라지는지 설명하는 틀이다.
- 단계는 특정 도메인에서의 숙련도를 나타내며 사람 전체의 등급이나 조직의 직급을 뜻하지 않는다.
- 개발 실무에 적용하면 다음과 같이 판단 방식의 차이를 살펴볼 수 있다.

| 단계 | 판단 방식 | 개발 실무에서의 예시 |
| :--- | :--- | :--- |
| 초보자(Novice) | 명시적인 규칙과 절차에 의존하며 상황에 따른 예외 판단이 어렵다. | 다형성을 사용하라는 원칙을 상황과 관계없이 적용한다. |
| 초급자(Advanced Beginner) | 유사한 경험을 활용하기 시작하지만 무엇이 중요한지 구분하는 데 도움이 필요하다. | 비슷한 사례에서 썼던 해법을 떠올리지만 조건의 차이를 놓칠 수 있다. |
| 유능한 수행자(Competent) | 목표와 우선순위를 정하고 대안을 분석해 행동을 계획한다. | 여러 설계 대안을 비용과 요구사항에 비춰 비교한다. |
| 숙련자(Proficient) | 전체 상황과 중요한 특징을 먼저 파악하고 행동은 분석해 결정한다. | 설계에서 이상 징후를 빠르게 알아차린 뒤 원인과 대안을 검토한다. |
| 전문가(Expert) | 익숙한 도메인에서는 상황 인식과 적절한 대응이 자연스럽게 연결된다. | 문제를 보고 유력한 해결 방향을 빠르게 떠올리며 필요하면 분석으로 확인한다. |

- 모든 사람이 같은 속도로 성장하거나 모든 업무에서 같은 단계에 있는 것은 아니다.
- 익숙한 도메인의 전문가도 새로운 기술이나 업무 영역에서는 명시적인 절차와 도움을 필요로 할 수 있다.
- 이 구분을 승진 점수표로 사용하기보다 현재 필요한 경험과 지원을 찾는 데 활용한다.

## 3. 유능함에서 숙련으로의 전환은 전체 맥락을 먼저 보는 데 있다

- 유능한 수행자는 여러 규칙과 대안을 분석해 우선순위를 정할 수 있다.
- 숙련자는 상황을 보면서 무엇이 중요한지 먼저 알아차리고 그에 맞춰 분석의 초점을 잡는다.
- 중요한 변화는 분석의 속도뿐 아니라 분석할 대상을 선택하는 방식에 있다.

| 관점 | 규칙 중심의 접근 | 맥락을 함께 보는 접근 |
| :--- | :--- | :--- |
| 요구사항 | 요청받은 기능을 어떻게 구현할지 생각한다. | 왜 필요한지, 만들지 않고도 목표를 달성할 수 있는지 확인한다. |
| 설계 원칙 | 널리 알려진 방식을 그대로 적용한다. | 원칙이 해결하려는 문제와 현재 조건이 일치하는지 확인한다. |
| 문제 발견 | 정해진 점검 항목에서 위반을 찾는다. | 전체 흐름에서 이상한 관계나 빠진 조건을 알아차린 뒤 조사한다. |
| 대안 선택 | 기술의 일반적인 장단점을 비교한다. | 업무 목표, 팀의 역량과 운영 부담을 포함해 비교한다. |

- 맥락을 고려한다는 이유로 계약, 보안 정책과 필수 품질 조건을 임의로 무시하지 않는다.
- 변경 가능한 설계 원칙과 반드시 지켜야 하는 제약조건을 구분한다.
- **규칙의 적용 여부를 판단하려면 그 규칙이 필요한 이유와 성립 조건을 이해해야 한다.**

## 4. 전문가의 직관도 확인과 설명이 필요하다

- 전문가는 익숙한 상황에서 매번 규칙을 하나씩 대입하지 않고도 유력한 대응을 떠올릴 수 있다.
- 이는 규칙을 모른다는 뜻이 아니라 축적한 경험을 바탕으로 상황의 패턴을 빠르게 인식한다는 뜻이다.
- 다음 흐름은 단계별 차이를 이해하기 위한 단순화된 표현이다.

| 단계 | 상황에서 행동으로 이어지는 흐름 |
| :--- | :--- |
| 초보자 | 주어진 규칙을 확인하고 행동한다. |
| 유능한 수행자 | 상황을 확인하고 규칙·대안을 선택한 뒤 분석해 행동한다. |
| 숙련자 | 중요한 상황을 직관적으로 인식하고 분석해 행동을 선택한다. |
| 전문가 | 익숙한 상황에서 대응이 빠르게 떠오르며 필요할 때 분석으로 전환한다. |

- 빠르게 떠오른 해법이 항상 옳은 것은 아니다. 과거와 조건이 다르면 잘못된 패턴을 적용할 수 있다.
- 낯선 문제나 실패 영향이 큰 결정에서는 가정을 드러내고 검증한다.
- 이상하다는 느낌은 조사할 단서로 사용하고 결함이 확인됐다는 사실과 구분한다.
- 중요한 결정은 판단 근거와 감수할 대가를 설명해 다른 사람도 검토할 수 있게 한다.
- 직관을 즉시 언어로 설명하기 어렵더라도 틀린 판단이라고 단정할 수는 없다. 다만 실행의 근거가 필요한 결정에는 분석과 증거를 보완한다.

## 5. 시니어의 판단은 개인의 문제 해결을 넘어 팀에 기여한다

- 시니어 개발자의 역할을 숙련자·전문가의 특징과 연결하면 전체 맥락을 이해하고 중요한 문제를 먼저 찾는 행동으로 설명할 수 있다.
- 조직의 시니어 역할에는 협업과 책임도 포함되므로 숙련도 단계만으로 직급을 결정할 수는 없다.

| 실무 행동 | 판단력에 드러나는 특징 |
| :--- | :--- |
| 무엇을 만들지보다 왜 필요한지 먼저 묻는다. | 기능 구현을 업무 목표와 연결한다. |
| 익숙한 해법도 현재 조건에서 다시 비교한다. | 적용 조건과 트레이드오프를 구분한다. |
| 코드와 설계에서 이상 징후를 발견한다. | 경험에서 얻은 단서를 분석과 검증으로 이어 간다. |
| 문제를 보면 해결 방향을 제안한다. | 가정, 대안과 확인할 위험을 함께 제시한다. |
| 팀원이 스스로 판단할 수 있게 돕는다. | 자신의 경험을 질문, 설명과 리뷰 기준으로 공유한다. |

- 자신만 빠르게 해결하면 팀이 같은 판단을 반복하기 어렵다.
- 결과뿐 아니라 어떤 조건을 중요하게 봤고 어떤 대안을 제외했는지 공유한다.
- 설명하는 과정에서 드러난 빈틈과 팀원의 반대 의견은 자신의 판단을 개선할 기회가 된다.

## 6. 판단력을 기르기 위한 경험을 의도적으로 설계한다

- 익숙한 일의 반복에서 벗어나 상황을 해석하고 결과를 확인하는 연습을 한다.
- 경험의 난도는 현재 역량에 맞추고 필요한 리뷰와 지원을 확보한다.

| 훈련 | 실행할 행동 | 확인할 내용 |
| :--- | :--- | :--- |
| 낯선 상황을 경험한다. | 잘 모르는 도메인·서비스·계층의 문제를 맡거나 함께 해결한다. | 기존 해법이 통하지 않은 조건과 새로 배운 판단 기준을 정리한다. |
| 맥락을 읽는다. | 요구사항을 받으면 목적, 사용자와 업무 영향을 먼저 묻는다. | 기능 요청과 실제로 달성할 목표가 같은지 확인한다. |
| 판단을 기록하고 회고한다. | 결정 당시의 이유와 기대 결과를 남기고 실제 결과와 비교한다. | 무엇을 맞게 봤고 어떤 가정을 놓쳤는지 확인한다. |
| 설명하고 가르친다. | 비개발자와 팀원에게 선택의 이유와 대가를 설명한다. | 설명이 막히는 부분과 상대가 다르게 이해한 부분을 찾는다. |
| 실패 경험을 구조화한다. | 장애와 문제 해결을 발생 조건·징후·원인·대응으로 정리한다. | 다음에 비슷한 징후를 발견했을 때 확인할 항목을 남긴다. |

- 낯선 경험을 얻기 위해 준비 없이 영향이 큰 운영 변경을 맡을 필요는 없다.
- 작은 범위의 작업, 공동 문제 해결과 실험으로도 기존 판단의 한계를 확인할 수 있다.
- 훈련의 결과는 작업 수보다 판단 근거와 결과 확인 방식이 어떻게 달라졌는지로 살펴본다.

## 7. 기록과 피드백으로 경험을 다음 판단에 연결한다

- 판단 당시의 정보와 결과를 함께 남겨야 경험을 다른 상황에 적용하기 쉽다.
- 처음부터 긴 기록을 만들기보다 다음 결정에서 다시 쓸 수 있는 내용을 중심으로 정리한다.

| 기록할 내용 | 확인할 질문 |
| :--- | :--- |
| 상황과 목표 | 어떤 문제와 제약 아래에서 무엇을 달성하려 했는가? |
| 판단과 이유 | 무엇을 선택했고 어떤 단서를 중요하게 봤는가? |
| 대안과 가정 | 다른 해법을 제외한 이유와 확인되지 않은 전제는 무엇인가? |
| 기대 결과 | 어떤 변화가 생길 것으로 예상했고 어떻게 확인하려 했는가? |
| 실제 결과 | 어떤 조건에서 무엇을 확인했고 예상과 어디가 달랐는가? |
| 다음 행동 | 비슷한 상황에서 무엇을 반복하고 무엇을 바꿀 것인가? |

- 결과가 좋았다는 이유만으로 판단 과정 전체가 타당했다고 보지는 않는다.
- 결과가 나빴다면 정보 부족, 잘못된 가정과 실행상의 문제를 구분해 살펴본다.
- 실패 사례는 원인 하나로 단순화하지 않고 발생 조건과 함께 공유한다.
- **성장을 이어 가려면 경험을 쌓는 것과 함께 판단을 검토하고 수정하는 과정을 반복해야 한다.**
