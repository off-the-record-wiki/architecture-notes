# ADR: 아키텍처 결정의 이유와 결과를 기록하기

## 1. 선택한 구조와 함께 판단 근거를 남긴다

- **ADR(Architecture Decision Record)은 아키텍처에 중요한 결정 하나와 그 배경·결과를 기록하는 문서이다.**
- 코드와 구성도에서 무엇을 선택했는지 확인할 수 있어도 당시의 요구사항, 제약조건과 대안을 복원하기는 어렵다.
- ADR은 다음 변경을 검토하는 사람이 기존 선택의 이유를 이해하도록 돕는다.
- 시스템 구조, 품질 특성, 중요한 의존성·인터페이스와 구현 방식에 영향을 주는 결정을 기록 대상으로 삼는다.

## 2. 기본 형식으로 결정의 맥락을 설명한다

- Michael Nygard가 제안한 기본 형식은 다음과 같다.

| 항목 | 기록할 내용 |
| :--- | :--- |
| Title | 어떤 문제에 어떤 선택을 했는지 식별할 수 있는 제목을 쓴다. |
| Status | 제안·채택·폐기·대체 등 결정의 상태를 표시한다. |
| Context | 요구사항, 제약조건과 서로 충돌하는 조건을 설명한다. |
| Decision | 무엇을 하기로 했는지 완결된 문장으로 쓴다. |
| Consequences | 이점뿐 아니라 불리한 영향과 이후에 생기는 책임을 기록한다. |

- 대안 비교가 필요하면 검토한 선택지, 판단 기준과 선택 이유를 추가한다.
- MADR은 검토 대안과 선택 결과를 구조화하고, 결정 준수 여부를 확인하는 방법도 기록할 수 있는 템플릿이다.
- 양식을 늘리기 전에 **어떤 조건 때문에 이 선택을 했는지**가 드러나는지 확인한다.

## 3. 주문 알림 처리 결정의 예시

- 아래는 기본 형식에 대안·검증 항목을 추가한 가상의 ADR이다.

| 항목 | 예시 |
| :--- | :--- |
| 제목 | 주문 확정 후 알림을 별도 워커에서 처리한다. |
| 상태 | 제안 상태이며 개발·운영 담당자의 검토를 기다린다. |
| 배경 | 알림 전송 지연이 주문 응답에 영향을 주고 있다. 업무 담당자는 주문 확정과 알림 수신 사이의 지연을 허용한다. |
| 대안 | 주문 요청 안에서 알림을 전송하거나, 작업을 영속적으로 기록한 뒤 별도 워커가 전송한다. |
| 제안하는 결정 | 주문 확정과 알림 작업 기록을 같은 DB 트랜잭션으로 저장하고, 워커가 미처리 작업을 읽어 전송한다. |
| 선택 이유 | 주문 응답의 외부 알림 서비스 의존성을 줄이고, 전송 전에 프로세스가 종료되어도 작업을 다시 찾을 수 있게 한다. |
| 결과와 부담 | 워커·작업 보관·재시도 정책을 운영해야 한다. 전송 성공 후 완료 기록이 실패하면 재시도 과정에서 중복 알림이 발생할 수 있다. |
| 검증 | 워커 중단과 전송 응답 유실을 재현해 작업 복구와 중복 처리 방식을 확인하고, 합의한 알림 지연 목표를 측정한다. |
| 재검토 조건 | 지연 목표를 충족하기 어렵거나 작업 조회가 주문 DB의 부하에 영향을 주면 작업 전달 구조를 다시 검토한다. |

- 제안 상태의 결정과 검증이 끝난 결과를 구분한다.
- “비동기이므로 성능이 좋아진다”보다 제거하려는 대기 구간과 새로 감당할 운영 책임을 구체적으로 적는다.
- 관련 품질 목표와 테스트 결과는 원본 문서를 링크해 근거를 추적할 수 있게 한다.

## 4. 결정이 바뀌면 이력을 연결한다

- 합의 전에는 `Proposed`, 채택되면 `Accepted`처럼 상태를 관리한다.
- 기존 결정을 다른 선택으로 대체하면 새 ADR을 작성하고, 이전 ADR에 `Superseded` 상태와 새 문서의 링크를 남긴다.
- 이전 선택의 배경을 지우면 왜 구조가 바뀌었는지 설명하기 어려워진다.
- 오탈자와 링크는 고칠 수 있지만 과거의 판단을 현재의 결론으로 덮어쓰지 않는다.
- 예를 들어 `docs/adr/0001-process-order-notifications-asynchronously.md`처럼 식별 가능한 경로에 두고 코드 변경과 함께 검토할 수 있다.

## 5. 재검토에 쓸 수 있는 기록인지 확인한다

- 선택한 대안이 당시의 요구사항과 제약조건에 어떻게 대응하는지 확인한다.
- 다른 대안을 제외한 이유가 취향이나 제품 인지도에 머물지 않는지 확인한다.
- 기대 효과, 측정 결과와 아직 남은 가정을 구분한다.
- 추가 운영 비용과 실패 처리 책임이 드러나는지 확인한다.
- 결정의 영향 범위가 바뀌었을 때 다시 검토할 조건을 남긴다.

## 6. 레퍼런스
