# 가벼운 아키텍처 리뷰: 중요한 변경의 위험을 먼저 찾기

## 1. 검토할 결정과 품질 목표를 좁힌다

- **가벼운 아키텍처 리뷰는 특정 변경이 요구사항과 기존 구조에 미치는 영향을 함께 검토하는 방식으로 운영할 수 있다.**
- iSAQB는 아키텍처 분석의 목적으로 위험 식별, 요구 충족 여부와 구현의 설계 준수 여부 확인을 제시한다.
- 아래 절차와 체크리스트는 이 원칙과 C4·arc42의 지침을 바탕으로 구성한 팀 리뷰 예시이다. 공식 ATAM 절차는 [별도 문서](05_evaluating_architecture_with_atam.md)에서 다룬다.
- 리뷰를 시작할 때 “이번에 어떤 결정을 내려야 하는가”와 “어떤 실패가 가장 큰 영향을 주는가”를 정한다.

## 2. 판단에 필요한 자료를 준비한다

| 준비할 자료 | 확인하려는 내용 |
| :--- | :--- |
| 변경 목적과 범위 | 해결하려는 문제와 영향을 받는 사용자·시스템을 확인한다. |
| 중요 품질 시나리오 | 부하·장애·변경 조건과 기대 결과를 확인한다. |
| 현재 구조와 변경안 | 경계, 책임과 의존성의 차이를 확인한다. |
| 주요 실행 흐름 | 정상 처리와 중요한 실패 시나리오를 따라간다. |
| 결정 근거 | 대안, 제약조건과 감수할 비용을 확인한다. |
| 검증 자료 | 테스트·측정 결과와 아직 확인하지 못한 가정을 구분한다. |

- 독자가 구조를 읽을 수 있도록 다이어그램의 범위, 요소의 책임과 화살표의 의미를 표시한다.
- 자료가 없는 부분은 미확인 사항으로 남기고, 그 불확실성이 결정을 막는지 판단한다.
- 예를 들어 외부 연동을 바꾸는 리뷰에는 해당 계약을 아는 담당자와 실패 대응을 맡는 운영 담당자가 참여할 수 있다.

## 3. 중요한 시나리오로 체크리스트를 적용한다

- 모든 항목을 같은 깊이로 점검하기보다 이번 변경과 관련된 위험을 선택해 검토한다.
- 각 질문에는 설명과 함께 확인할 근거를 연결한다.

| 검토 영역 | 질문 | 확인할 근거의 예 |
| :--- | :--- | :--- |
| 목표와 제약 | 성공 기준과 반드시 지킬 조건이 명확한가? | 품질 시나리오, 업무 규칙과 제약조건을 확인한다. |
| 책임과 의존성 | 변경 책임과 데이터 소유자가 분명한가? 새 의존성이 다른 기능에 영향을 주는가? | 구성도, 인터페이스와 의존 관계를 확인한다. |
| 데이터와 계약 | 동시 변경·중복·부분 성공·구버전 요청을 어떻게 처리하는가? | 트랜잭션 경계, API·이벤트 계약과 상태 전이를 확인한다. |
| 장애와 복구 | 의존 시스템의 지연·중단이 어디까지 전파되는가? 재시도와 복구는 누가 책임지는가? | 시간 초과·재시도 정책과 장애 재현 결과를 확인한다. |
| 성능과 용량 | 목표 부하에서 병목과 적체는 어디에 생기는가? 자원 한도에 도달하면 어떻게 되는가? | 부하 조건, 처리량·지연·자원 사용량을 확인한다. |
| 보안과 접근 | 신뢰 경계에서 호출자·권한을 어떻게 확인하고 민감 정보를 보호하는가? | 데이터 흐름, 권한 정책과 위협 분석을 확인한다. |
| 배포와 운영 | 버전 혼재, 데이터 이전과 되돌리기를 어떻게 처리하는가? 문제를 감지할 수 있는가? | 배포·복구 계획, 로그·지표·알림을 확인한다. |
| 변경과 비용 | 예상하는 다음 변경이 어디까지 번지는가? 운영 부담과 비용을 감당할 수 있는가? | 변경 시나리오, 대안 비교와 비용 추정을 확인한다. |

- “재시도가 있다”는 답에는 최대 횟수, 간격, 중복 처리와 총 대기 시간까지 확인할 필요가 있다.
- “이중화되어 있다”는 답에는 공통 의존성이 무엇이고 장애 시 어떻게 전환하는지 확인할 필요가 있다.
- 근거의 종류는 질문에 맞게 고른다. 구현된 시스템은 코드·테스트·운영 데이터로 문서의 설명과 실제 동작이 맞는지도 확인한다.

## 4. 발견 사항을 실행 가능한 후속 작업으로 남긴다

- 회의 메모에는 문제의 조건과 영향, 근거, 대응 또는 검증 작업을 함께 적는다.
- 아래는 외부 결제 연동을 검토한 가상의 결과이다.

| 항목 | 기록 예시 |
| :--- | :--- |
| 발견 사항 | 승인 응답이 유실된 뒤 재시도하면 중복 결제가 발생할 가능성이 있다. |
| 근거와 불확실성 | 요청마다 새 식별자를 만들고 있으며, 결제사의 중복 요청 처리 계약을 아직 확인하지 못했다. |
| 영향 | 고객에게 중복 청구되면 주문 상태와 실제 결제 상태가 어긋날 수 있다. |
| 후속 작업 | 동일 업무 요청의 식별자 유지와 결제사 계약을 확인하고, 응답 유실을 재현한다. |
| 담당과 확인 시점 | 결제 연동 담당자가 배포 전까지 검증 결과를 공유한다. |
| 재검토 기준 | 중복 청구 방지와 결과 조회·복구 절차를 확인한 뒤 배포 여부를 판단한다. |

- 확인된 사실, 가능성이 있는 위험과 미확인 가정을 구분한다.
- 합의한 구조적 결정은 ADR에, 지속적으로 추적할 위험은 위험 목록에 연결한다.
- **점검 항목의 통과 개수보다 중요한 위험에 근거와 후속 조치가 있는지가 중요하다.**

## 5. 추가 분석이 필요한 조건을 판단한다

- 핵심 목표가 수치와 조건으로 정의되지 않았다면 요구사항부터 구체화한다.
- 성능이나 복구 가능성이 결정의 핵심인데 근거가 부족하면 실험·부하 테스트·장애 재현을 추가한다.
- 여러 팀과 업무 영역의 목표가 충돌하고 영향이 크면 이해관계자 범위를 넓혀 체계적인 평가를 진행한다.
- 보안 등 전문 판단이 필요한 사안은 해당 전문가의 검토로 연결한다.
- 검증이 필요한 조건을 남긴 경우에는 그 조건을 확인한 뒤 결정을 마무리한다.

- [arc42 — Quality Requirements](https://docs.arc42.org/section-10/): 검증 가능한 품질 요구사항의 작성 기준이다.
