# arc42: 아키텍처 문서를 체계적으로 구성하기

## 1. 구조와 함께 목표·결정·위험을 설명한다

- **arc42는 소프트웨어 아키텍처에서 무엇을 문서화할지 정리한 템플릿이다.**
- Peter Hruschka와 Gernot Starke가 만들었으며, 목적이 다른 12개 절로 구성된다.
- 구성도뿐 아니라 요구사항, 제약조건, 설계 이유와 알려진 위험을 함께 다룬다.
- 프로젝트의 규모와 독자의 필요에 맞춰 상세 수준을 조정한다.

## 2. 12개 절의 역할을 구분한다

| 절 | 담을 내용 |
| :--- | :--- |
| 1. Introduction and Goals | 주요 요구사항, 핵심 품질 목표와 이해관계자를 설명한다. |
| 2. Constraints | 설계의 선택 범위를 제한하는 기술·조직 등의 조건을 적는다. |
| 3. Context and Scope | 시스템 경계와 외부 사용자·시스템의 관계를 설명한다. |
| 4. Solution Strategy | 목표를 달성하기 위한 주요 설계 방향을 요약한다. |
| 5. Building Block View | 구성요소의 책임과 정적 관계를 계층적으로 설명한다. |
| 6. Runtime View | 중요한 시나리오에서 구성요소들이 어떻게 협력하는지 설명한다. |
| 7. Deployment View | 소프트웨어가 인프라에 배치되는 구조를 설명한다. |
| 8. Crosscutting Concepts | 여러 부분에 공통으로 적용하는 개념과 규칙을 설명한다. |
| 9. Architecture Decisions | 중요한 결정과 그 이유를 기록한다. |
| 10. Quality Requirements | 품질 요구사항을 구체적인 시나리오와 기준으로 설명한다. |
| 11. Risks and Technical Debt | 알려진 위험과 기술 부채를 기록한다. |
| 12. Glossary | 해석을 통일해야 하는 용어를 정의한다. |

## 3. 정적 구조·실행·배치를 연결한다

- 정적 구조에서는 구성요소의 책임과 인터페이스를 설명한다.
- 실행 관점에서는 그 구성요소들이 중요한 기능, 외부 연동, 기동·종료와 예외 상황을 어떻게 처리하는지 보여 준다.
- 실행 시나리오는 구조적으로 중요한 사례를 선택한다. 모든 기능의 호출 순서를 나열하면 변경 시 유지할 범위가 커진다.
- 배치 관점에서는 실행 인스턴스와 인프라의 관계를 설명한다.

### 주문 알림을 문서화하는 예시

| 문서 위치 | 가상의 시스템에서 설명할 내용 |
| :--- | :--- |
| Building Block View | 주문 처리와 알림 처리의 책임, 작업 저장소와의 관계를 설명한다. |
| Runtime View | 주문 확정, 알림 작업 기록, 워커의 작업 조회와 전송 순서를 설명한다. |
| Runtime View의 장애 시나리오 | 전송 후 완료 기록이 실패했을 때 재처리되는 흐름을 설명한다. |
| Deployment View | API와 워커의 배치 위치, DB 접근 경로와 실행 인스턴스를 표시한다. |
| Crosscutting Concepts | 여러 작업에 공통인 재시도·관측·오류 분류 규칙을 설명한다. |

- 시나리오에 등장하는 요소는 구조에서 찾을 수 있어야 하며, 배치 설명에서도 같은 이름을 사용한다.
- 공통 규칙은 한곳에 두고 각 구성요소에서는 적용 위치와 예외를 연결한다.

## 4. 목표·전략·결정·위험을 추적할 수 있게 한다

- 핵심 품질 목표는 문서 앞에서 드러내고, 상세한 조건과 측정 기준은 품질 요구사항에서 관리한다.
- 주요 설계 방향은 Solution Strategy에 요약하고, 구체적인 대안 비교와 결정 이력은 [ADR](03_recording_architectural_decisions_with_adrs.md)에 연결한다.
- Architecture Decisions 절에 별도 ADR의 본문을 반복해서 복사할 필요는 없다. 결정 목록과 링크로 찾을 수 있게 한다.
- 확인된 문제와 아직 검증하지 못한 가정을 구분하고, 영향을 받는 품질 요구사항을 연결한다.

| 연결 관계 | 주문 알림 예시 |
| :--- | :--- |
| 목표 → 전략 | 알림 서비스 지연이 주문 응답을 지연시키지 않도록 별도 처리를 검토한다. |
| 전략 → 결정 | 작업의 영속화 방식과 워커 처리 방식을 ADR에 기록한다. |
| 결정 → 위험 | 중복 전송 가능성과 작업 적체가 업무에 미치는 영향을 기록한다. |
| 위험 → 검증 | 응답 유실과 워커 중단을 재현하고 작업 복구와 지연을 확인한다. |

## 5. 작성 범위와 갱신 기준을 정한다

- 먼저 독자가 판단해야 하는 목표·경계·주요 구조·위험을 작성하고, 설명이 더 필요한 부분을 상세화한다.
- 특정 절을 생략한다면 검토 후 해당 없음으로 판단했는지, 아직 조사하지 못했는지 구분한다.
- C4의 구조도와 배포도는 arc42의 관련 설명에 활용할 수 있다. 문서의 목차와 다이어그램의 상세 수준을 기계적으로 대응시키지는 않는다.
- 인터페이스 명세나 운영 절차가 별도로 관리되면 해당 문서를 링크한다.
- **구조나 결정이 바뀌는 변경에서 관련 시나리오·품질 요구사항·위험도 함께 검토한다.**
