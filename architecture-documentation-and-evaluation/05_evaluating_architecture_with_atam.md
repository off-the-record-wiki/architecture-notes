# ATAM: 품질 목표를 기준으로 아키텍처 위험을 평가하기

## 1. 결정이 품질 목표에 미치는 영향을 분석한다

- **ATAM(Architecture Tradeoff Analysis Method)은 SEI가 개발한 시나리오 기반 아키텍처 평가 방법이다.**
- 품질 목표에 비추어 설계 결정의 영향과 트레이드오프를 분석하고, 업무 목표를 위협하는 위험을 찾는다.
- 평가 팀, 아키텍트와 이해관계자가 함께 목표·구조·가정을 확인한다.
- 분석 결과의 유효 범위는 검토한 시나리오와 가정에 달려 있다. 실제 구현의 성능이나 장애 대응은 필요한 테스트와 측정으로 확인한다.

## 2. 업무 목표를 분석 가능한 시나리오로 구체화한다

- Utility Tree는 품질 요구를 계층적으로 정리하고, 구체적인 시나리오까지 상세화한 구조이다.
- 시나리오는 업무상 중요도와 달성의 어려움·위험을 기준으로 우선순위를 정한다.
- 중요하고 달성 위험이 큰 시나리오가 주요 분석 대상이 된다.
- 시나리오의 작성 요소는 [품질 목표와 시나리오](../architecture-quality/03_defining_measurable_quality_goals_and_scenarios.md)에서 확인할 수 있다.

### Utility Tree의 일부를 작성하는 예시

- 아래 수치와 우선순위는 설명을 위한 가정이다.

| 품질 영역 | 구체적인 관심사 | 시나리오 | 중요도 / 달성 어려움 |
| :--- | :--- | :--- | :--- |
| 성능 | 피크 부하에서 주문을 접수한다. | 정의된 요청·데이터 구성에서 초당 500건의 주문 접수 요청이 10분간 발생하면, 오류율 0.1% 이하와 응답 시간 p95 1초 이하를 유지한다. | 높음 / 높음 |
| 가용성 | API 인스턴스 장애에 대응한다. | API 인스턴스 하나가 종료되어도 30초 안에 신규 요청을 정상 처리하고, 성공 응답한 주문을 유실하지 않는다. | 높음 / 높음 |
| 변경 용이성 | 외부 결제 연동을 추가한다. | 새 결제사 연동을 주문 상태 전이 코드의 변경 없이 개발·테스트하여 5인일 이내에 완료한다. | 중간 / 중간 |

- 표를 채웠다는 사실만으로 목표를 만족한 것은 아니다. 각 시나리오를 처리할 구조와 근거를 이어서 분석한다.

## 3. 아홉 단계로 목표·구조·분석 결과를 공유한다

| 단계 | 수행할 일 |
| :--- | :--- |
| 1. ATAM 소개 | 평가 방법과 기대 결과를 공유한다. |
| 2. 업무 동인 설명 | 업무 목표와 주요 아키텍처 요구를 설명한다. |
| 3. 아키텍처 설명 | 목표에 대응하는 구조와 결정을 설명한다. |
| 4. 설계 접근법 식별 | 적용한 패턴과 주요 설계 수단을 식별한다. |
| 5. Utility Tree 작성 | 품질 요구를 시나리오로 구체화하고 우선순위를 정한다. |
| 6. 설계 접근법 분석 | 우선순위가 높은 시나리오로 위험과 주요 영향을 분석한다. |
| 7. 시나리오 발굴·우선순위 결정 | 더 넓은 이해관계자 그룹에서 시나리오를 수집하고 투표로 우선순위를 정한다. |
| 8. 설계 접근법 재분석 | 추가로 선정한 시나리오를 분석한다. |
| 9. 결과 발표 | 발견한 위험과 분석 근거를 이해관계자에게 공유한다. |

- 5단계의 요구 구체화와 7단계의 이해관계자 시나리오 발굴은 분석의 관점을 넓히는 데 기여한다.

## 4. 위험과 민감점·트레이드오프 지점을 구분한다

| 분석 결과 | 의미 |
| :--- | :--- |
| Risk | 품질 목표 달성에 문제를 일으킬 수 있는 결정이나 미결정 사항이다. |
| Non-risk | 명시한 가정 아래에서 요구를 만족한다고 판단할 근거가 있는 결정이다. |
| Sensitivity Point | 특정 품질의 달성에 큰 영향을 주는 구조적 속성이나 매개변수이다. |
| Tradeoff Point | 둘 이상의 품질에 민감하게 영향을 주는 속성이나 매개변수이다. |
| Risk Theme | 여러 위험을 묶어 업무 목표에 미치는 공통 영향을 설명한 것이다. |

- 민감점과 트레이드오프 지점은 영향이 집중되는 곳을 나타낸다. 위험 여부는 요구 수준, 선택한 값과 가정에 비추어 판단한다.

### 주문 조회 캐시를 분석하는 예시

- 조회 응답 시간과 허용 가능한 데이터 반영 지연이 모두 중요하다고 가정한다.
- TTL을 바꿨을 때 DB 부하와 응답 시간이 크게 달라진다면 TTL은 성능에 대한 민감점 후보이다.
- 같은 TTL이 데이터 최신성 요구에도 크게 영향을 준다면 트레이드오프 지점으로 분석할 수 있다.
- 재고 변경을 늦게 반영할 가능성이 허용 범위를 넘는다면 위험으로 기록하고, 결제 단계의 원본 검증 등 대응 방식을 검토한다.
- TTL의 실제 영향은 조회 분포, 갱신 빈도와 무효화 방식에 따라 달라지므로 측정과 가정 확인이 필요하다.

## 5. 분석 결과를 후속 결정으로 연결한다

- 위험마다 관련 시나리오, 설계 결정, 근거와 남은 불확실성을 남긴다.
- 실무에서는 위험 대응을 맡을 담당자와 추가 검증 작업을 연결해 후속 조치를 추적할 수 있다.
- 가정한 부하, 장애 범위나 요구사항이 바뀌면 해당 분석 결과도 다시 확인한다.
- 여러 이해관계자의 품질 요구가 얽힌 큰 변경은 ATAM 같은 체계적인 평가를 검토할 수 있다.
- 범위가 좁은 변경을 검토할 때는 [가벼운 아키텍처 리뷰](06_conducting_lightweight_architecture_reviews.md)에서 위험을 먼저 식별하고 필요한 분석을 추가한다.

## 6. 레퍼런스

- [SEI — Architecture Tradeoff Analysis Method Collection](https://www.sei.cmu.edu/library/architecture-tradeoff-analysis-method-collection/): 아홉 단계와 이해관계자 참여, 평가 산출물과 위험 주제를 설명한다.
