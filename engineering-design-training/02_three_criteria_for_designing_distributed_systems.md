# 분산 시스템 설계: 처리·상태·시간을 나누어 보기

- 분산 시스템의 설계를 처리 주체, 데이터 위치와 실행 시점의 세 관점으로 살펴본다.
- 세 관점은 서로 배타적이지 않으며 한 시스템에서 함께 사용할 수 있다.

## 1. 단일 서버의 한계와 분산의 목적

- Scale-up은 한 서버의 CPU·메모리 등 자원을 늘리고, Scale-out은 서버 수를 늘리는 방식이다.
- 단일 서버에서 늘릴 수 있는 자원에는 상한이 있다.
- 단일 서버에 의존하는 기능은 그 서버가 중단되면 사용할 수 없다.
- 여러 서버에 작업과 데이터를 나누면 처리량·저장 용량을 확장하거나 장애에 대비할 수 있다.
- 성능 향상, 가용성 개선과 비용 절감은 분산만으로 보장되지 않는다. 공유 자원의 병목, 장애 전환 구성과 운영 비용에 따라 달라진다. [Microsoft — 확장 전략](https://learn.microsoft.com/en-us/azure/well-architected/reliability/scaling)

## 2. 처리의 분산 — 누가 처리하는가

- **작업을 여러 실행 주체에 나누어 맡긴다.**
- 여러 요청을 나눌지, 한 요청의 작업을 나눌지 구분한다.

### 동일한 기능의 서버를 늘린다 — 로드밸런싱

- 같은 기능을 제공하는 서버 인스턴스를 여러 개 두고 로드밸런서가 요청을 분배한다.
- 각 요청을 처리할 서버를 선택하는 방식이며, 한 요청을 여러 하위 작업으로 나누는 방식과 구분한다.
- 특정 인스턴스의 상태에 의존하지 않는 무상태 서버는 요청을 나누기 쉽다.
- 공유 DB나 외부 서비스가 병목이면 서버를 늘려도 처리량이 비례해 증가하지 않는다.
- 장애 서버를 분배 대상에서 제외하고 남은 서버가 부하를 감당할 수 있어야 서비스를 이어갈 수 있다.

### 요청을 나누고 결과를 모은다 — Scatter/Gather

- 한 요청에 필요한 처리를 여러 서버에 보내고 응답을 하나의 결과로 조합한다.
- 서로 독립적으로 실행할 수 있는 작업을 병렬로 처리할 때 사용한다.
- 모든 결과를 기다린다면 가장 늦은 응답과 결과 조합 시간이 전체 지연에 영향을 준다.
- 일부 결과만으로 응답할 수 있는지는 업무 요구에 따라 정하고, 대기 기한과 부분 실패 처리 규칙을 둔다. [Enterprise Integration Patterns — Scatter-Gather](https://www.enterpriseintegrationpatterns.com/patterns/messaging/BroadcastAggregate.html)

### 분배와 집계를 여러 단계로 나눈다 — 병렬 트리

- 요청 분배와 결과 집계를 트리 형태의 여러 계층에서 수행한다.
- 중간 서버는 하위 서버의 결과를 조합·필터링해 상위 서버로 전달한다.
- 루트의 역할은 구조에 따라 다르며 메타데이터 관리로 한정되지 않는다. [Google Research — Dremel](https://research.google/pubs/dremel-interactive-analysis-of-web-scale-datasets/)

## 3. 상태의 분산 — 데이터를 어디에 두는가

- **시스템의 데이터를 여러 위치에 저장하고 관리한다.**
- 같은 데이터를 복사하는 복제와 서로 다른 데이터를 나누는 샤딩을 구분한다.

### 같은 데이터를 여러 곳에 둔다 — 복제

- 동일한 데이터의 복사본을 여러 노드에 유지한다.
- 읽기를 지원하는 복제본에 조회를 분배하면 읽기 처리량을 늘릴 수 있다.
- 비동기 복제에서는 변경 반영이 늦어져 복제본이 이전 값을 반환할 수 있다. [PostgreSQL — 복제](https://www.postgresql.org/docs/17/warm-standby.html)
- Primary 장애 시 복제본을 승격하는 구성에서는 장애 감지와 전환 절차가 필요하다. 자동 전환 여부는 제품과 구성에 따라 달라진다. [PostgreSQL — Failover](https://www.postgresql.org/docs/17/warm-standby-failover.html)

### 서로 다른 데이터를 나눈다 — 샤딩

- 데이터를 키에 따라 수평으로 나누어 여러 저장 노드에 배치한다.
- 저장 용량을 확장하고, 쓰기 요청이 샤드에 분산되면 쓰기 부하도 나눌 수 있다.
- 특정 샤드에 요청이 집중되는 핫스폿을 줄이려면 데이터량과 접근 패턴을 고려해 키를 정한다.
- 샤드 간 조인·집계에는 추가 처리가 필요하며, 데이터를 재배치할 때 이동 비용이 든다.
- 파티셔닝은 데이터를 나누는 더 넓은 개념이며, 모든 파티셔닝이 여러 노드로의 분산을 뜻하지는 않는다. [Microsoft — Sharding](https://learn.microsoft.com/en-us/azure/architecture/patterns/sharding)

## 4. 시간의 분산 — 언제 처리하는가

- **요청을 받는 시점과 실제 작업을 처리하는 시점을 분리한다.**

### 메시지를 저장하고 따로 처리한다 — 비동기 메시지 큐

- 생산자는 작업을 메시지로 큐에 넣고, 소비자는 메시지를 가져와 처리한다.
- 생산자는 소비자의 작업 완료를 기다리지 않을 수 있지만, 큐의 접수 성공과 작업 완료는 구분해야 한다.
- 소비자의 처리 속도를 제한하면 일시적인 요청 집중을 큐로 완충할 수 있다.
- 큐가 처리 용량을 늘리지는 않는다. 유입이 처리량을 계속 넘으면 적체와 대기 시간이 늘어난다.
- 큐의 저장 용량·보관 기간과 작업의 완료 기한 안에서 처리할 수 있어야 한다. [Microsoft — Queue-Based Load Leveling](https://learn.microsoft.com/en-us/azure/architecture/patterns/queue-based-load-leveling)
- 비동기 처리는 반드시 피크 이후에 실행한다는 뜻은 아니다. 실제 실행 시점은 소비자의 동작과 처리 여력에 따라 달라진다.
