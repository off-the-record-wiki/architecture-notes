# 코드 레벨 공통처리: 분리 대상과 배치 위치 판단하기

## 1. 공통처리의 목적은 동작을 일관되게 만드는 것이다

- **공통처리는 여러 기능에 반복되는 정책과 실행 절차를 정하고, 필요한 위치에서 같은 방식으로 적용하는 설계이다.**
- 로깅, 오류 응답, 입력 검증과 접근 제어를 각 기능에 흩어 놓으면 적용 범위와 동작이 달라질 수 있다.
- 정책 변경 시 수정할 곳이 많아지므로 공통으로 유지할 규칙과 서비스별로 달라질 규칙을 구분한다.
- 공통처리를 분리해도 각 기능의 업무 규칙까지 동일하게 만들 필요는 없다.

## 2. 무엇을 공통으로 다룰지 먼저 정한다

| 관심사 | 공통으로 정할 내용 | 기능별로 남길 내용 |
| :--- | :--- | :--- |
| 로깅 | 요청 식별자, 기록 형식과 민감정보 처리 | 업무상 필요한 추가 기록 |
| 오류 처리 | 예상하지 못한 오류의 응답 형식과 기록 기준 | 업무 오류의 종류와 사용자에게 안내할 내용 |
| 인증·인가 | 신원 확인 방법과 공통 접근 정책 | 자원별 권한과 업무 조건 |
| 입력 검증 | 요청 형식, 필수 항목과 기본 범위 확인 | 업무 맥락에 따른 유효성 판단 |
| 요청·응답 형식 | 공통 오류 형식과 메타데이터 | 각 API가 반환할 업무 데이터 |
| 보안 | 공통 보안 헤더, 접근 제한과 민감정보 보호 정책 | 기능별 위험에 따른 추가 통제 |
| 캐싱 | 공통 설정과 관측 방식 | 캐시 키, 만료와 데이터 최신성의 허용 범위 |
| 트랜잭션 | 경계 선언과 실행 방식 | 한 트랜잭션에 묶을 업무 작업의 범위 |

- 공통 정책을 한 곳에 정의해도 모든 요청에 동일한 규칙을 적용한다는 뜻은 아니다. 공개 API와 인증이 필요한 API 등 적용 대상을 구분한다.
- 특히 인가, 업무 검증과 트랜잭션 경계는 기능의 의미에 따라 달라진다.

## 3. 어느 실행 지점에서 가로챌지 정한다

- 처리할 대상이 HTTP 요청인지, 특정 컨트롤러인지, 업무 메서드인지에 따라 실행 지점을 고른다.

| 방식 | 적용 위치 | 적합한 처리와 확인할 범위 |
| :--- | :--- | :--- |
| Filter | Servlet 요청·응답 경로 | 컨트롤러 선택 전후의 HTTP 수준 처리. 적용할 URL·요청 경로와 필터 순서를 확인한다. |
| Interceptor | Spring MVC의 핸들러 실행 전후 | 핸들러 정보에 따른 처리. MVC가 처리하지 않는 경로에는 적용되지 않는지 확인한다. |
| AOP | 프록시를 거치는 메서드 호출 전후 | 메서드 단위의 로깅·트랜잭션 등. 프록시를 거치지 않는 내부 호출에는 적용되지 않을 수 있다. |

- 이 표는 Java/Spring 기반 시스템의 선택지다. 프레임워크가 달라도 **어떤 실행 경로에서 어느 범위에 적용되는가**라는 판단은 같다.
- 보안 검사를 MVC Interceptor에만 의존하지 않는다. Spring은 보안 적용에 필터 체인과 연동된 방식을 권장한다. [Spring MVC — Interceptors](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-config/interceptors.html)
- Spring AOP는 프록시 기반이므로 같은 객체 안에서 직접 호출한 메서드는 advice를 거치지 않는다. [Spring Framework — AOP Proxies](https://docs.spring.io/spring-framework/reference/core/aop/proxying.html)
- 실행 순서와 예외 경로는 실제 프레임워크 구성에서 확인한다. Filter, Interceptor와 AOP를 항상 같은 순서로 모두 거친다고 가정하지 않는다.

## 4. 공통 규칙을 어디에 배치할지 선택한다

| 위치 | 적합한 범위 | 감수할 비용 |
| :--- | :--- | :--- |
| 서비스 안의 공통 모듈·라이브러리 | 메서드나 프레임워크 맥락을 알아야 하는 처리 | 라이브러리를 바꾸면 사용하는 서비스의 버전 갱신과 배포가 필요할 수 있다. |
| API Gateway | 외부 요청의 진입점에서 일괄 적용할 정책 | 게이트웨이를 거치지 않는 호출에는 적용되지 않는다. 서비스 내부의 세부 권한 판단은 별도로 남는다. |
| 별도 공통 서비스·API | 여러 서비스가 같은 정책이나 데이터를 독립적으로 조회·변경해야 하는 처리 | 네트워크 호출, 가용성과 배포 의존성이 생긴다. |

- 한 관심사를 한 위치에만 둘 필요는 없다. 게이트웨이에서 신원을 확인하고 서비스에서 자원별 권한을 판단할 수 있다.
- 중앙 배치가 정책 변경의 영향을 줄이는지는 배포 방식과 호출 범위에 달려 있다. [Microsoft — Gateway Offloading](https://learn.microsoft.com/en-us/azure/architecture/patterns/gateway-offloading)

## 5. 변경 빈도·적용 범위·업무 맥락으로 결정한다

| 질문 | 판단에 미치는 영향 |
| :--- | :--- |
| 정책은 얼마나 자주 바뀌며 배포를 함께 할 수 있는가? | 서비스별 배포와 중앙 정책 변경의 비용을 비교한다. |
| 어떤 요청·서비스·실행 경로에 적용해야 하는가? | 게이트웨이, 서비스 내부 또는 두 위치의 책임을 정한다. |
| 메서드 인자·반환값이나 업무 상태를 알아야 하는가? | 요청 진입점에서 처리할 수 있는지, 서비스 내부 처리가 필요한지 판단한다. |
| 공통 처리의 실패가 어느 기능에 영향을 주는가? | 실패 시 차단·우회 정책과 장애 범위를 정한다. |

- 최종 결정에는 공통 정책의 소유자, 적용 대상, 예외 규칙과 검증 방법을 남긴다.
- 적용 범위를 잘못 정하면 누락 또는 중복 실행이 생길 수 있으므로 정상 요청과 오류·우회 경로를 함께 확인한다.
