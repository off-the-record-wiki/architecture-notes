# 모니터링 접근 비교: Four Golden Signals·USE·RED를 실무에 적용하기

## 1. 서비스 상태와 자원 상태를 서로 다른 관점에서 확인한다

- **Four Golden Signals, USE와 RED는 같은 시스템을 서로 다른 대상과 질문으로 살펴보는 접근이다.**
- Four Golden Signals는 서비스의 지연·수요·실패·처리 한계를 함께 보고, RED는 각 서비스의 요청 처리 상태를 공통된 기준으로 본다.
- USE는 자원별 사용률·포화도·오류를 점검해 병목과 자원 오류를 조사한다.
- 어느 하나를 고르는 문제보다 서비스 상태를 어떻게 감지하고 관련 자원을 어떻게 조사할지 정하는 것이 중요하다.

| 접근 | 핵심 지표 | 주로 답할 질문 |
| :--- | :--- | :--- |
| Four Golden Signals · FGS | Latency, Traffic, Errors, Saturation이다. | 서비스의 품질과 처리 여유가 어떤 상태인가? |
| USE | Utilization, Saturation, Errors이다. | 어떤 자원에 부하·대기·오류가 발생하는가? |
| RED | Rate, Errors, Duration이다. | 어느 서비스에서 요청량·실패·응답 시간이 달라졌는가? |

- 지표의 정의와 해석은 [Four Golden Signals 문서](02_monitoring_services_with_the_four_golden_signals.md)와 [USE·RED 문서](03_monitoring_infrastructure_and_services_with_use_and_red.md)를 참고한다.
- 이 문서의 메트릭명, 쿼리와 알림 단계는 적용을 설명하기 위한 예시이다. 실제 계측 환경과 서비스의 목표에 맞춰 조정한다.

## 2. 적용할 상황은 시스템 구조와 조사 목적에 따라 정한다

| 상황 | 활용할 접근 | 적용하는 이유와 함께 확인할 내용 |
| :--- | :--- | :--- |
| 모놀리식 백엔드의 전체 상태를 파악한다. | FGS로 서비스 상태를 요약하고 USE로 관련 자원을 조사한다. | 요청 품질과 처리 여유를 함께 볼 수 있다. 기능별 부하 차이가 크면 주요 작업도 구분한다. |
| 모니터링을 처음 구성한다. | FGS나 RED로 요청의 지연·실패·수요부터 확인한다. | 사용자 영향을 먼저 파악하고 서비스의 처리 한계와 필요한 자원 지표를 추가한다. |
| RDS·ElastiCache 등 매니지드 서비스를 사용한다. | 서비스 지표와 제공자가 노출하는 자원 지표를 함께 본다. | 직접 관리하지 않는 인프라도 연결 한도, 메모리, 저장 공간과 처리 용량의 제약이 있다. |
| 여러 마이크로서비스와 HTTP·gRPC API를 운영한다. | 각 서비스에 RED를 공통으로 적용한다. | 내부 구현이 달라도 요청량·실패·지연으로 상태를 비교할 수 있다. 서비스별 성공 조건과 목표값은 구분한다. |
| Istio·Envoy 등으로 서비스 간 트래픽을 관찰한다. | 프록시가 제공하는 RED 지표를 활용한다. | 서비스 간 호출을 일관되게 관찰할 수 있다. 프록시 지표만으로 업무 결과의 정확성까지 판단하지는 않는다. |
| 서비스가 느린데 원인을 모른다. | USE로 CPU·메모리·디스크·네트워크 등을 점검한다. | 서비스 지연과 같은 시간대의 자원 사용·대기·오류를 비교한다. |
| 용량 계획이나 인프라의 일상 점검을 수행한다. | USE 지표의 현재 상태와 추세를 확인한다. | 사용률뿐 아니라 대기와 오류, 확장에 걸리는 시간을 함께 보고 여유 용량을 판단한다. |

- FGS는 모놀리식에만, RED는 마이크로서비스에만 적용하는 방식이 아니다. 구조별 예시는 시작할 구성을 고르는 데 활용한다.
- 공통된 RED 구성이 있으면 직접 개발하지 않은 서비스도 같은 질문으로 조사할 수 있어 장애 대응 부담을 줄일 수 있다.

## 3. FGS·RED와 USE를 조합하되 포화도의 측정 대상을 확인한다

- **서비스 요청의 이상은 FGS·RED로 파악하고, 자원 병목과 오류는 USE로 조사하는 구성을 활용할 수 있다.**
- [Grafana의 RED Method 설명](https://grafana.com/blog/the-red-method-how-to-instrument-your-services/)에서도 RED와 USE를 함께 사용해 서비스와 자원 상태를 보완하는 접근을 제안한다.

| 구성 | 서비스에서 확인할 내용 | 자원에서 확인할 내용 |
| :--- | :--- | :--- |
| FGS + USE | 요청의 지연·수요·실패와 서비스를 제한하는 자원의 여유·대기이다. | 개별 자원의 사용률·포화도·오류이다. |
| RED + USE | 서비스별 요청량·실패·응답 시간이다. | 개별 자원의 사용률·포화도·오류이다. 서비스의 처리 한계를 놓치지 않도록 풀·큐 등도 확인한다. |

- RED의 Rate·Errors·Duration은 FGS의 Traffic·Errors·Latency와 대응하며, RED 자체에는 Saturation이 포함되지 않는다.
- FGS의 Saturation은 스레드 풀 고갈, 연결 풀 대기와 요청 큐 적체 등 서비스를 제한하는 자원을 살펴본다. CPU·디스크 등 인프라 자원도 대상이 될 수 있다.
- USE도 스레드 풀이나 연결 풀 같은 소프트웨어 자원에 적용할 수 있다. 따라서 FGS의 포화도는 서비스 전용이고 USE의 포화도는 인프라 전용이라고 고정해서 나누지 않는다.
- RED + USE로 FGS의 주요 관심사를 다룰 수 있지만 CPU·메모리만 수집하면 서비스 내부의 풀 고갈과 큐 적체를 놓칠 수 있다. 조합 이름보다 실제 측정 범위를 확인한다.
- 사용률이 높아도 대기와 사용자 지연이 적을 수 있고, 긴 구간의 평균 사용률이 낮아도 순간적인 포화가 발생할 수 있다. 사용률만으로 안전이나 장애를 판정하지 않는다.

## 4. 서비스 지표는 계측 조건에 맞춰 PromQL로 집계한다

- 다음 예시는 `job="api"`에 한 서비스의 인스턴스가 속하고, 요청 Counter인 `http_requests_total`에 HTTP 응답 코드 `code`가 있다고 가정한다.
- 응답 시간은 초 단위 Classic Histogram인 `http_request_duration_seconds`로 수집한다고 가정한다. 실제 메트릭명과 레이블은 프레임워크·계측 라이브러리의 설정을 확인한다.

| 지표 | 메트릭 예시 | 확인할 내용 |
| :--- | :--- | :--- |
| Traffic · Rate | `http_requests_total` | 누적 요청 수를 구간별 초당 요청 수로 변환한다. |
| Errors | `http_requests_total{code=~"5.."}` | 예시에서는 HTTP `5xx`를 실패로 집계한다. 전체 대상 요청 대비 비율도 확인한다. |
| Latency · Duration | `http_request_duration_seconds_bucket` | 응답 시간 분포에서 p95·p99 등을 추정한다. |
| Saturation | 사용 중인 스레드 수, 최대 스레드 수와 큐 길이 등이다. | 서비스의 처리 한계와 대기를 확인한다. RED의 세 지표에는 포함되지 않는다. |

### 요청률은 Counter에 rate를 적용한 뒤 합산한다

```promql
sum(rate(http_requests_total{job="api"}[5m]))
```

- 최근 5분 구간의 초당 평균 요청 수이며 단위는 RPS이다.
- [Prometheus의 `rate()` 정의](https://prometheus.io/docs/prometheus/latest/querying/functions/#rate)에 따라 Counter 재설정은 개별 시계열에서 처리하고 그 결과를 합산한다.
- 전체 요청률에서 이상을 찾으면 API·작업별 레이블로 범위를 좁힌다. 집계 구간은 수집 주기와 감지하려는 변화에 맞춰 정한다.

### 오류율은 같은 대상의 실패 요청과 전체 요청을 비교한다

```promql
sum(rate(http_requests_total{job="api", code=~"5.."}[5m]))
/
sum(rate(http_requests_total{job="api"}[5m]))
```

- 결과는 0~1의 비율이며 퍼센트로 표시하려면 100을 곱한다.
- HTTP `429`, 타임아웃과 업무상 실패 등을 포함할지는 성공 조건에 맞춰 정한다. 요청 Counter에 기록되지 않는 실패는 관측 지점을 보완한다.
- 대상 요청이 없거나 오류 시계열이 생성되지 않은 경우의 표시·판정 규칙도 정한다. 빈 결과나 수집 누락을 오류율 0으로 간주하지 않는다.

### p99는 인스턴스별 값을 평균내지 않고 버킷을 합산해 계산한다

```promql
histogram_quantile(
  0.99,
  sum by (le) (
    rate(http_request_duration_seconds_bucket{job="api"}[5m])
  )
)
```

- 최근 5분 동안 관측한 요청의 응답 시간에서 p99를 추정하며 단위는 초이다.
- [Classic Histogram 집계](https://prometheus.io/docs/prometheus/latest/querying/functions/#histogram_quantile)에는 버킷 경계인 `le` 레이블을 유지한다. API별로 보려면 해당 레이블도 집계 기준에 포함한다.
- 버킷 구성이 같은 인스턴스를 합산하며, 버킷 경계에 따라 추정 오차가 달라진다. 성공·실패 요청의 분포와 요청 수도 함께 확인한다.

### 서비스 포화도는 풀 사용량과 대기를 함께 본다

- Tomcat 계측이 해당 메트릭을 제공한다면 `tomcat_threads_busy_threads / tomcat_threads_config_max_threads`로 스레드 풀 사용 비율을 확인할 수 있다.
- 같은 인스턴스·커넥터의 값끼리 비교하고, 큐 길이와 대기 시간도 함께 본다. 전체 평균은 특정 인스턴스의 고갈을 가릴 수 있다.
- 풀 사용 비율만으로 서비스의 전체 처리 여유가 결정되지는 않는다. 연결 풀, 외부 호출과 다른 제한 자원도 확인한다.

## 5. 인프라 지표는 장치별 의미와 단위를 확인한다

- 다음은 Linux의 `node_exporter`가 제공하는 디스크·네트워크 메트릭 예시이다. 실제 노출 여부는 OS, 수집기와 버전에 따라 확인한다.
- 쿼리 결과는 `instance`와 `device` 등으로 장치별로 구분한다. 실제 조사할 디스크와 NIC를 선택해 본다.

| 자원·관점 | 메트릭 예시 | 조회 예시 | 해석 |
| :--- | :--- | :--- | :--- |
| Disk · U | `node_disk_io_time_seconds_total` | `rate(node_disk_io_time_seconds_total[5m])` | 관측 구간 중 I/O가 진행된 시간의 비율을 나타내는 근사 지표이다. |
| Disk · S 조사 | `node_disk_io_time_weighted_seconds_total` | `rate(node_disk_io_time_weighted_seconds_total[5m])` | 진행 중인 I/O 수로 가중한 시간을 통해 평균 미완료 I/O 수를 추정한다. |
| Network · U 조사 | `node_network_receive_bytes_total` | `rate(node_network_receive_bytes_total[5m])` | 초당 수신 바이트 수이다. 사용률을 구하려면 사용 가능한 대역폭과 비교한다. |
| Network · U 조사 | `node_network_transmit_bytes_total` | `rate(node_network_transmit_bytes_total[5m])` | 초당 송신 바이트 수이다. 수신과 송신을 각각 확인한다. |
| Network · S 조사 | `node_network_receive_drop_total` | `rate(node_network_receive_drop_total[5m])` | 초당 수신 패킷 드롭 수이다. 버퍼 부족 등 포화와 관련된 원인을 조사할 단서이다. |
| Network · E | `node_network_receive_errs_total` | `rate(node_network_receive_errs_total[5m])` | 초당 수신 오류 수이다. 드롭과 오류의 정의를 구분해 확인한다. |

- [Linux I/O 통계의 가중 시간](https://docs.kernel.org/admin-guide/iostats.html)은 처리 중인 I/O도 포함한다. 이를 순수한 대기 시간이나 대기 큐 길이로 해석하지 않는다.
- SSD·NVMe처럼 병렬 처리가 가능한 장치는 I/O 사용 시간의 비율만으로 처리 한계 도달 여부를 알기 어렵다. 요청 지연, I/O 수와 장치 특성을 함께 확인한다.
- 네트워크 전송량은 바이트/초이고 링크 속도는 비트/초로 표시될 수 있으므로 단위를 맞춰 비교한다. 가상 환경에서는 실제 대역폭 제한도 확인한다.
- 드롭이 발생했다는 사실만으로 대역폭 포화를 확정하지 않는다. NIC·OS의 카운터 의미와 발생 원인을 조사한다.
- 디스크 오류는 장치·커널이 제공하는 오류 지표나 로그 등으로 보완한다. 이 표의 메트릭만으로 모든 자원의 U·S·E를 확인한 것은 아니다.
- 사용률이나 드롭의 공통 임계값을 그대로 적용하지 않는다. 정상 상태, 사용자 영향과 부하 테스트 결과에 맞춰 대응 기준을 정한다.

## 6. 사용자 여정·서비스·자원 지표를 연결한다

- **기술 지표가 정상이어도 사용자가 원하는 작업을 완료하지 못할 수 있으므로 핵심 사용자 여정의 SLI를 함께 측정한다.**
- 결제 API의 응답이 빨라도 주문이 최종 완료되지 않거나, 로그인 API가 성공해도 사용자가 다음 화면에 진입하지 못할 수 있다.

| 관점 | 지표 예시 | 역할 |
| :--- | :--- | :--- |
| 사용자 여정 | 결제 완료율, 검색 응답 시간, 로그인 성공률이다. | 사용자가 목적을 달성하는지와 합의한 서비스 수준을 확인한다. |
| 서비스 · FGS·RED | 서비스별 요청량·실패·지연과 처리 여유이다. | 문제가 관찰되는 서비스와 작업을 좁힌다. |
| 자원 · USE | CPU·메모리·디스크·네트워크와 풀의 사용·대기·오류이다. | 관련 자원의 병목과 오류를 조사한다. |

```text
사용자 여정 SLI의 목표 미달 감지
→ FGS·RED로 관련 서비스와 작업 확인
→ USE로 자원 병목·오류 조사
→ 로그·트레이스로 원인 후보 확인
```

- 이 흐름은 조사 순서의 예시이다. 애플리케이션 오류나 의존 서비스 지연이 원인이면 인프라 자원에서 이상을 찾지 못할 수 있다.
- SLI의 분모·분자, 성공 조건과 관측 지점은 [SLI·SLO·Error Budget 문서](01_managing_reliability_with_slis_slos_and_error_budgets.md)의 기준으로 정한다.
- 가입·결제 전환율 같은 퍼널 지표는 사용자 행동과 상품 조건에도 영향을 받는다. 기술적 실패를 측정하는 SLI와 구분해 함께 해석한다.

## 7. 시스템 특성에 맞는 지표를 점진적으로 추가한다

- FGS·USE·RED는 공통된 출발점이다. 시스템 고유의 처리 지연과 품질 문제를 설명하는 지표도 필요하다.

| 시스템 | 추가 지표 후보 | 확인할 내용 |
| :--- | :--- | :--- |
| 데이터베이스 | QPS, 슬로 쿼리 수, 연결 풀 사용률, Lock Wait Time, Cache Hit Ratio와 Replication Lag이다. | 쿼리 비용, 잠금 경합, 연결 부족과 복제 지연을 구분한다. |
| 메시지 큐 | Consumer Lag, 메시지 처리 속도, Dead Letter Queue 수와 파티션별 지연이다. | 처리가 뒤처지는지, 특정 파티션에 지연이 집중되는지와 실패 메시지가 쌓이는지 확인한다. |
| 스트리밍 | 동시 세션 수, 버퍼링 발생률, 비트레이트, 연결 성공률과 CDN 캐시 적중률이다. | 연결 품질과 재생 중단 등 사용자가 겪는 품질을 확인한다. |
| 캐시 | Hit Ratio, Eviction Rate, 메모리 사용률, 키 만료율과 연결 수이다. | 적중률 변화, 용량 압박과 원본 시스템의 부하를 함께 확인한다. |

- 처음부터 모든 후보를 수집하기보다 운영 중 생긴 질문과 장애에서 필요했던 지표를 추가한다.
- 지표를 추가할 때는 무엇을 판단하고 어떤 행동을 할지 정한다. 수집·저장 비용과 대시보드 관리 부담도 함께 고려한다.

## 8. 대시보드는 핵심 상태를 단순하게 보여 준다

- **대시보드는 사용자 영향과 주요 서비스 상태를 먼저 보여 주고, 이상이 보이면 관련 작업과 자원으로 좁혀 볼 수 있게 구성한다.**
- [Google SRE Book의 모니터링 원칙](https://sre.google/sre-book/monitoring-distributed-systems/)은 실제 장애를 감지하는 규칙을 단순하고 예측 가능하며 신뢰할 수 있게 유지하는 데 초점을 둔다.

| 구성 | 담을 내용 |
| :--- | :--- |
| 상태 요약 | 핵심 사용자 여정의 SLI·SLO와 주요 서비스의 FGS·RED를 표시한다. |
| 서비스 상세 | API·작업·인스턴스별 요청량, 실패, 지연과 풀·큐 상태를 확인한다. |
| 자원 상세 | 관련 호스트·장치의 USE 지표를 같은 시간 범위로 비교한다. |
| 원인 분석 연결 | 해당 시간과 대상의 로그·트레이스, 배포·설정 변경 이력을 확인할 수 있게 한다. |

- Metrics는 상태와 추세의 집계에, Logs는 개별 이벤트와 오류 내용 확인에 활용한다. Traces는 서비스 간 요청 경로와 구간별 지연을 조사하는 데 활용한다.
- 대시보드나 알림에 쓰이지 않는 지표와 거의 사용하지 않는 복잡한 규칙은 유지 필요성을 검토한다. 사후 분석에 필요한 상세 기록은 보존 목적과 비용에 맞춰 관리한다.

## 9. 알림은 필요한 대응과 긴급도에 맞춰 전달한다

- **사람을 호출하는 알림에는 실제로 할 수 있는 조치와 대응할 담당자가 있어야 한다.**
- [Prometheus의 알림 원칙](https://prometheus.io/docs/practices/alerting/)은 사용자에게 나타나는 증상을 중심으로 알리고 원인은 대시보드에서 조사할 수 있게 구성하도록 제안한다.
- 사용자 오류·지연, 빠른 Error Budget 소진과 임박한 자원 고갈 등을 기준으로 대응 필요성을 판단한다. 수집하는 지표마다 알림을 만들지는 않는다.
- 다음은 전달 방식의 예시이며 단계명과 채널은 조직의 대응 체계에 맞춰 정한다.

| 구분 | 판단 예시 | 전달·대응 예시 |
| :--- | :--- | :--- |
| Warning | 즉시 장애 대응보다 추세 확인과 계획된 조치가 필요하다. | 담당자에게 채팅이나 티켓으로 전달한다. |
| Critical | 사용자 영향이 크거나 조속한 조치가 필요하다. | 온콜 알림 도구로 즉시 대응자를 호출한다. |
| Escalation | 정한 시간 안에 수신 확인·대응이 없거나 추가 권한과 지원이 필요하다. | 대체 담당자나 상위 책임자에게 전달하고 필요하면 전화로 호출한다. |

- 심각한 장애는 Warning을 거치지 않고 바로 호출한다. 긴급도는 영향과 대응 가능 시간으로 정하고, 전달 대상을 높이는 조건은 별도로 정한다.
- 알림에는 영향, 관측값, 대시보드와 대응 절차를 연결한다. 반복 통지 간격과 상향 전달 기준도 함께 정한다.
- 같은 장애의 중복 알림은 묶고, 짧은 변동에는 지속 시간이나 여러 관측 구간을 활용한다. 감지 지연이 커져 필요한 대응을 늦추지 않는지도 확인한다.
- 불필요한 호출이 반복되면 중요한 알림까지 무시하는 Alert Fatigue가 생긴다. 발생 빈도와 실제 조치 결과를 검토해 조건을 고치거나 제거한다.
