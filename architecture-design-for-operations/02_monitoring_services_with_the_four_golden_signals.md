# Four Golden Signals: 서비스 상태를 네 가지 지표로 파악하기

## 1. 사용자 서비스의 상태를 네 가지 관점으로 본다

- **Four Golden Signals는 Latency, Traffic, Errors, Saturation으로 서비스의 지연, 수요, 실패와 자원 한계를 함께 살펴보는 모니터링 접근이다.**
- [Google SRE Book의 모니터링 장](https://sre.google/sre-book/monitoring-distributed-systems/)은 사용자 대상 시스템에서 측정 항목을 제한해야 한다면 이 네 가지에 집중하도록 제안한다.
- CPU와 메모리가 정상이어도 사용자는 느린 응답이나 잘못된 결과를 받을 수 있다. 내부 자원 상태와 사용자가 겪는 품질을 함께 확인한다.
- 각 신호는 관찰할 범주이며 서비스 특성에 맞춰 구체적인 측정 대상과 단위를 정한다.

| 지표 | 확인할 질문 | 측정 예시 |
| :--- | :--- | :--- |
| Latency · 지연 시간 | 요청을 처리하는 데 얼마나 걸리는가? | 성공·실패 요청별 p95·p99 응답 시간이다. |
| Traffic · 요청량 | 시스템에 얼마나 많은 수요가 들어오는가? | 초당 요청 수, 동시 세션 수와 네트워크 전송량이다. |
| Errors · 오류율 | 요청이 얼마나 실패하는가? | 시스템 오류, 잘못된 응답과 기준 시간 초과 요청의 비율이다. |
| Saturation · 포화도 | 제약이 큰 자원이 한계에 얼마나 가까운가? | 자원 사용률, 풀의 여유 용량과 큐 적체이다. |

- 이 문서의 응답 시간과 사용률 수치는 개념을 설명하기 위한 예시이며 실제 서비스의 권장 기준은 아니다.

## 2. Latency는 평균뿐 아니라 느린 요청의 분포를 확인한다

- Latency는 요청을 처리하는 데 걸리는 시간이다. 측정 시작·종료 지점에 따라 포함되는 시간이 달라진다.
- 사용자가 요청을 보내고 결과를 받기까지의 시간에는 네트워크, 서버 처리와 의존 서비스의 대기 등이 포함될 수 있다. 서버 내부의 처리 시간만으로 사용자 체감 시간을 모두 설명하지 않는다.
- **평균은 전체 경향을 보여 주지만 일부 요청의 긴 대기를 가릴 수 있으므로 p95·p99와 함께 본다.**
- 예를 들어 평균이 100ms여도 일부 요청은 수 초 동안 기다릴 수 있다. 평균이 목표 안에 있다는 사실만으로 모든 사용자의 응답이 빠르다고 판단하지 않는다.

| 측정값 | 의미 | 해석할 때의 주의점 |
| :--- | :--- | :--- |
| 평균 | 관측한 응답 시간의 합을 요청 수로 나눈 값이다. | 느린 요청이 소수이면 긴 대기가 충분히 드러나지 않을 수 있다. |
| p95 | 응답 시간 분포의 95번째 백분위수이다. | 느린 상위 5%가 얼마나 더 느린지까지 보여 주지는 않는다. |
| p99 | 응답 시간 분포의 99번째 백분위수이다. | 가장 느린 1%의 모든 요청 시간을 나타내는 값은 아니다. |
| 기준 시간 내 완료 비율 | 대상 요청 중 정한 시간 안에 완료한 요청의 비율이다. | 대상 요청, 성공 조건과 집계 기간을 함께 정의한다. |

- 예를 들어 정한 관측 구간에서 `p99 ≤ 300ms`를 목표로 삼을 수 있다. 이는 99번째 백분위수의 기준이며 모든 요청을 300ms 안에 처리한다는 보장은 아니다.
- 백분위수는 집계 기간과 요청 유형에 영향을 받는다. 요청 수가 적은 구간에서는 소수의 느린 요청으로 값이 크게 변할 수 있으므로 요청 수도 함께 확인한다.

### 성공 요청과 실패 요청의 지연을 구분한다

- 의존 서비스의 연결 실패 등으로 오류를 즉시 반환하면 성공 요청보다 실패 요청의 응답이 더 빠를 수 있다.
- 성공과 실패를 섞어 집계하면 오류가 늘어날수록 전체 응답 시간이 짧아지는 왜곡이 생길 수 있다.
- 성공 요청의 지연과 실패 요청의 지연을 나눠 보고 오류율을 함께 확인한다.
- 실패 요청도 측정 대상이다. 오래 기다린 뒤 실패하는 요청은 사용자 대기와 자원 점유를 함께 늘릴 수 있다.

## 3. Traffic은 서비스 특성에 맞는 단위로 측정한다

- Traffic은 시스템에 들어오는 수요의 규모이다. 요청량의 변화를 알아야 지연, 오류와 자원 사용의 변화도 해석할 수 있다.
- 같은 요청 수라도 작업의 비용이 다르면 부하는 달라진다. 정적·동적 요청이나 읽기·쓰기처럼 처리 특성이 다른 작업을 구분해 본다.

| 서비스 유형 | 측정 후보 | 구분해서 볼 내용 |
| :--- | :--- | :--- |
| 웹 서비스 | RPS · 초당 HTTP 요청 수 | 정적·동적 요청, API나 작업별 요청량을 구분한다. |
| 스트리밍 서비스 | 동시 세션 수, 네트워크 I/O 전송률 | 연결 수와 세션별 전송량을 함께 본다. |
| DB·캐시 | 초당 트랜잭션 수, 조회·쓰기 작업 수 | 제품과 작업 특성에 맞춰 읽기·쓰기의 양과 비용을 구분한다. |

- 과부하형 장애에서는 요청량 급증을 먼저 관찰할 수 있다. 평소 시간대별 패턴과 비교하면 수요 변화를 파악하는 데 도움이 된다.
- 요청량 감소도 확인 대상이다. 사용자 수요가 줄었을 수도 있지만 요청이 서비스에 도달하지 못하는 문제일 수도 있다.
- 시스템이 받은 요청량과 완료한 처리량을 구분한다. 처리량이 정체된 상태에서 유입이 늘면 대기 중인 작업이 증가할 수 있다.

## 4. Errors는 응답 코드와 업무 결과를 함께 판단한다

- **Errors는 대상 요청 중 정의한 실패 조건에 해당하는 요청의 비율이다. HTTP `5xx`만으로 모든 실패를 설명할 수는 없다.**
- 오류율은 `실패 요청 수 / 대상 요청 수`로 계산한다. 어떤 요청을 분모에 넣고 무엇을 실패로 볼지 먼저 정한다.

| 실패 유형 | 예시 | 확인 방법 |
| :--- | :--- | :--- |
| 명시적 실패 | HTTP `500`·`503`이나 타임아웃 등으로 요청이 실패한다. | 로드밸런서, 클라이언트와 애플리케이션의 요청 결과를 관찰한다. |
| 묵시적 실패 | HTTP `200`이지만 잘못된 내용이나 불완전한 결과를 반환한다. | 애플리케이션의 결과 검증과 엔드투엔드 테스트 등으로 확인한다. |
| 정책적 실패 | 응답 내용은 맞지만 합의한 시간 기준을 초과한다. | 요청별 소요 시간을 합의한 성공 조건과 비교한다. |

- 예를 들어 1초 안에 완료하는 것을 성공 조건으로 정했다면 1.5초가 걸린 요청은 해당 지표에서 실패로 집계한다.
- 로드밸런서의 응답 코드만으로는 정상 코드에 담긴 잘못된 결과를 찾기 어렵다. 업무의 성공 여부를 알 수 있는 지점에서도 측정한다.
- 입력 오류나 업무상 거절을 시스템 장애와 같은 실패로 볼지는 서비스의 성공 조건에 따라 정한다.
- 하나의 요청이 여러 실패 조건에 해당하면 유형별로 분류하더라도 전체 실패 요청 수에는 중복으로 더하지 않는다.
- 오류율과 함께 실패 건수와 전체 요청 수도 본다. 요청이 적을 때의 높은 오류율과 많은 사용자에게 영향을 주는 실패를 구분할 수 있다.

### Error Budget과 연결한다

- SLO의 대상 요청과 실패 조건에 맞춰 집계한 오류율로 허용 예산이 얼마나 빠르게 소진되는지 판단한다.
- 예산 계산과 Burn Rate는 [SLI·SLO·Error Budget 문서](01_managing_reliability_with_slis_slos_and_error_budgets.md)의 정의를 따른다.

## 5. Saturation은 가장 제약이 큰 자원의 여유를 확인한다

- Saturation은 서비스가 처리 한계에 얼마나 가까운지 나타낸다. CPU 사용률만 보지 않고 현재 처리 능력을 제한하는 자원에 집중한다.
- **많은 시스템은 자원 사용률이 100%에 도달하기 전에 대기와 지연이 증가한다.**
- 자원 사용률과 함께 큐 길이, 대기 시간과 자원 획득 실패를 보면 처리 한계에 가까워지는 상황을 파악하기 쉽다.

| 측정 대상 | 함께 볼 지표 | 확인할 내용 |
| :--- | :--- | :--- |
| CPU | 사용률, 실행 대기와 응답 시간 | CPU를 기다리는 작업이 늘어나는가? |
| 메모리 | 사용량, 할당 실패와 GC 시간 | 메모리 압박과 GC가 처리에 영향을 주는가? |
| 스레드·연결 풀 | 사용 중인 수, 최대 수와 획득 대기 시간 | 사용 가능한 자원이 줄고 요청이 대기하는가? |
| 작업 큐 | 큐 길이와 작업 대기 시간 | 처리하지 못한 작업이 계속 쌓이는가? |
| 디스크·네트워크 | 용량·대역폭 사용, I/O 대기와 지연 | 저장 공간이나 전송·처리 한계에 가까워지는가? |

- 목표 사용률과 대응 기준은 부하 테스트, 정상 운영 측정값과 확장에 걸리는 시간을 바탕으로 정한다. `CPU 80%` 같은 단일 수치를 모든 서비스에 일괄 적용하지 않는다.
- 전체 평균만 보면 특정 인스턴스나 자원의 과부하를 놓칠 수 있다. 부하가 집중되는 단위도 확인한다.
- p99 응답 시간이 증가하면 자원 포화 여부를 확인한다. 지연 증가는 포화를 조기에 파악하는 단서이지만 의존 서비스 지연 등 다른 원인도 가능하다.
- 디스크 잔여 용량처럼 현재 상태뿐 아니라 증가 추세로 한계 도달 시점을 예상할 수 있는 항목도 함께 본다.

## 6. 네 가지 지표의 변화를 함께 해석한다

- 과부하형 장애에서는 요청량 증가가 자원 경합과 대기를 늘리고, 응답 지연을 거쳐 타임아웃과 오류로 이어질 수 있다.
- 다음은 원인을 조사할 때 참고할 수 있는 대표적인 흐름이다.

```text
Traffic 증가 → Saturation 증가 → Latency 증가 → Errors 증가
```

| 관찰한 변화 | 이어서 확인할 내용 |
| :--- | :--- |
| 요청량이 평소보다 급증한다. | 어떤 작업이 늘었고 제한된 자원에 여유가 있는지 확인한다. |
| 풀 대기와 큐 적체가 증가한다. | 처리량이 유입량을 따라가는지와 요청 지연을 확인한다. |
| p99 응답 시간이 증가한다. | 자원 경합, 의존 서비스와 특정 작업의 지연을 확인한다. |
| 타임아웃과 오류가 증가한다. | 실패 유형과 사용자 영향을 보고 요청량·자원·지연의 변화를 비교한다. |

- 이 흐름은 모든 장애의 고정된 발생 순서가 아니다. 배포 오류로 실패가 먼저 늘거나, 의존 서비스가 느려져 요청량 증가 없이 지연과 자원 점유가 늘 수 있다.
- 지표가 함께 변했다는 사실만으로 원인을 확정하지 않는다. 같은 시간대의 변경 이력, 로그와 트레이스를 확인해 원인 후보를 좁힌다.

## 7. 대시보드에서 측정 조건과 대응을 함께 정한다

- 네 가지 지표를 같은 시간축에서 비교할 수 있게 구성하면 장애 전후의 변화를 파악하기 쉽다.
- 과부하 시의 변화를 따라가기 쉽도록 Traffic → Saturation → Latency → Errors 순서의 배치를 활용할 수 있다.

| 단계 | 정리할 내용 |
| :--- | :--- |
| 현재 측정 확인 | 중요한 서비스와 작업에 네 가지 지표가 있는지 확인한다. |
| 지연 분포 확인 | 평균과 함께 p95·p99를 표시하고 성공·실패 요청을 구분한다. |
| 실패 조건 정의 | 응답 코드뿐 아니라 업무 결과와 시간 기준을 반영한다. |
| 자원 한계 확인 | 제약이 큰 자원과 목표 사용률, 대기·고갈 시 대응 기준을 정한다. |
| 한 화면에서 비교 | 같은 대상과 시간 범위로 요청량, 자원 여유, 지연과 오류를 비교한다. |

- 사용자 서비스의 상태를 요약하는 화면과 세부 원인 분석 화면을 연결한다. 처음부터 모든 지표를 한 화면에 넣기보다 이상이 보이면 해당 작업과 자원으로 좁혀 볼 수 있게 한다.
- 지표를 수집하는 것과 사람에게 알리는 조건은 구분한다. 사용자 영향이나 임박한 자원 고갈에 대해 실제 대응이 필요한 조건을 알림으로 정한다.

## 8. 흔한 모니터링 실수를 피한다

| 실패 패턴 | 생기는 문제 | 바꿀 행동 |
| :--- | :--- | :--- |
| CPU·메모리만 본다. | 내부 자원이 정상이어도 사용자 요청의 지연과 실패를 놓친다. | 요청량, 지연과 오류를 함께 확인한다. |
