# 무중단 배포: 서비스와 DB를 안전하게 변경하기

## 1. 무중단 배포는 배포로 인한 사용자 중단을 없애거나 최소화한다

- **무중단 배포는 서비스를 계속 제공하면서 새 버전으로 교체하는 방식이다. 목표는 배포 때문에 사용자가 겪는 요청 실패와 이용 중단을 없애거나 최소화하는 것이다.**
- 배포 도구가 성공을 알리고 서버 프로세스가 정상이어도 사용자의 주문이나 결제가 실패할 수 있다. 배포 완료와 서비스의 정상 동작은 구분해 판단한다.
- 서버를 교체하는 절차뿐 아니라 준비 상태, 처리 중인 요청, 버전 간 호환성과 데이터 변경을 함께 다룬다.

| 배포 중 생길 수 있는 문제 | 원인 | 필요한 대응 |
| :--- | :--- | :--- |
| 새 서버로 보낸 요청이 실패한다. | DB 연결과 초기화가 끝나기 전에 요청을 받는다. | 요청을 처리할 준비가 된 뒤 트래픽에 포함한다. |
| 처리 중이던 결제가 끊긴다. | 구 서버가 요청을 마치기 전에 종료된다. | 새 요청을 차단하고 처리 중인 작업을 마무리한다. |
| 구 버전의 주문 저장이 실패한다. | 아직 구 버전이 사용하는 DB 컬럼을 삭제한다. | 두 버전이 함께 사용할 수 있는 스키마를 유지한다. |

- 무중단 배포만으로 새 버전의 결함이나 잘못된 데이터 변경을 막을 수는 없다. 이상을 감지할 지표와 복구 방법도 함께 준비한다.

## 2. 구 버전과 신 버전이 공존하는 시간을 고려한다

- **배포 중에는 구 버전과 신 버전이 함께 동작할 수 있다. 이 시간 동안 트래픽·상태·계약·데이터가 두 버전과 호환되어야 한다.**
- 애플리케이션 서버를 교체해도 DB·캐시·큐에 저장된 데이터와 메시지는 남는다. 서버 교체가 끝난 시점과 구 형식의 사용이 끝난 시점은 다를 수 있다.

```text
구 버전만 요청 처리
→ 구 버전과 신 버전이 함께 요청 처리
→ 신 버전만 요청 처리
→ 복구 가능 기간과 남은 사용처를 확인한 뒤 구 구조 정리
```

| 관점 | 확인할 질문 |
| :--- | :--- |
| 트래픽 전환 | 신 서버에 언제 요청을 보내고 구 서버에서 언제 새 요청을 차단할 것인가? |
| 상태 | 세션·캐시·처리 중인 작업을 서버 교체 뒤에도 유지하거나 복구할 수 있는가? |
| 계약 | 구 버전과 신 버전이 서로의 API·이벤트·메시지를 이해할 수 있는가? |
| 데이터 | 두 버전이 같은 DB 스키마와 데이터를 안전하게 읽고 쓸 수 있는가? |

## 3. 배포 전략은 자원 비용·전환 방식·위험 범위로 비교한다

| 기준 | 롤링 · Rolling | 블루-그린 · Blue-Green | 카나리 · Canary |
| :--- | :--- | :--- | :--- |
| 배포 방식 | 서버를 일부씩 차례로 교체한다. | 별도 환경에 새 버전을 준비한 뒤 트래픽을 전환한다. | 일부 트래픽을 새 버전에 보내 검증하고 비율을 늘린다. |
| 추가 자원 | 교체 중 유지할 처리 용량과 배치 크기에 따라 달라진다. | 기존 환경과 새 환경을 함께 유지할 자원이 필요하다. | 초기에는 일부 서버로 시작할 수 있고 확대에 따라 자원이 늘어난다. |
| 되돌리는 방식 | 교체한 서버에 이전 버전을 다시 배포한다. | 유지 중인 기존 환경으로 트래픽을 돌린다. | 새 버전으로 보내는 트래픽을 차단한다. |
| 복구 속도의 특성 | 재배포와 준비 상태 확인에 시간이 걸린다. | 기존 환경이 정상이고 호환성이 유지되면 빠르게 전환할 수 있다. | 기존 버전에 처리 여유가 있으면 빠르게 제외할 수 있다. |
| 요청에 미치는 영향 | 교체된 서버가 받는 요청부터 문제가 나타날 수 있다. | 전체 전환 뒤에는 전체 요청이 영향을 받을 수 있다. | 새 버전으로 보낸 요청에서 먼저 문제를 확인할 수 있다. |
| 두 버전의 공존 | 교체하는 동안 서버가 섞여 있다. | 전환 중인 요청과 공유 DB 등의 상태에서 공존할 수 있다. | 검증을 위해 두 버전을 의도적으로 함께 운영한다. |

- **트래픽을 나누는 방식과 데이터 변경의 영향 범위는 다르다. 공유 DB나 메시지를 잘못 변경하면 카나리 비율이 작아도 기존 버전까지 영향을 받을 수 있다.**
- 블루-그린에서 기존 환경을 유지하더라도 공유 DB의 변경까지 원래대로 돌아가는 것은 아니다.
- 전략은 조합할 수 있다. 예를 들어 카나리로 일부 요청을 먼저 확인한 뒤 롤링으로 나머지 서버를 교체할 수 있다.
- 자원 비용과 복구 속도는 고정된 순위가 아니다. 환경 규모, 남겨 둔 처리 용량과 데이터 호환성에 따라 달라진다.

## 4. 준비 상태 확인·연결 비우기·정상 종료를 연결한다

- 프로세스가 실행 중이라는 사실과 요청을 처리할 준비가 됐다는 사실은 다르다. DB 연결과 필요한 초기화가 끝난 뒤 트래픽에 포함한다.

```text
서버 시작: 요청을 받지 않음
→ 준비 상태 확인: DB 연결·초기화 완료
→ 트래픽에 포함: 요청 처리
→ 교체 시 트래픽에서 제외: 새 요청 차단
→ 처리 중인 작업을 마친 뒤 종료
```

| 절차 | 역할 | 확인할 내용 |
| :--- | :--- | :--- |
| Readiness Check · 준비 상태 확인 | 요청을 처리할 준비가 된 서버에만 트래픽을 보낸다. | 프로세스 실행 여부와 실제 요청 처리 준비를 구분한다. |
| Connection Draining · 연결 비우기 | 서버를 트래픽에서 제외하고 이미 받은 요청을 마무리한다. | 새 요청의 유입 차단과 기존 요청의 완료를 함께 확인한다. |
| Graceful Shutdown · 정상 종료 | 종료 신호를 받은 뒤 새 작업을 받지 않고 처리 중인 요청·메시지를 마친다. | 종료 대기 시간의 한도와 시간 안에 끝나지 않은 작업의 처리 방법을 정한다. |

- 배포 플랫폼의 트래픽 전환·종료 절차와 애플리케이션의 종료 동작을 함께 맞춘다. 트래픽 제외가 반영되기 전에 프로세스가 종료되지 않는지 확인한다.
- 장시간 연결이나 오래 걸리는 작업은 종료 대기 시간 안에 끝나지 않을 수 있다. 재연결·재처리 방법까지 고려한다.

## 5. 서버 교체 뒤에도 필요한 상태를 유지하거나 복구한다

- **서버는 교체될 수 있다고 가정하고, 유지해야 할 상태는 서버 밖에 저장하거나 다시 처리할 수 있게 구성한다.**

| 상태 | 서버 교체·버전 공존 시의 문제 | 설계 방향 |
| :--- | :--- | :--- |
| 세션 | 서버 메모리에만 저장하면 교체 시 세션이 사라져 로그인이 풀릴 수 있다. | 외부 세션 저장소를 사용하거나 요청에 필요한 정보를 담은 토큰을 사용한다. |
| 캐시 | 신 버전이 저장한 형식을 구 버전이 해석하지 못할 수 있다. | 캐시 키에 버전을 구분하거나 두 버전이 읽을 수 있는 형식을 유지한다. |
| 처리 중인 메시지 | 처리 도중 종료되면 작업이 미완료 상태로 남거나 재전달될 수 있다. | 처리를 마친 뒤 완료를 알리고 재전달돼도 업무 결과가 중복되지 않도록 멱등하게 처리한다. |

- 상태를 외부에 저장해도 형식이 호환되지 않으면 버전 공존에 실패한다. 저장 위치와 함께 읽기·쓰기 형식도 확인한다.
- 메시지 처리 결과를 저장한 뒤 완료를 알리기 전에 종료될 수도 있다. 정상 종료 절차와 중복 처리 방지는 함께 필요하다.

## 6. 새 형식을 받는 쪽을 먼저 바꾸고 보내는 쪽을 나중에 바꾼다

- 공존하는 동안 구 버전이 신 버전의 API를 호출하거나 신 버전이 구 버전의 API를 호출할 수 있다. 큐에도 여러 버전이 만든 메시지가 섞일 수 있다.
- **새 데이터 형식을 읽을 수 있는 쪽을 먼저 배포한 뒤, 새 형식을 쓰거나 보내는 쪽을 배포한다.**

| 대상 | 변경 원칙 | 확인할 내용 |
| :--- | :--- | :--- |
| API 필드 추가 | 새 필드는 선택 항목으로 추가하고 받는 쪽이 모르는 필드를 허용하도록 한다. | 필수 필드 추가나 엄격한 역직렬화가 기존 호출을 실패시키지 않는지 확인한다. |
| API 필드 삭제·이름 변경 | 기존 필드를 사용하는 호출자가 전환한 뒤 정리한다. | 필드 이름뿐 아니라 값의 의미와 기본 동작도 호환되는지 확인한다. |
| 이벤트·메시지 | 형식 버전을 구분하고 소비자가 새 형식을 읽을 수 있게 먼저 배포한다. | 생산자를 전환한 뒤에도 큐에 남은 구 형식의 메시지를 처리할 수 있어야 한다. |

- API 요청 필드를 추가할 때 받는 쪽은 서버이고, 응답 필드를 추가할 때 받는 쪽은 클라이언트이다. 호출 방향마다 배포 순서를 확인한다.
- 구 형식의 지원을 제거할 때는 실행 중인 버전뿐 아니라 남은 메시지와 되돌릴 버전도 확인한다.

## 7. DB 스키마는 확장·이전·축소로 나눠 변경한다

- 애플리케이션은 여러 버전이어도 공유 DB의 스키마는 함께 사용한다. 신 버전만 이해하는 구조로 즉시 바꾸면 아직 실행 중인 구 버전이 실패할 수 있다.
- 다음은 주문의 배송지를 `address` 하나에서 `zipcode`, `address1`, `address2`로 나누는 가상 사례이다. 버전과 단계는 변경 순서를 설명하기 위한 예시이다.
- 새 컬럼 추가와 동시에 `address`를 삭제하면 구 버전의 조회·저장이 실패한다. 신 버전이 새 컬럼에만 기록한 주문은 이전 코드로 되돌려도 읽지 못할 수 있다.

| 단계 | 변경 | 공존·검증 조건 |
| :--- | :--- | :--- |
| ① 확장 | 새 컬럼 세 개를 빈 값을 허용하도록 추가하고 `address`는 유지한다. | 구 버전 `v1`의 읽기·쓰기가 계속 동작해야 한다. |
| ② 양쪽 쓰기 · `v2` | 옛 컬럼과 새 컬럼에 함께 쓰고 읽기는 옛 컬럼에서 한다. | `v1`과 공존할 수 있지만 `v1`이 쓴 주문에는 새 컬럼이 비어 있을 수 있다. |
| ③ 데이터 이전 | 기존 배송지를 변환해 새 컬럼을 채운다. | `v1`이 모두 종료된 뒤 수행한다. 자동 변환이 어려운 데이터는 따로 보완하고 동시 갱신과 충돌하지 않게 처리한다. |
| ④ 읽기 전환 · `v3` | 새 컬럼에서 읽고 쓰기는 양쪽 컬럼에 계속한다. | 이전 완료와 데이터 일치를 확인한다. `v2`와 공존해도 읽기 결과가 맞아야 한다. |
| ⑤ 옛 컬럼 쓰기 중단 · `v4` | 옛 컬럼의 필수 값 제약을 먼저 해제한 뒤 새 컬럼에만 쓴다. | 새 컬럼을 읽는 `v3`와 공존할 수 있다. 옛 컬럼을 읽는 버전으로 되돌릴 때는 데이터 보완이 필요하다. |
| ⑥ 축소 | 관찰 기간과 복구 가능 범위를 확인한 뒤 `address`를 삭제한다. | 옛 컬럼을 쓰는 버전과 다른 사용처가 없고 해당 컬럼이 필요한 버전으로 되돌릴 필요도 없어야 한다. |

- **호환성을 바꾸는 단계를 한 번의 배포에 묶지 않고, 단계마다 공존 가능한 버전과 진행 조건을 확인한다.**
- `v1`이 남아 있는 동안 데이터를 이전하면 이후 `v1`이 쓴 주문의 새 컬럼이 다시 비거나 최신 값과 달라질 수 있다.
- 양쪽 쓰기에서는 한쪽만 저장되거나 서로 다른 값이 남지 않도록 일관성을 관리한다. 데이터 이전도 진행 중인 갱신을 덮어쓰지 않게 구성하고 결과를 대조한다.
- 큰 테이블의 컬럼 추가와 데이터 이전은 잠금·부하·복제 지연을 일으킬 수 있다. 실제 DB의 DDL 동작을 확인하고 필요하면 작업을 나눠 수행한다.
- 확장·이전·축소는 버전 간 호환성을 관리하는 방법이다. 이 순서만으로 DB 작업 중의 무중단까지 보장하지는 않는다.

## 8. 롤백 가능 범위는 코드·스키마·데이터를 함께 확인한다

| 복구 방식 | 의미 | 확인할 조건 |
| :--- | :--- | :--- |
| Rollback · 롤백 | 이전 버전의 코드로 되돌리거나 기존 환경으로 트래픽을 돌린다. | 이전 버전이 현재 스키마와 변경된 데이터를 읽고 쓸 수 있어야 한다. |
| Roll Forward · 롤포워드 | 문제를 수정한 새 버전을 배포한다. | 수정본을 준비하고 검증·배포하는 동안의 사용자 영향을 고려한다. |

- **코드를 이전 버전으로 되돌려도 이미 바뀐 데이터와 스키마는 자동으로 복구되지 않는다.**
- 배송지 변경 사례에서 되돌릴 수 있는 범위는 단계에 따라 달라진다.

| 변경 상태 | 롤백 범위 | 이유 |
| :--- | :--- | :--- |
| ①~④ · 새 컬럼 추가부터 읽기 전환까지 | 옛 컬럼을 읽는 버전으로 되돌릴 수 있다. | 양쪽 쓰기가 정상적으로 유지됐다면 옛 컬럼에 최신 데이터가 남아 있다. |
| ⑤ · 옛 컬럼 쓰기 중단 | 새 컬럼을 읽는 `v3`로는 되돌릴 수 있지만 `v2`·`v1`로 되돌리려면 데이터 보완이 필요하다. | 쓰기 중단 뒤 들어온 주문은 옛 컬럼에 배송지가 없다. |
| ⑥ · 옛 컬럼 삭제 | 옛 컬럼을 사용하는 버전으로는 코드만 즉시 되돌릴 수 없다. | 별도의 스키마·데이터 복구나 롤포워드가 필요하다. |

- 되돌리기 어려운 변경은 마지막에 별도로 수행한다. 그전에 관찰할 기간, 복구할 버전과 필요한 데이터가 남아 있는지 확인한다.

## 9. 배포 성공은 기술 지표와 업무 지표로 판단한다

- 서버가 정상이어도 주문 완료나 결제 승인이 실패할 수 있다. 배포 성공은 미리 정한 지표가 정상 범위인지로 판단한다.

| 관점 | 확인할 지표·조건 |
| :--- | :--- |
| 기술 지표 | 오류율, 응답 시간, 자원 사용량과 처리 여유를 확인한다. |
| 업무 지표 | 주문 성공률, 결제 승인율 등 핵심 작업의 최종 결과를 확인한다. |
| 비교 기준 | 가능하면 같은 시간대의 기존 버전과 비교하고 요청량·요청 유형의 차이를 함께 본다. |
| 중단 조건 | 지표 악화 시 확대를 멈추고 트래픽 복귀·기능 비활성화·복구 배포 중 어떤 조치를 할지 정한다. |

- 카나리의 오류가 보이지 않아도 요청 수나 관찰 시간이 부족하면 안전하다고 판단하기 어렵다. 주요 작업이 실제로 수행됐는지도 확인한다.
- 비교할 지표, 관찰 구간과 중단 기준은 배포 전에 정한다. 고정된 카나리 비율이나 공통 임계값을 모든 서비스에 적용하지 않는다.
- 사용자 여정의 성공 조건과 지표 정의는 [SLI·SLO·Error Budget 문서](01_managing_reliability_with_slis_slos_and_error_budgets.md)를, 서비스·자원 지표의 조합은 [모니터링 접근 비교 문서](04_comparing_monitoring_approaches_and_applying_them_in_practice.md)를 참고한다.

### 기능 토글로 배포와 기능 공개를 나눈다

- 새 코드를 배포하되 기능 토글로 새 기능을 꺼 두고, 준비가 끝난 뒤 활성화할 수 있다.
- 문제가 생기면 재배포 없이 기능을 비활성화할 수 있다. 다만 기능을 끈다고 이미 기록한 데이터나 발생한 부작용까지 되돌아가지는 않는다.
- 기능 공개가 끝나 더 이상 필요하지 않은 토글과 과도기 코드는 제거해 분기와 관리 부담이 남지 않게 한다.

## 10. 무중단의 비용을 가용성 목표와 비교한다

- 무중단 배포에는 추가 자원과 호환성 유지 비용이 든다. 한 번에 끝낼 변경을 여러 배포로 나누고 양쪽 쓰기 같은 과도기 코드를 관리해야 한다.
- 축소 단계를 생략하면 옛 컬럼과 과도기 코드가 계속 남는다. 전환 완료와 정리 조건까지 변경 계획에 포함한다.

| 기준 | 무중단 배포 | 점검 시간에 배포 |
| :--- | :--- | :--- |
| 사용자 이용 | 배포 중에도 요청 처리를 유지한다. | 공지한 시간 동안 서비스의 일부 또는 전체를 멈춘다. |
| 설계·운영 부담 | 버전 공존과 상태·계약·데이터 호환성을 유지해야 한다. | 모든 사용처를 통제해 공존을 없앨 수 있다면 전환 절차를 단순화할 수 있다. |
| 적용을 검토할 상황 | 지속적인 서비스 제공이 필요하거나 배포가 잦다. | 중단을 허용할 수 있는 운영 시간이 있거나 큰 데이터 변경을 통제된 시간에 수행한다. |

- 평소에는 무중단으로 배포하고 큰 데이터 변경은 점검 시간에 수행하는 혼합 방식도 가능하다. 점검 배포에도 검증과 데이터 복구 계획은 필요하다.
- **무중단 배포는 가용성 목표를 지키기 위한 수단이다. 허용 가능한 중단, 변경 위험과 구현·운영 비용을 함께 비교해 적용 범위를 정한다.**
