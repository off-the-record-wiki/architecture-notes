    # USE·RED: 인프라 자원과 서비스 요청을 함께 모니터링하기

## 1. USE는 자원별 사용률·포화도·오류를 점검한다

- **USE Method는 각 자원의 Utilization, Saturation, Errors를 확인해 성능 병목과 자원 오류를 찾는 접근이다.**
- Brendan Gregg가 정리한 [USE Method](https://www.brendangregg.com/usemethod.html)는 성능 조사 초기에 중요한 자원을 빠뜨리지 않고 점검하는 데 활용한다.
- 수집 중인 지표부터 나열하기보다 CPU, 메모리, 디스크, 네트워크 등 확인할 자원을 먼저 정하고 각 자원에 필요한 지표를 찾는다.
- 지표를 수집할 수 없는 항목도 구분해 두면 어떤 자원을 아직 확인하지 못했는지 알 수 있다.

| 지표 | 의미 | 확인할 질문 |
| :--- | :--- | :--- |
| Utilization · 사용률 | 자원이 작업을 처리한 시간의 비율이나 전체 용량 중 사용한 비율이다. | 자원이 얼마나 사용되고 있는가? |
| Saturation · 포화도 | 자원이 바로 처리하지 못해 대기하거나 처리 한계를 넘긴 작업의 정도이다. | 자원을 기다리는 작업이 있는가? |
| Errors · 오류 | 자원 수준에서 발생한 오류의 수이다. | 자원에서 어떤 오류가 발생하는가? |

- CPU처럼 작업을 처리하는 자원은 바쁘게 일한 시간의 비율을, 메모리처럼 용량이 중요한 자원은 사용한 용량의 비율을 볼 수 있다.
- 포화도는 대기 큐 길이와 대기 시간 등으로 확인한다. 오류는 누적 건수뿐 아니라 관측 구간에 새로 발생한 건수도 본다.

## 2. 자원 특성에 맞는 USE 지표를 선택한다

- **같은 U·S·E라도 자원마다 측정 방법과 해석이 다르다.** 다음은 점검에 활용할 수 있는 지표 예시이다.

| 자원 | Utilization | Saturation | Errors |
| :--- | :--- | :--- | :--- |
| CPU | 전체·코어별 사용률이다. | 실행 대기 큐 길이와 스케줄러 대기 시간이다. | 하드웨어와 OS에서 제공하는 CPU·캐시 ECC 오류 등이다. |
| 메모리 | 사용 가능한 용량과 사용량이다. | 메모리 압박에 따른 익명 페이지의 페이징·스왑 활동 등이다. | 메모리 할당 실패 등이다. |
| 디스크 I/O | 장치가 I/O를 처리한 시간의 비율이다. | I/O 대기 큐 길이와 대기 시간이다. | 읽기·쓰기와 장치 오류이다. |
| 네트워크 | 최대 대역폭 대비 송수신 전송률이다. | 포화와 관련된 NIC·OS의 패킷 드롭과 버퍼 초과 등이다. | CRC·프레이밍 오류 등이다. |

- 네트워크 드롭은 여러 원인으로 발생할 수 있으므로 카운터의 의미와 발생 원인을 확인한다. 모든 드롭을 포화의 증거로 단정하지 않는다.
- 디스크는 I/O 처리와 저장 용량을 구분해 본다. 저장 공간이 부족한 문제는 I/O 사용률만으로 찾을 수 없다.
- 스레드 풀이나 연결 풀처럼 용량과 대기를 정의할 수 있는 소프트웨어 자원에도 USE를 적용할 수 있다.

## 3. 사용률만으로 병목 여부를 판단하지 않는다

- **높은 사용률은 병목을 조사할 단서이며, 대기와 사용자 지연을 함께 확인해야 영향을 판단할 수 있다.**
- 예를 들어 CPU 사용률이 85%여도 실행 대기가 적고 요청을 제때 처리한다면 해당 수치만으로 장애라고 판단하지 않는다.
- 반대로 긴 구간의 평균 사용률이 낮아도 짧은 시간 동안 부하가 집중되면 포화가 발생할 수 있다. 5분 평균은 수 초 동안의 급증을 가릴 수 있다.
- 이 절의 수치는 해석을 설명하기 위한 예시이며 실제 서비스의 권장 임계값은 아니다.

| 관찰한 상태 | 이어서 확인할 내용 |
| :--- | :--- |
| CPU 사용률이 높다. | 코어별 사용률, 실행 대기와 요청 지연을 함께 확인한다. |
| 평균 사용률은 낮지만 간헐적으로 느려진다. | 더 짧은 관측 구간과 부하가 집중된 인스턴스·코어를 확인한다. |
| 대기 큐가 계속 늘어난다. | 유입량이 처리량을 넘는지와 자원의 처리 한계를 확인한다. |
| 오류 카운터가 증가한다. | 오류 유형, 발생 시점과 재시도·복구 과정의 성능 영향을 확인한다. |

- 처음에는 CPU 포화, 메모리 압박, 네트워크 대역폭과 디스크 I/O처럼 확인하기 쉬운 항목부터 살펴볼 수 있다.
- 병목 후보를 찾으면 같은 시간대의 작업량과 지연을 비교해 실제 원인인지 조사한다. 하나의 자원에서 이상을 찾았어도 다른 문제가 함께 있을 수 있다.

## 4. USE는 자원 분석에 강점이 있지만 서비스 품질을 모두 설명하지는 못한다

- 메모리는 캐시를 사용량에 포함할지에 따라 사용률의 의미가 달라진다. 사용 가능한 메모리와 메모리 압박을 함께 확인한다.
- 메모리 포화는 CPU 실행 대기 큐처럼 하나의 직관적인 값으로 표현하기 어렵다. 페이징·스왑 등 환경에 맞는 지표를 해석해야 한다.
- 메모리 할당 실패가 항상 물리 메모리 부족을 뜻하지는 않는다. 가상 메모리나 프로세스 제한 등 실패 조건을 구분한다.
- 하드웨어와 OS에 따라 오류 카운터의 제공 범위도 다르다. 지표가 없다는 사실을 오류가 없다는 뜻으로 해석하지 않는다.
- **API·DB·외부 서비스 전체의 상태는 자원 사용률만으로 판단하기 어렵다.** 내부 자원이 정상이어도 요청이 실패하거나 잘못된 결과를 반환할 수 있다.
- USE로 개별 자원의 상태를 조사하고, 서비스 요청의 성공과 지연은 RED 등 요청 중심의 지표로 확인한다.

## 5. RED는 모든 서비스에 요청량·오류·응답 시간을 적용한다

- **RED Method는 각 서비스의 Rate, Errors, Duration을 측정해 요청이 얼마나 들어오고, 얼마나 실패하며, 얼마나 오래 걸리는지 확인하는 접근이다.**
- Tom Wilkie가 2015년에 만든 방식으로, [Grafana의 RED Method 설명](https://grafana.com/blog/the-red-method-how-to-instrument-your-services/)은 마이크로서비스에 공통된 모니터링 기준을 적용하는 데 초점을 둔다.
- 서비스마다 내부 구현과 자원 구성이 달라도 요청을 받는 경계에서는 같은 세 가지 질문으로 상태를 살펴볼 수 있다.

| 지표 | 의미 | 확인할 질문 |
| :--- | :--- | :--- |
| Rate · 요청률 | 단위 시간당 요청 수이다. 보통 RPS로 측정한다. | 서비스에 얼마나 많은 요청이 들어오는가? |
| Errors · 실패 요청 | 실패한 요청의 수와 비율이다. | 요청이 얼마나 실패하는가? |
| Duration · 응답 시간 | 요청을 처리하는 데 걸린 시간의 분포이다. | 요청이 얼마나 오래 걸리는가? |

## 6. RED 지표에는 요청의 측정 조건을 함께 정한다

### Rate는 요청량 변화의 기준이 된다

- 요청량은 서비스가 얼마나 사용되는지 보여 주며 오류와 지연의 변화를 해석하는 기준이 된다.
- 유입 요청 수와 완료한 요청 수는 과부하 상황에서 달라질 수 있으므로 어느 지점에서 측정했는지 구분한다.
- 요청량이 늘지 않아도 작업의 처리 비용이 커질 수 있다. 필요하면 API나 작업 유형별로 구분해 본다.

### Errors는 실패 건수와 비율을 함께 본다

- 실패 요청에는 타임아웃, HTTP `5xx`와 서비스의 성공 조건에 따라 실패로 정의한 결과를 포함한다.
- 실패 요청 수를 단위 시간으로 집계하고, 전체 대상 요청 수로 나눈 오류율도 함께 확인한다.
- 요청량이 증가하면 오류율이 같아도 실패 건수가 늘어난다. 실패 건수와 비율을 함께 보면 사용자 영향과 실패 빈도를 구분하기 쉽다.
- USE의 Errors는 자원 수준의 오류이며 RED의 Errors는 요청 수준의 실패이다. 이름이 같아도 측정 대상이 다르다.

### Duration은 평균보다 분포를 함께 본다

- 평균만으로는 일부 사용자의 긴 대기를 놓칠 수 있으므로 p95·p99 등 응답 시간의 분포를 함께 본다.
- 성공 요청과 실패 요청의 시간을 구분하면 오류를 빠르게 반환해 전체 평균이 낮아지는 상황을 파악할 수 있다.
- 호출자와 서버에서 측정한 시간은 포함하는 구간이 다를 수 있다. 측정 시작·종료 지점을 정해 비교한다.
- 지연과 실패 조건의 자세한 해석은 [Four Golden Signals 문서](02_monitoring_services_with_the_four_golden_signals.md)의 기준을 함께 참고한다.

## 7. 마이크로서비스에서는 일관된 지표가 장애 대응 부담을 줄인다

- **RED의 장점은 여러 서비스의 상태를 같은 기준으로 확인할 수 있다는 점이다.**
- API Gateway, 사용자 서비스와 주문 서비스에 같은 R·E·D 구성을 적용하면 처음 보는 서비스도 요청량, 실패와 지연부터 확인할 수 있다.
- 서비스마다 화면과 핵심 지표가 모두 다르면 장애 대응자가 각 서비스의 측정 방식을 먼저 이해해야 한다. 공통 구성을 사용하면 이 부담을 줄일 수 있다.

| 공통으로 확인할 내용 | 장애 대응에서의 이점 |
| :--- | :--- |
| 평소 대비 요청량 변화 | 요청이 늘거나 특정 서비스에 도달하지 않는 상황을 파악하는 데 도움이 된다. |
| 실패 건수와 오류율 | 요청이 실패하는 서비스와 영향 범위를 조사할 수 있다. |
| 응답 시간 분포 | 요청이 느려지는 서비스와 작업을 좁혀 볼 수 있다. |

- 오류와 지연은 사용자가 겪는 문제를 파악하는 단서이다. 내부 서비스의 실패가 재시도나 대체 처리로 복구될 수 있으므로 최종 사용자 영향은 사용자 요청 경계에서도 확인한다.
- 공통 지표를 적용하더라도 서비스별 목표값까지 같게 정할 필요는 없다. 허용 지연과 실패 조건은 기능의 요구에 따라 정한다.

## 8. Four Golden Signals·USE·RED는 서로 다른 관점을 보완한다

- Four Golden Signals와 RED는 요청의 수요·실패·지연을 공통으로 다룬다. RED의 Rate는 Traffic, Errors는 Errors, Duration은 Latency에 대응한다.
- RED의 세 가지 지표에는 Saturation이 직접 포함되지 않는다. 자원 여유와 대기는 Four Golden Signals의 Saturation이나 USE로 함께 확인한다.

| 접근 | 주로 살펴볼 대상 | 핵심 질문 |
| :--- | :--- | :--- |
| Four Golden Signals | 사용자 서비스의 지연·수요·실패·처리 한계이다. | 서비스의 품질과 처리 여유가 어떤 상태인가? |
| USE | 개별 인프라·소프트웨어 자원의 사용·대기·오류이다. | 어떤 자원이 병목이거나 오류를 일으키는가? |
| RED | 각 서비스의 요청량·실패·응답 시간이다. | 어느 서비스의 요청 처리가 달라졌는가? |

- **RED로 서비스 요청의 이상을 확인하고 USE로 관련 자원의 병목과 오류를 조사하면 사용자 영향과 인프라 상태를 함께 볼 수 있다.**
- 자원 지표가 정상이어도 애플리케이션 오류나 의존 서비스 지연이 있을 수 있다. 요청 지표와 자원 지표를 비교하고 로그·트레이스 등으로 원인 후보를 확인한다.
