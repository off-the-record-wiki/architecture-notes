# SLI·SLO·Error Budget: 사용자 경험을 측정하고 신뢰성을 관리하기

## 1. 신뢰성 목표는 사용자 영향과 변경 비용을 함께 고려한다

- **신뢰성 관리는 사용자가 기대하는 서비스 수준을 정하고, 측정 결과에 따라 기능 개발과 안정화의 우선순위를 조정하는 일이다.**
- 장애를 모두 없애는 것만 목표로 삼으면 작은 변경도 미루게 되고, 변경이 누적되면서 한 번의 배포에 포함되는 위험이 커질 수 있다.
- 가용성을 더 높이려면 이중화, 장애 격리, 자동화와 운영 인력 등에 추가 비용이 든다. 개선 비용과 사용자가 얻는 이점을 함께 판단한다.
- 서비스 내부가 정상이어도 사용자 기기와 네트워크 등 전체 이용 경로에는 실패 가능성이 남는다. 제한된 기간에 장애가 없었다는 사실이 앞으로의 100% 가용성을 보장하지는 않는다.
- 목표 수준은 대상 기능과 실패의 피해에 따라 정한다. 가용성 목표를 조정하더라도 데이터 손실 방지 등 반드시 지킬 조건까지 완화하는 것은 아니다.
- 이 문서의 목표값, 예산 구간과 운영 주기는 개념을 설명하기 위한 예시이며 실제 서비스의 권장 기준은 아니다.

## 2. SRE는 운영 문제를 소프트웨어와 측정으로 다룬다

- SRE(Site Reliability Engineering)는 Google에서 발전한 접근으로, 소프트웨어 엔지니어링을 서비스 운영에 적용한다.
- 반복적인 수동 작업을 자동화하고 시스템을 개선해 서비스 규모가 커져도 운영 부담이 같은 비율로 늘어나지 않도록 한다.
- DevOps가 개발과 운영의 협업·공동 책임을 강조한다면, SRE는 이를 실천하는 구체적인 접근 중 하나이다. 두 개념을 서로 배타적인 조직 모델로 보지는 않는다.

| 운영에서 다룰 문제 | SRE의 접근 |
| :--- | :--- |
| 안정성에 대한 판단 기준이 다르다. | 사용자 관점의 지표와 합의한 목표로 현재 상태를 판단한다. |
| 기능 배포와 안정화 작업이 경쟁한다. | Error Budget의 잔량과 소진 속도로 우선순위를 조정한다. |
| 수동·반복 작업이 엔지니어의 시간을 소모한다. | 작업을 자동화하고 원인을 제거하는 개선에 시간을 확보한다. |
| 장애가 같은 방식으로 반복된다. | 개인 비난보다 시스템·절차의 원인과 재발 방지 작업을 확인한다. |

- Google SRE의 운영 모델은 반복 운영 작업이 엔지니어의 시간을 모두 차지하지 않도록 운영 업무에 쓰는 시간을 최대 50%로 제한하고 나머지를 엔지니어링 작업에 확보한다. 이 비율을 모든 조직의 인력 배분 기준으로 그대로 적용할 필요는 없다.

## 3. SLI는 측정값, SLO는 목표, SLA는 고객과의 약속이다

| 개념 | 의미 | 예시 |
| :--- | :--- | :--- |
| SLI · Service Level Indicator | 서비스 수준을 정량적으로 측정하는 지표이다. | 최근 30일의 결제 완료율을 측정한 결과가 99.92%이다. |
| SLO · Service Level Objective | 정해진 기간과 조건에서 SLI가 충족해야 할 목표이다. | 최근 30일의 결제 완료율을 99.9% 이상으로 유지한다. |
| SLA · Service Level Agreement | 고객과 합의한 서비스 수준과 미달 시 조치 등을 정한 약속이다. | 계약에서 정한 가용률에 미달하면 서비스 크레딧을 제공한다. |

- **SLI로 현재 상태를 측정하고 SLO와 비교한다. SLA가 있다면 계약에서 정한 측정·보상 조건도 별도로 확인한다.**
- SLO는 내부 운영 기준으로 사용할 수 있으며 SLA가 없는 서비스에도 필요하다.
- 내부에서 더 일찍 대응하도록 SLO를 SLA보다 엄격하게 설정할 수 있다. 예를 들어 같은 가용률 정의에서 SLO 99.9%, SLA 99.5%로 정하면 두 기준 사이에 0.4%p의 차이가 생긴다.
- 목표를 비교하려면 측정 대상, 기간과 제외 조건이 같아야 한다. 응답 시간처럼 낮을수록 좋은 지표에는 엄격한 목표가 더 작은 값이므로 `SLO > SLA`를 모든 지표에 적용하지 않는다.

## 4. SLI는 핵심 사용자 여정에서 정의한다

- 서버가 정상이라는 사실과 사용자가 원하는 작업을 완료할 수 있다는 사실은 다르다. CPU 사용률이 낮고 API가 성공 응답을 반환해도 결제 화면이 동작하지 않을 수 있다.
- Critical User Journey는 사용자가 서비스에서 중요한 목적을 달성하는 과정이다. 회원가입, 검색 후 상품 확인, 결제 완료 등이 해당한다.
- 먼저 중요한 여정을 고르고 성공 여부와 대기 시간을 설명하는 지표를 정한다. 사용자 영향이 다른 여정에 같은 SLO를 일괄 적용하지 않는다.

| 사용자 여정 | SLI 후보 | 정의할 내용 |
| :--- | :--- | :--- |
| 회원가입 후 첫 로그인 | 가입 완료율, 인증 메일 도달 시간 | 가입 시도의 시작·완료 조건, 중도 이탈과 시스템 실패의 구분을 정한다. |
| 검색 후 상품 확인 | 검색 응답 시간, 정상 결과 반환 비율 | 측정 시작·종료 지점과 정상 결과의 조건을 정한다. |
| 결제 완료 | 결제 완료율, 완료까지 걸린 시간 | 유효한 결제 시도, 업무상 거절과 시스템 오류, 최종 완료 상태를 구분한다. |

- 좋은 SLI는 사용자가 겪는 품질을 반영하고, 일관되게 측정할 수 있으며, 결과에 따라 개선 행동을 정할 수 있어야 한다.
- HTTP `2xx`·`3xx` 비율만으로 업무 성공을 단정하지 않는다. 응답 본문에 오류를 담거나 결제 완료 전 성공을 반환하는 서비스라면 실제 결과를 별도로 확인한다.
- CPU·메모리·디스크 사용률은 원인 분석과 용량 관리에 유용하지만 일반적인 사용자 서비스의 품질을 직접 설명하지는 못한다.
- 평균 응답 시간은 느린 요청을 가릴 수 있으므로 p95·p99 같은 백분위수와 실패율을 함께 본다. p99는 관측한 응답 시간의 99번째 백분위수이며 가장 느린 1%의 모든 요청 시간을 보여 주는 값은 아니다.

### VALET으로 지표 후보를 분류한다

- VALET은 지표 후보를 정리하는 비공식 분류 도구이며 Google SRE의 공식 표준은 아니다. 각 항목을 반드시 SLO로 만들 필요는 없다.

| 분류 | 관찰할 내용 | 지표 예시 |
| :--- | :--- | :--- |
| Volume | 단위 시간당 처리 규모이다. | 요청 수, RPS, TPS이다. |
| Availability | 서비스를 정상적으로 이용할 수 있는 정도이다. | 유효한 요청 중 성공한 요청의 비율이다. |
| Latency | 사용자가 결과를 받기까지 걸리는 시간이다. | p95·p99 응답 시간, 기준 시간 안에 완료한 요청 비율이다. |
| Errors | 실패의 빈도와 유형이다. | 시스템 오류율, 타임아웃 비율이다. |
| Tickets | 사람이 처리해야 하는 문제와 운영 부담이다. | 장애·문의 건수와 수동 처리 건수이다. |

- 요청량과 티켓 수는 SLI를 해석하거나 운영 부담을 파악하는 보조 지표가 될 수 있다. 사용자 경험과의 관계를 확인해 필요한 지표만 선택한다.

## 5. SLO에는 측정 조건과 목표 기간을 함께 정한다

- `성공률 99.9%`만으로는 측정과 판정 방법이 정해지지 않는다. 어떤 요청을 어디서 측정하고 어느 기간으로 집계하는지 함께 정의한다.

| 항목 | 결제 완료율 SLO를 정의할 때의 예시 |
| :--- | :--- |
| 대상 | 사용자의 유효한 결제 시도를 대상으로 한다. |
| 성공 조건 | 결제 시도와 연결된 주문이 합의한 기한 안에 완료 상태에 도달한다. |
| 분모와 분자 | 대상 결제 시도 수를 분모로, 성공 조건을 충족한 시도 수를 분자로 사용한다. |
| 실패·제외 조건 | 시스템 오류·타임아웃과 잔액 부족 등 업무상 거절의 집계 규칙을 구분한다. |
| 관측 지점 | 결제 시도 기록과 최종 주문 상태를 대조한다. 사용자 화면의 완료 여부와 차이가 있는지도 확인한다. |
| 집계 기간과 목표 | 최근 30일을 이동 구간으로 집계하고 완료율 99.9% 이상을 목표로 한다. |
| 데이터 누락 | 측정 기록이 빠진 경우를 정상으로 간주하지 않고 누락 여부와 처리 규칙을 정한다. |

- 목표값은 과거 측정값, 사용자가 감수할 수 있는 실패, 업무상 손실과 개선 비용을 바탕으로 제품·개발·운영 담당자가 합의한다.
- 현재 달성 수준만 따라 정하면 필요한 개선을 놓칠 수 있다. 반대로 근거 없이 높은 목표를 정하면 계속된 미달로 지표를 신뢰하지 않게 될 수 있다.
- 월 단위 고정 기간과 최근 30일 이동 구간은 예산 계산과 회복 시점이 다르다. 대시보드와 운영 정책에서 같은 정의를 사용한다.
- 지연 SLO를 Error Budget으로 관리하려면 `p99 300ms 이하`처럼 백분위수로 표현하는 방식과 함께, `300ms 안에 완료한 요청이 99% 이상`처럼 좋은 요청의 비율로 표현하는 방식을 검토할 수 있다.

## 6. 가용률을 시간으로 환산할 때는 계산 기준을 구분한다

- 아래는 30일 내내 서비스를 제공하고 시간 기준 가용률을 사용하는 경우의 단순 환산이다. 업종별 권장 수준이나 한 번의 장애에 허용된 복구 시간을 뜻하지 않는다.

| 가용률 목표 | 30일 기준 허용 중단 시간 | 365일 기준 허용 중단 시간 |
| :--- | :--- | :--- |
| 99% | 7시간 12분 | 3일 15시간 36분 |
| 99.9% | 43.2분 | 8시간 45분 36초 |
| 99.95% | 21.6분 | 4시간 22분 48초 |
| 99.99% | 4.32분 | 약 52분 34초 |
| 99.999% | 약 25.9초 | 약 5분 15초 |

- 계산식은 `대상 기간 × (1 - 가용률 목표)`이다. 월간 목표를 충족했는지와 연간 목표를 충족했는지는 각각 해당 기간으로 판정한다.
- 요청 기준 가용률은 성공한 요청 수를 전체 대상 요청 수로 나눈다. 트래픽이 몰린 시간의 장애는 같은 길이의 한산한 시간 장애보다 더 많은 실패 요청을 만들 수 있다.
- **요청 기준 SLO의 실패 허용량을 중단 시간으로 그대로 환산하지 않는다.**

## 7. Error Budget은 SLO가 허용하는 실패량이다

- Error Budget은 목표 기간에 SLO를 충족하면서 허용할 수 있는 실패량이다. 성공 비율로 정의한 SLO에서 허용 실패 비율은 `1 - SLO`이다.

```text
허용 실패 비율 = 1 - SLO
요청 기준 총예산 = 대상 요청 수 × 허용 실패 비율
남은 예산 = 총예산 - 관측한 실패 요청 수
시간 기준 총예산 = 대상 운영 시간 × 허용 실패 비율
```

- 예를 들어 SLO가 99.9%이고 대상 요청이 1,000,000건이면 실패 예산은 1,000건이다. 300건이 실패했다면 남은 예산은 700건으로 총예산의 70%이다.
- 시간 기준으로 30일의 가용률 목표가 99.9%라면 예산은 `30 × 24 × 60 × 0.001 = 43.2분`이다.
- 예산은 배포 실패뿐 아니라 집계 대상에 포함된 인프라 장애와 의존 서비스 장애 등으로도 소진된다. 원인과 별개로 사용자가 겪은 실패를 측정하고, 원인에 따른 후속 행동은 운영 정책에서 정한다.
- 예산이 남았다는 이유로 장애를 일부러 만들거나 전부 사용할 필요는 없다. 남은 예산과 변경 위험을 함께 보고 배포·실험을 진행할 여지가 있는지 판단한다.
- 요청 기준 예산은 기간 내 요청량에 영향을 받으며 이동 구간에서는 오래된 성공·실패 기록이 구간 밖으로 빠진다. 예산 잔량이 시간에 따라 반드시 줄어들기만 하는 것은 아니다.

## 8. Burn Rate로 예산이 줄어드는 속도를 본다

- 예산 잔량이 같아도 빠르게 실패가 늘어나는 서비스와 안정적으로 운영되는 서비스의 대응은 달라야 한다.
- **Burn Rate는 관측한 실패 비율이 SLO의 허용 실패 비율보다 몇 배 높은지 나타낸다.**

```text
Burn Rate = 관측 구간의 실패 비율 / (1 - SLO)
```

- SLO가 99.9%라면 허용 실패 비율은 0.1%이다. 최근 관측 구간의 실패율이 1.4%라면 Burn Rate는 14이다.
- 다음은 30일 예산이 전부 남아 있고 같은 실패율이 지속된다는 가정의 환산이다. 요청 기준에서는 요청량이 시간에 걸쳐 일정하다고 가정한다.

| Burn Rate | 전체 예산을 소진하는 데 걸리는 시간 |
| :--- | :--- |
| 1 | 30일이다. |
| 10 | 3일이다. |
| 14 | 약 2.14일이다. |
| 100 | 7시간 12분이다. |

- 이미 예산을 사용했다면 소진까지 남은 시간은 더 짧다. 실제 트래픽과 오류율이 변하므로 이 계산을 확정된 예측으로 사용하지 않는다.
- 30일을 720시간으로 보면 Burn Rate 14.4가 1시간 관측될 때 전체 예산의 약 2%에 해당한다. 이 환산 역시 시간 기준 또는 요청량이 일정하다는 가정에 따른다.
- [Google SRE Workbook의 알림 예시](https://sre.google/workbook/alerting-on-slos/)는 최근 1시간과 최근 5분의 Burn Rate가 모두 14.4를 넘는 조건을 사용한다. 이는 14배를 한 시간 동안 연속으로 넘겨야만 알린다는 뜻이 아니다.
- 긴 구간으로 누적 영향을 보고 짧은 구간으로 문제가 계속되는지 확인한다. 임계값과 구간은 서비스의 요청량, 대응 시간과 알림 부담에 맞춰 정한다.

## 9. 예산 상태에 따른 행동을 사전에 합의한다

- Error Budget은 대시보드에 표시하는 것만으로 역할을 다하지 못한다. 예산이 줄어들 때 어떤 변경을 멈추고 어떤 작업을 우선할지 미리 정한다.
- 다음 표는 운영 정책의 예시이다. 잔량뿐 아니라 Burn Rate와 목표 기간의 남은 시간도 함께 판단한다.

| 남은 예산 | 운영 상태 | 행동 예시 |
| :--- | :--- | :--- |
| 50% 초과 | 정상 운영 | 합의한 배포 절차에 따라 기능 개발과 변경을 진행한다. |
| 25% 초과 ~ 50% 이하 | 주의 | 위험이 큰 변경을 보류하고 안정화 작업의 우선순위를 높인다. |
| 10% 초과 ~ 25% 이하 | 경고 | 신규 기능 배포를 멈추고 오류 수정과 안정화 작업에 집중한다. |
| 10% 이하 | 비상 | 비필수 변경을 중단하고 장애 대응·안정화를 우선한다. 원인 분석과 재발 방지 작업을 정한다. |

- 배포 제한에는 장애 복구, 긴급 보안 수정 등 필요한 변경의 예외 조건과 판단 책임을 함께 정한다. 모든 변경을 금지해 복구까지 막지 않는다.
- 예산이 회복됐다고 판단할 조건과 배포 재개 기준도 정한다. 기간이 바뀌었다는 이유만으로 원인을 해결하지 않은 변경을 반복하지 않는다.
- 개발팀과 운영팀은 같은 SLO, 예산 계산과 변경 정책을 사용한다. 의견이 다를 때 판단할 책임과 협의 경로를 정해 둔다.
- 장애 회고에는 사용자 영향, 실패량, 예산 소진량과 재발 방지 작업을 남긴다. 예산 초과를 개인이나 팀에 대한 처벌 기준으로 사용하지 않는다.

## 10. 측정과 의사결정을 작은 범위에서 시작한다

| 단계 | 정리할 내용 |
| :--- | :--- |
| 핵심 여정 선택 | 사용자와 업무에 중요한 여정을 골라 성공 조건을 정한다. |
| SLI 정의 | 핵심 지표의 분모·분자, 관측 지점과 집계 규칙을 정하고 데이터를 수집한다. |
| SLO 합의 | 과거 측정값과 사용자 요구를 비교해 목표 기간과 목표값을 정한다. |
| 예산 정책 합의 | 배포 제한, 안정화 우선순위, 예외와 재개 조건을 정한다. |
| 대시보드와 알림 연결 | SLI, 목표 달성 여부, 남은 예산과 Burn Rate를 함께 확인한다. |
| 정기 검토 | 측정이 사용자 경험을 반영하는지와 정책이 실제 결정에 쓰이는지 확인한다. |

- 처음에는 중요한 여정 하나와 소수의 지표로 시작할 수 있다. 측정 결과와 운영 정책을 실제로 사용할 수 있는 범위에서 확장한다.
- 주간 운영 검토와 분기별 목표 검토 등을 활용할 수 있지만 주기는 변경 빈도와 업무 영향에 맞춰 정한다.
- 목표를 바꿀 때는 사용자 요구와 운영 조건이 어떻게 달라졌는지 확인한다. 미달을 없애기 위해 목표값만 낮추지 않는다.

## 11. SLO를 형식적으로 운영하게 만드는 패턴을 피한다

| 실패 패턴 | 생기는 문제 | 바꿀 행동 |
| :--- | :--- | :--- |
| 근거 없이 높은 목표를 정한다. | 계속된 미달로 알림을 무시하고 목표를 신뢰하지 않게 된다. | 사용자 요구, 현재 수준과 개선 비용을 비교해 목표와 개선 계획을 함께 정한다. |
| 지나치게 낮은 목표를 정한다. | 사용자가 불편을 겪어도 목표는 달성한 것으로 보일 수 있다. | 사용자 영향과 업무 손실을 반영해 목표의 적절성을 확인한다. |
| 수집하기 쉬운 지표만 본다. | 인프라가 정상이어도 사용자 여정의 실패를 놓친다. | 사용자 여정의 성공과 지연을 측정한다. |
| 모든 지표를 SLI·SLO로 만든다. | 검토와 대응이 어려워지고 중요한 지표를 놓친다. | 의사결정에 필요한 핵심 지표와 원인 분석용 지표를 구분한다. |
| 문서만 만들고 사용하지 않는다. | 배포와 안정화 우선순위가 측정 결과와 무관하게 정해진다. | 정기 검토와 배포 판단에 SLO·예산 상태를 사용한다. |
