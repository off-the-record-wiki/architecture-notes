# 품질 요구사항: 구조를 바꾸는 조건과 숨은 기대 찾기

## 1. 품질 요구사항은 구조 선택의 근거이다

- **품질 요구사항은 시스템이 어떤 조건에서 어느 수준으로 동작해야 하는지 정한다.**
- 상품을 검색한다는 기능만으로는 적합한 처리 구조, 배포 단위나 저장 방식을 충분히 판단하기 어렵다.
- 피크 부하에서의 응답 시간과 검색 장애의 허용 범위가 정해지면 필요한 구조를 구체적으로 비교할 수 있다.
- 품질 목표를 뒤늦게 확인하면 코드 수정뿐 아니라 데이터 구조와 서비스 경계까지 바꿔야 할 수 있다.
- 기능 요구사항, 품질 요구사항과 제약조건을 함께 확인하고 설계를 시작한다.

| 구분 | 의미 | 예시 |
| :--- | :--- | :--- |
| 기능 요구사항 | 시스템이 수행할 일을 정한다. | 사용자가 상품을 검색할 수 있다. |
| 품질 특성 | 검토할 성질의 이름이다. | 성능 효율성, 신뢰성과 보안성이다. |
| 품질 요구사항 | 특정 조건에서 요구하는 동작 수준이다. | 지정한 피크 부하에서 검색 요청의 95%가 2초 이내에 완료된다. |
| 제약조건 | 선택 가능한 해법의 범위를 제한한다. | 기존 인증 체계를 사용하고 정해진 예산 안에서 운영한다. |

- 표의 수치는 설명용 예시이며 실제 목표는 업무 조건에 맞춰 합의한다.
- 비기능 요구사항이라는 표현은 품질 요구사항과 기술·조직 등의 제약조건을 함께 가리키기도 한다.
- 성능이나 보안 같은 이름을 적는 것과 검증 가능한 요구사항을 정하는 것은 다르다.

## 2. 명세서에 없는 품질을 네 경로로 찾는다

- 모두 당연하다고 생각하거나 사용량을 모르거나 관련 담당자가 참여하지 않으면 품질 요구가 빠질 수 있다.
- 문서에 적혀 있지 않은 기대도 실제 사용자와 운영자의 판단에 영향을 준다.
- 발견한 내용은 바로 확정하지 않고 확인할 후보로 기록한다.

| 발견 경로 | 확인할 질문 | 확인할 품질 후보 |
| :--- | :--- | :--- |
| 이해관계자 | 이 시스템 때문에 가장 곤란해질 상황은 무엇인가? | 응답 성능, 복구성, 책임 추적성과 테스트 용이성 등이다. |
| 업무 목표 | 목표를 달성하지 못하게 하는 기술적 원인은 무엇인가? | 빠른 기능 변경, 시스템 간 연동과 장애 감소 등이다. |
| 요구사항 문장 | 숫자, 마감 시각, 지역과 금액은 어떤 조건을 뜻하는가? | 피크 처리량, 배치 완료 시간, 정확성과 데이터 보호 등이다. |
| 적용 의무와 약속 | 어떤 법·지침·조직 정책·계약이 이 시스템에 적용되는가? | 접근 통제, 접근성, 기록 보존과 서비스 수준 등이다. |

- 사용자뿐 아니라 업무, 운영, 보안, QA와 개발 담당자의 관점을 확인한다.
- 빨리 출시해야 한다는 말은 변경 용이성 요구일 수도 있고 단순한 납기 제약일 수도 있다.
- 고객 불만을 줄여야 한다는 말에서는 지연, 오류와 사용의 어려움 중 실제 원인을 확인한다.
- 법·정책·계약은 적용 범위와 담당자의 해석을 확인하고 구체적인 요구사항이나 제약조건으로 정리한다.

## 3. 문장 속 단서는 질문으로 바꾼다

> 전국 200개 지점이 매월 말일에 정산 내역을 등록하고, 본사는 다음 날 오전 9시까지 결과를 확인한다.

| 단서 | 추가로 확인할 내용 | 설계에 미치는 영향 |
| :--- | :--- | :--- |
| 200개 지점 | 동시에 등록하는 지점 수와 지점별 데이터량은 얼마인가? | 유입량과 처리 용량을 산정한다. |
| 매월 말일 | 특정 시간에 요청이 집중되는가? | 피크 처리와 작업 분산 방식을 검토한다. |
| 다음 날 오전 9시 | 입력 마감은 언제이며 실패한 작업을 다시 처리할 시간이 있는가? | 배치 처리 시간과 복구 여유를 정한다. |
| 정산 결과 | 허용 오차, 정정 절차와 변경 이력은 무엇인가? | 계산 검증, 데이터 일관성과 감사 기록을 설계한다. |

- 지점 수만으로 동시 사용자 수나 초당 요청 수를 확정하지 않는다.
- 가정한 부하와 확인된 부하를 구분하고, 실측 자료나 업무 담당자의 답변으로 보완한다.
- 품질 모델은 이 질문들에서 놓친 관점이 있는지 확인하는 데 사용한다.

## 4. 후보를 요구사항으로 확정한다

| 단계 | 남길 내용 |
| :--- | :--- |
| 발견 | 어떤 문장, 업무 목표나 담당자의 우려에서 나온 후보인지 기록한다. |
| 확인 | 적용 대상과 조건을 확인하고 미확인 내용은 가정으로 표시한다. |
| 구분 | 품질 요구사항인지 이미 정해진 제약조건인지 구분한다. |
| 합의 | 필요한 수준, 우선순위와 확인 책임자를 정한다. |
| 구체화 | 상황, 기대 동작과 판정 방법을 품질 시나리오로 작성한다. |

- 보안 상, 성능 상처럼 모두 높은 등급으로 표시하면 대안을 고르는 기준이 부족하다.
- 한 요구가 여러 품질에 해당할 수 있으므로 분류 하나에 억지로 맞추지 않는다.
- 중요한 미확인 가정을 숨기고 요구사항이 확정된 것처럼 설계하지 않는다.

## 5. 아키텍처 드라이버와 우선순위를 구분한다

- 아키텍처 드라이버는 중요한 설계 결정을 좌우하는 요구사항이나 제약조건이다.
- **이 조건이 달라지면 구조, 인터페이스, 데이터 소유권이나 배포 방식도 달라지는지 확인한다.**
- 품질 요구사항뿐 아니라 핵심 업무 기능과 외부 시스템 유지 조건도 드라이버가 될 수 있다.
- 우선순위는 요구가 충돌하거나 자원이 부족할 때 무엇을 먼저 지킬지 정하는 기준이다.
- 중요도가 높다는 이유만으로 모든 항목이 구조를 바꾸는 드라이버가 되는 것은 아니다.
- 응답 시간 목표만 보고 특정 아키텍처를 바로 선택하지 않고, 현재 구조를 포함한 여러 대안을 비교한다.
