# 품질 목표와 시나리오: 설계부터 검증까지 같은 기준 사용하기

## 1. 숫자뿐 아니라 조건과 판정 방법을 정한다

- **검증 가능한 품질 목표에는 대상, 조건, 지표와 합격 기준이 필요하다.**
- 응답 시간 500ms라는 숫자만으로는 어떤 요청을 어떤 부하에서 측정하는지 알 수 없다.
- 평균인지 p95인지, 외부 시스템 호출을 포함하는지에 따라서도 결과가 달라진다.
- 측정 방법과 판정 기준을 미리 합의해야 구현 결과를 같은 의미로 평가할 수 있다.
- 이 문서의 수치와 환경은 작성 방법을 보여 주기 위한 예시이며 실제 서비스의 권장 기준은 아니다.

| 항목 | 주문 API 성능 목표의 예시 |
| :--- | :--- |
| 대상 | 주문 생성 API를 대상으로 한다. |
| 조건 | 합의한 데이터 규모와 요청 구성을 사용해 초당 500건을 30분간 요청한다. |
| 측정 범위 | 클라이언트가 요청을 보내고 최종 응답을 받기까지 측정하며 외부 결제 호출을 포함한다. |
| 지표와 목표 | 응답 시간 p95는 500ms 이하, 요청 실패율은 0.1% 이하이다. |
| 실패 집계 | 서버 오류와 타임아웃을 실패로 집계하고 업무상 거절 응답의 분류를 별도로 정한다. |
| 검증 방법 | 부하 테스트 결과와 서버·외부 연동 지표를 함께 확인한다. |

- 동시 사용자 수와 초당 요청 수는 같은 값이 아니다. 사용자의 행동과 대기 시간을 반영해 부하 모델을 정한다.
- p95는 측정한 응답 시간의 95번째 백분위수이며 모든 요청이 해당 시간 안에 끝난다는 뜻은 아니다.
- 빠르게 실패한 요청 때문에 성능이 좋아 보이지 않도록 응답 시간과 실패율을 함께 본다.

## 2. 목표값은 업무 영향과 비용을 바탕으로 합의한다

- 표준의 측정 방법을 사용할 수 있어도 목표값은 시스템의 맥락에 맞게 정해야 한다.
- 사용자가 기다릴 수 있는 시간, 장애 시 손실과 이미 약속한 서비스 수준을 확인한다.
- 현재 측정값과 예상 부하를 기준으로 목표 달성에 필요한 변경과 비용을 비교한다.
- 근거가 부족한 목표는 가정임을 밝히고 실험으로 달성 가능성을 확인한다.
- 측정 결과가 목표에 미치지 못하면 구조, 구현이나 목표를 재검토하되 목표 변경은 이해관계자와 다시 합의한다.

## 3. 품질 요구사항을 네 요소의 시나리오로 표현한다

- 품질 시나리오는 새로운 종류의 요구사항이 아니라 품질 요구사항을 구체적인 상황으로 표현하는 방법이다.
- 사용자 요청뿐 아니라 장애, 데이터 증가와 기능 변경 요청도 시나리오의 자극이 될 수 있다.

| 요소 | 적을 내용 | 검색 성능 예시 |
| :--- | :--- | :--- |
| 맥락 · Context | 운영 환경, 부하와 데이터 상태를 적는다. | 할인 행사 시작 직후, 검색 요청이 초당 1,000건 유입된다. |
| 자극 · Stimulus | 어떤 사건이나 요청이 발생하는지 적는다. | 고객이 키워드로 상품을 검색한다. |
| 응답 · Response | 시스템이 제공해야 할 결과를 적는다. | 검색 결과 첫 페이지 20건을 반환한다. |
| 측정 · Measurement | 응답의 합격 기준을 적는다. | 요청의 95%가 2초 이내에 완료되고 실패율은 0.1% 이하이다. |

- 응답에는 Redis를 사용한다 같은 구현 방법 대신 기대하는 동작을 적는다.
- 이미 특정 기술을 사용하도록 정해져 있다면 그 조건은 제약조건으로 별도 관리한다.
- SEI의 여섯 요소 형식은 자극원, 자극, 환경, 대상, 응답과 응답 측정을 구분한다.
- 네 요소로 작성해도 누가 사건을 일으키고 어느 기능이 영향을 받는지는 본문에서 명확히 한다.

## 4. 장애와 변경도 시나리오로 검증한다

### 검색 장애가 주문에 미치는 영향

| 요소 | 예시 |
| :--- | :--- |
| 맥락 | 합의한 주문 요청 구성을 초당 200건으로 보내는 동안 검색 장애를 10분간 유지한다. |
| 자극 | 검색 서비스가 모든 요청에 응답하지 않는다. |
| 응답 | 주문·결제 처리를 계속하고 검색 화면에는 이용 불가 안내를 표시한다. |
| 측정 | 장애 기간의 주문 성공률이 99.9% 이상이며 검색 요청 후 3초 이내에 안내를 표시한다. |

- 검색 프로세스를 분리했다는 사실만으로 이 목표가 충족되지는 않는다.
- 주문이 검색을 기다리는지, 연결 풀과 DB 같은 자원을 공유하는지 실제 흐름을 확인한다.

### 새로운 결제수단의 추가

| 요소 | 예시 |
| :--- | :--- |
| 맥락 | 기존 결제 시스템을 운영 중이며 새 연동의 API 명세와 테스트 환경을 사용할 수 있다. |
| 자극 | 기존 연동 방식을 따르는 결제수단 한 개를 추가한다. |
| 응답 | 기존 결제수단의 동작을 유지하면서 신규 결제수단을 지원한다. |
| 측정 | 해당 코드에 익숙한 개발자 두 명이 개발과 통합 테스트를 3영업일 안에 완료하고 기존 회귀 테스트를 통과한다. |

- 개발 기간은 변경 범위, 담당자의 경험과 외부 승인 대기에 영향을 받는다.
- 인력과 작업 범위를 고정해야 변경 용이성에 대한 판단 근거로 사용할 수 있다.

## 5. 지표가 실제 품질을 반영하는지 확인한다

| 목표 | 함께 정할 내용 | 잘못 해석하기 쉬운 부분 |
| :--- | :--- | :--- |
| 응답 시간 | 부하, 측정 구간, 백분위수와 오류·타임아웃 집계 | 평균이 낮아도 일부 사용자가 오래 기다릴 수 있다. |
| 가용성 | 대상 기능, 관측 기간, 중단 판정과 제외 조건 | 프로세스가 떠 있어도 핵심 기능은 실패할 수 있다. |
| 복구 시간 | 장애 발생·탐지 중 어느 시점부터 재는지와 복구 완료 조건 | 서버 재기동이 데이터 정합성 회복까지 뜻하지는 않는다. |
| 감사 기록률 | 기록해야 할 행위의 범위와 실제 행위 수를 확인하는 방법 | 이미 수집된 로그만 세면 누락된 행위를 발견하기 어렵다. |

- 시간 기준 가용률을 사용할 경우 서비스 제공 가능 시간을 약속한 운영 시간으로 나눈다.
- 예를 들어 30일 내내 운영하는 서비스의 가용률 목표가 99.95%라면 단순 계산상 허용 중단 시간은 21.6분이다.
- 이 계산만으로 한 번의 장애 복구 시간이나 데이터 손실 허용 범위까지 정해지지는 않는다.
- 감사 기록이 남았다는 사실과 그 기록의 위변조 방지·조회 가능성은 각각 확인한다.
- **한 지표를 맞추는 과정에서 다른 품질이 나빠지지 않도록 보완 지표와 기대 동작을 함께 정한다.**

## 6. 시나리오를 테스트와 인수 기준으로 연결한다

| 시나리오 요소 | 검증 계획에서 구체화할 내용 |
| :--- | :--- |
| 맥락 | 환경 구성, 데이터 규모, 요청 비율, 지속 시간과 준비 상태를 정한다. |
| 자극 | 부하나 장애를 어떤 위치와 시점에 발생시킬지 정한다. |
| 응답 | 정상·대체·실패 경로의 기대 동작을 확인한다. |
| 측정 | 관측 지점, 집계 방식과 합격·실패 기준을 정한다. |

- 같은 시나리오를 설계 대안 검토, 구현 검증과 인수 판정에서 사용한다.
- 테스트 환경과 운영 환경의 차이도 기록해야 결과의 적용 범위를 알 수 있다.
- 구조나 요구사항이 바뀌면 관련 시나리오와 검증 계획을 함께 갱신한다.
