# 트레이드오프: 품질과 비용을 함께 비교해 결정하기

## 1. 하나의 설계 결정은 여러 품질에 영향을 준다

- **트레이드오프는 어떤 이점을 얻는 대신 다른 품질이나 비용에서 부담을 감수해야 하는 관계이다.**
- 캐시로 조회 지연을 줄여도 갱신 정책, 데이터 최신성과 장애 처리를 함께 다뤄야 한다.
- 이중화로 장애 대응 능력을 높여도 자원과 운영 비용이 추가된다.
- 비용과 일정은 품질 특성과 구분되는 제약조건이지만 설계 대안의 선택에 영향을 준다.
- 여러 요구를 각각 달성할 수 있어도 같은 구조와 예산 안에서 동시에 달성할 수 있는지는 따로 검토해야 한다.

| 설계 수단 | 기대하는 효과 | 함께 확인할 부담 |
| :--- | :--- | :--- |
| 추가 인증 단계 | 계정 보호를 강화한다. | 사용자 절차와 실패 가능성이 늘고 지연이 추가될 수 있다. |
| 조회 캐시 | 반복 조회의 응답 시간과 원본 부하를 줄인다. | 갱신 전의 값 노출, 무효화와 운영 로직이 필요하다. |
| 비동기 읽기 복제본 | 조회 부하를 분산한다. | 복제 지연과 장애 전환 동작을 다뤄야 한다. |
| 서비스 분리 | 독립적인 배포와 확장이 가능해진다. | 통신 실패와 데이터 일관성을 다룰 코드가 필요하고 운영 대상이 늘어난다. |

- 품질이 항상 서로 충돌하는 것은 아니다. 입력 검증은 보안과 잘못된 입력에 대한 신뢰성을 함께 높일 수 있다.
- 각 수단의 효과와 비용은 실제 구현과 부하 조건에서 확인해야 한다.

## 2. 반드시 지킬 조건과 조정할 목표를 구분한다

- 먼저 적용 의무, 업무상 금지된 실패와 계약상 필수 조건을 확인한다.
- 반드시 지켜야 하는 조건을 충족하지 못하는 대안은 다른 장점만으로 채택할 수 없다.
- 조정 가능한 목표는 허용 범위와 업무 영향을 이해관계자와 협의한다.

| 질문 | 확인하려는 내용 |
| :--- | :--- |
| 이 목표를 지키지 못하면 누가 어떤 손해를 보는가? | 목표의 업무상 중요성을 확인한다. |
| 어느 기능에서는 지연이나 일시적인 불일치를 허용할 수 있는가? | 모든 기능에 같은 수준이 필요한지 확인한다. |
| 가장 먼저 검증해야 할 조건은 무엇인가? | 구조 선택에 큰 영향을 주는 불확실성을 찾는다. |
| 목표를 높일 때 필요한 비용과 운영 부담을 감당할 수 있는가? | 목표와 제약조건의 양립 가능성을 확인한다. |

- 필수 조건들이 충돌하면 기능 범위, 일정과 자원 등을 다시 협의해야 한다.
- **트레이드오프가 존재한다는 말은 요구사항을 충족하지 못한 설계에도 문제가 없다는 뜻이 아니다.**

## 3. 동일한 시나리오로 여러 대안을 비교한다

- 먼저 목표 부하, 실패 조건과 허용 지연을 구체화한다.
- 구조를 유지하는 대안과 부분 개선안을 포함해 비교한다.
- 제품 이름이나 일반적인 장단점 대신 해당 시나리오에서의 효과와 위험을 적는다.

### 검색 부하를 처리하는 세 가지 대안

- 예를 들어 피크 검색 성능을 높이면서 검색 장애가 주문 처리로 전파되지 않게 하려는 상황을 생각할 수 있다.
- 아래 표는 검토할 가설이며 성능과 격리 수준의 확정된 평가가 아니다.

| 대안 | 기대하는 효과 | 남는 위험과 검증할 내용 |
| :--- | :--- | :--- |
| 주 DB에서 검색을 유지한다. | 구조와 데이터 전달 경로가 단순하다. | 검색이 주문과 자원을 경합하는지, 쿼리와 인덱스 개선으로 목표를 만족할 수 있는지 확인한다. |
| 읽기 복제본으로 검색한다. | 검색 읽기 부하를 주 DB에서 분리할 수 있다. | 복제 지연과 공통 앱 자원에서의 장애 전파를 확인한다. |
| 검색 서비스와 인덱스를 분리한다. | 검색을 독립적으로 확장하고 장애를 격리할 수 있다. | 데이터 반영 지연, 실패한 동기화의 재처리와 추가 운영 비용을 확인한다. |

- 검색을 분리해도 주문이 동기적으로 검색을 기다리면 검색 장애가 주문에 영향을 줄 수 있다.
- 별도 프로세스나 복제본이 있다는 사실만으로 모든 자원과 장애가 격리되는 것은 아니다.
- 성능 테스트, 장애 주입과 데이터 지연 측정으로 가설을 확인한다.

## 4. 허용할 차이를 업무 경계에서 정한다

- 검색 화면의 가격이 잠시 늦게 반영되어도 결제 금액은 정확해야 할 수 있다.
- 이 경우 검색에는 반영 지연을 허용하고 주문 확정 시에는 원본 데이터로 가격을 검증하는 대안을 검토할 수 있다.
- 검증과 확정 사이의 동시 변경도 처리해야 하므로 단순 재조회만으로 정확성이 보장되지는 않는다.
- 검색 결과의 최신성, 주문 시 검증과 데이터 변경의 책임을 구분한다.
- 업무 담당자와 허용 지연, 가격 변경 시 안내와 주문 처리 규칙을 합의한다.
- **품질 수준은 시스템 전체에 동일하게 적용하기보다 각 업무가 허용하는 범위에 맞춰 정할 수 있다.**

## 5. 선택의 근거와 재검토 조건을 기록한다

| 기록할 내용 | 남겨야 하는 이유 |
| :--- | :--- |
| 요구사항과 제약조건 | 어떤 문제와 조건에서 내린 결정인지 알 수 있다. |
| 검토한 대안 | 다른 해법을 선택하지 않은 이유를 설명할 수 있다. |
| 이점과 비용 | 개선할 품질과 감수할 운영·개발 부담을 확인할 수 있다. |
| 검증 근거와 남은 가정 | 확인된 사실과 아직 불확실한 부분을 구분할 수 있다. |
| 합의한 책임과 허용 범위 | 누가 어떤 결과를 받아들이고 관리할지 알 수 있다. |
| 재검토 조건 | 부하, 요구사항이나 비용이 달라졌을 때 다시 판단할 수 있다. |

- 아키텍처 드라이버는 대안을 비교할 기준을 정하고, 우선순위는 기준이 충돌할 때의 선택을 돕는다.
- 아직 측정하지 않은 효과를 확정된 장점으로 기록하지 않는다.
- 선택 이후에도 목표 달성 여부와 감수한 비용을 관찰한다.
- 요구사항이나 운영 조건이 달라지면 같은 대안을 다시 비교한다.
