# 소프트웨어 아키텍처: 구조와 중요한 결정을 이해하는 기준

## 1. 아키텍처가 다루는 것

- **소프트웨어 아키텍처는 시스템을 이루는 주요 요소와 관계, 외부에 드러나는 속성, 설계와 변경을 이끄는 중요한 결정과 원칙을 다룬다.**
- 어떤 기능을 제공할지뿐 아니라 그 기능을 어떤 구조로 구현하고 운영할지 결정한다.
- 판단의 기준은 업무 목표, 기능·품질 요구사항과 제약조건이다.
- 시스템을 여러 부분으로 나누는 것만으로는 각 부분이 어떻게 협력하고 요구사항을 충족하는지 설명할 수 없다.
- 구조, 협력 방식과 선택의 이유를 함께 이해해야 한다.

## 2. 구조를 설명할 때 필요한 요소

| 요소 | 확인할 질문 | 주문 시스템의 예시 |
| :--- | :--- | :--- |
| 구성요소와 책임 | 무엇으로 나누고 각 부분이 무엇을 맡는가? | 주문, 결제와 재고의 책임을 구분한다. |
| 관계와 의존성 | 누가 누구를 호출하거나 어떤 데이터를 공유하는가? | 주문이 결제 API를 호출하고 주문 완료 이벤트를 발행한다. |
| 인터페이스와 속성 | 다른 요소가 무엇을 기대할 수 있는가? | 요청 형식, 오류 응답, 중복 요청 처리와 응답 시간을 정한다. |
| 외부 환경 | 시스템 밖의 무엇과 연결되고 어떤 제약을 받는가? | 외부 결제사와 연동하며 호출 한도를 지킨다. |
| 공통 관심사 | 여러 부분이 함께 지켜야 할 처리 방식은 무엇인가? | 인증, 트랜잭션과 로그 추적 방식을 정한다. |
| 결정과 원칙 | 왜 이 구조를 선택했고 변경할 때 무엇을 지키는가? | 데이터 소유권을 정하고 다른 서비스의 DB를 직접 수정하지 않는다. |

- 빌딩 블록은 모듈, 서비스와 계층 등 시스템의 구성요소를 가리키는 포괄적인 표현이다.
- **인터페이스는 함수나 API의 이름뿐 아니라 호출자가 기대하는 동작의 계약이다.**
- 실패 시 동작, 데이터 일관성과 성능도 다른 요소의 설계에 영향을 준다면 계약에서 다룬다.
- 내부 구현을 감추더라도 다른 요소가 의존하는 동작은 명확해야 한다.

## 3. 기능, 품질과 제약조건을 구분한다

| 구분 | 의미 | 예시 |
| :--- | :--- | :--- |
| 기능 요구사항 | 시스템이 수행해야 하는 일을 정한다. | 사용자가 주문을 취소할 수 있어야 한다. |
| 품질 요구사항 | 어떤 조건에서 어느 수준으로 동작해야 하는지 정한다. | 피크 부하에서도 정해진 응답 시간과 오류율을 만족해야 한다. |
| 제약조건 | 선택 가능한 해법의 범위를 제한한다. | 기존 결제 시스템을 유지하고 정해진 인력과 예산으로 운영해야 한다. |

- 같은 기능도 품질 요구와 제약조건이 다르면 적합한 구조가 달라진다.
- 빠르고 안정적이어야 한다는 표현만으로는 설계 대안을 비교하기 어렵다.
- 어떤 작업을 어떤 부하와 장애 조건에서 어느 수준으로 처리해야 하는지 구체화한다.
- 새로운 기술을 채택하는 것 자체가 아키텍처의 목표는 아니다.

### 품질 사이의 트레이드오프를 판단한다

- 캐시로 조회 시간을 줄이면 데이터 갱신과 무효화 처리가 필요해진다.
- 비동기 처리로 요청과 작업 실행을 분리하면 결과 확인과 실패 처리가 복잡해진다.
- 서비스를 나누면 독립적인 배포와 확장이 가능해지는 대신 통신과 운영 비용이 늘어난다.
- **어떤 품질을 우선하고 어떤 비용을 감수할지는 업무 맥락에서 결정한다.**
- 팀이 구현하고 운영할 수 있는지도 선택 기준에 포함한다.

## 4. 결정과 원칙을 함께 남긴다

- 아키텍처 결정은 특정 문제에 대해 선택한 해법이다.
- 설계 원칙은 이후의 여러 결정을 일관되게 내리는 기준이다.
- 선택한 기술 이름만으로는 해결하려는 문제나 감수한 비용을 알기 어렵다.

| 기록할 내용 | 비동기 알림 처리 예시 |
| :--- | :--- |
| 문제와 목표 | 알림 지연이 주문 응답을 늦추지 않게 한다. |
| 결정 | 주문 완료 이후의 알림을 큐로 전달한다. |
| 원칙 | 주문 성립에 필요하지 않은 외부 작업은 주문 처리와 분리한다. |
| 감수한 비용 | 알림이 늦어질 수 있으며 재시도와 중복 방지가 필요하다. |
| 검증할 내용 | 알림 서비스가 멈춰도 주문 처리 목표를 만족하는지 확인한다. |

- 결정에는 적용 범위와 성립 조건이 있다.
- 요구사항이나 운영 환경이 바뀌면 기존 결정이 여전히 적합한지 다시 판단한다.
- 변경 비용이 큰 결정은 주의해서 다뤄야 하지만, 변경할 수 없다는 뜻은 아니다.

## 5. 다이어그램과 실제 아키텍처를 구분한다

- 다이어그램은 아키텍처를 설명하는 수단이다.
- 상자와 화살표만으로는 각 요소의 책임, 호출 계약과 결정의 이유를 충분히 설명하기 어렵다.
- 코드 의존 관계, 실행 중 호출 흐름과 배포 위치는 서로 다른 정보이다.
- 그림이 어떤 관계를 나타내는지 명시하고, 필요한 설명을 함께 남긴다.
- 문서가 없어도 시스템에는 구조와 의존 관계가 존재한다.
- 문서의 구조와 실제 구현이 다르면 그 차이를 확인하고 설계나 구현을 조정해야 한다.
- **좋은 아키텍처 설명은 팀이 같은 구조와 결정의 이유를 이해하고 변경에 활용할 수 있어야 한다.**
