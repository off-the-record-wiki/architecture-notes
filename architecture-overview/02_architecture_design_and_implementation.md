# 아키텍처와 설계·구현: 결정의 영향으로 구분하기

## 1. 아키텍처 설계는 소프트웨어 설계의 일부이다

- 설계는 소프트웨어를 어떻게 구성하고 동작하게 할지 결정하는 활동이다.
- 아키텍처 설계는 그중 시스템의 중요한 구조와 품질에 영향을 미치는 결정을 다룬다.
- 상세 설계는 각 부분의 내부 구성과 구체적인 동작을 다룬다.
- 구현은 이러한 결정을 코드와 설정으로 실현한다.
- **아키텍처 설계, 상세 설계와 구현은 서로 연결되며 개발 중에도 반복된다.**

| 구분 | 주요 질문 | 주문 처리 예시 |
| :--- | :--- | :--- |
| 아키텍처 설계 | 어떤 책임과 경계로 나누고 어떻게 협력하는가? | 주문과 결제의 책임, 호출 방식과 실패 처리 경계를 정한다. |
| 상세 설계 | 담당 부분의 내부를 어떻게 구성하는가? | 주문 검증 객체와 메서드의 역할을 나눈다. |
| 구현 | 정한 동작을 실제로 어떻게 실행하는가? | 검증 로직, 연동 코드와 테스트를 작성한다. |

- 이 구분은 업무의 초점을 설명하며 직책이나 개발 순서를 고정하지 않는다.
- 같은 개발자가 아키텍처 결정과 상세 설계, 구현을 모두 수행할 수 있다.

## 2. 아키텍처적으로 중요한 결정인지 판단한다

- 기술 이름이나 코드의 크기만으로 결정의 중요성을 구분하기 어렵다.
- 그 결정이 현재 시스템에 미치는 영향과 변경 부담을 함께 살펴본다.

| 판단 기준 | 확인할 질문 |
| :--- | :--- |
| 영향 범위 | 여러 모듈, 서비스나 팀의 작업 방식이 함께 바뀌는가? |
| 변경 비용 | 바꾸려면 데이터 전환, 호출자 수정이나 여러 팀의 협의가 필요한가? |
| 품질 영향 | 성능, 가용성, 보안이나 변경 용이성에 큰 영향을 미치는가? |
| 구조와 계약 | 책임 경계, 데이터 소유권과 외부에 제공하는 계약이 달라지는가? |

- 여러 기준에 모두 해당해야만 아키텍처 결정이 되는 것은 아니다.
- 영향 범위가 작아도 핵심 처리 경로의 성능이나 보안을 좌우하면 중요하게 다뤄야 한다.
- 추상화 수준이 높은 설계는 아키텍처를 설명하는 데 유용하지만, 구체적인 코드에도 중요한 결정이 포함될 수 있다.
- **결정의 이름보다 무엇에 영향을 주고 무엇을 바꾸기 어렵게 만드는지가 중요하다.**

## 3. 같은 기술도 맥락에 따라 중요성이 달라진다

| 선택 | 상세 설계에 가까운 상황 | 아키텍처 수준에서 검토할 상황 |
| :--- | :--- | :--- |
| 캐시 | 한 모듈의 반복 계산을 줄이고 외부 동작은 유지한다. | 여러 서비스의 데이터 일관성, 장애 처리와 갱신 정책을 결정한다. |
| 클래스 분리 | 모듈 내부의 가독성을 개선한다. | 공통 API와 여러 팀이 사용하는 확장 계약을 바꾼다. |
| 저장 방식 | 외부 계약에 영향 없이 내부 구현을 조정한다. | 데이터 소유권, 트랜잭션 범위와 전환 절차가 달라진다. |
| 통신 방식 | 모듈 내부의 호출 코드를 정리한다. | 동기 응답을 비동기 접수로 바꿔 사용자 경험과 실패 처리가 달라진다. |

- 디자인 패턴을 사용했다는 사실만으로 상세 설계라고 단정하지 않는다.
- 클래스 다이어그램이나 ERD도 중요한 책임과 데이터 경계를 표현할 수 있다.
- 산출물의 종류가 결정의 중요성을 대신하지 않는다.

## 4. 중요한 결정은 공유하고 상세 설계의 자율성을 둔다

- 아키텍처 결정을 모두 한 사람이 내릴 필요는 없다.
- 영향을 받는 팀이 논의에 참여하고 누가 최종 판단과 후속 검증을 맡는지 정한다.
- 합의한 경계와 계약 안의 상세 설계는 담당 개발자가 결정할 수 있게 한다.
- 담당 영역의 변경이 다른 팀의 계약이나 공통 원칙을 바꾸면 함께 검토한다.
- 모든 구현 선택에 중앙 승인을 요구하면 의사결정이 병목이 될 수 있다.
- 중요한 변경을 공유하지 않으면 팀마다 서로 다른 가정으로 구현할 수 있다.

### 나중에 다시 판단할 수 있게 기록한다

- 중요한 결정은 ADR(Architecture Decision Record) 등으로 남긴다.
- 해결하려는 문제, 비교한 대안, 선택한 이유와 감수한 결과를 기록한다.
- 결정의 적용 범위와 판단의 전제가 된 조건도 명확히 한다.
- 코드에서 드러나는 상세 동작을 모두 문서에 중복해서 적을 필요는 없다.

## 5. 구현과 운영 결과로 설계를 검증한다

- 구조를 정한 시점에는 실제 성능, 장애 동작과 구현 난도를 모두 알기 어렵다.
- 위험이 큰 가정부터 작은 구현과 실험으로 확인한다.
- 결과가 요구사항에 미치지 못하면 구현 최적화뿐 아니라 구조와 계약도 재검토한다.

| 검증 대상 | 확인 방법의 예시 |
| :--- | :--- |
| 성능 가정 | 실제와 비슷한 데이터와 부하로 처리량과 응답 시간을 측정한다. |
| 장애 처리 | 외부 의존성이 느려지거나 끊겼을 때 타임아웃과 복구 동작을 확인한다. |
| 책임과 의존 관계 | 코드와 모듈 의존성이 합의한 경계를 지키는지 검토한다. |
| 변경 용이성 | 예상한 기능 변경이 어느 모듈과 팀까지 영향을 주는지 확인한다. |

- 테스트가 통과했다는 사실만으로 모든 품질 목표가 충족되는 것은 아니다.
- 어떤 조건과 범위를 검증했는지 함께 확인한다.
- 운영에서 드러난 제약과 장애 경험을 다음 설계에 반영한다.

### 건축 비유에서 가져올 수 있는 것과 한계

- 전체 구조, 전문 분야 간 조율과 설계 결과의 확인은 소프트웨어에서도 중요한 활동이다.
- 다만 소프트웨어에서는 구현 중 발견한 문제가 설계 변경으로 이어지고, 운영 중에도 요구사항과 환경이 바뀐다.
- 도면을 완성해 전달하듯 설계 문서를 넘기는 것만으로 아키텍처 작업이 끝나지는 않는다.
- **구현은 정해진 구조를 실현하는 과정이면서, 그 구조가 적합한지 확인하는 과정이다.**
