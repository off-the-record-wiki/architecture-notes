# 소프트웨어 아키텍트: 결정과 실행 결과에 대한 책임

## 1. 직책보다 수행하는 역할이 중요하다

- **아키텍트는 요구사항과 제약조건을 바탕으로 중요한 설계 결정을 이끌고, 구현과 운영에서 그 결과를 확인하는 역할을 맡는다.**
- 조직에 따라 전담 아키텍트, 기술 리더나 개발팀이 이 역할을 수행할 수 있다.
- 개발 경력과 특정 기술의 전문성은 도움이 되지만 시스템 전체를 판단하는 역량을 대신하지 않는다.
- 여러 사람이 결정을 나눠 맡더라도 결정의 책임자와 관련 팀 사이의 협의 방법은 명확해야 한다.

## 2. 핵심 책임은 요구사항부터 검증까지 이어진다

| 책임 | 실제로 해야 할 일 |
| :--- | :--- |
| 요구사항과 제약조건을 명확히 한다. | 업무 목표, 품질 수준, 일정·예산·운영 제약의 모호함과 충돌을 확인한다. |
| 구조와 인터페이스를 정한다. | 구성요소의 책임, 의존 관계와 협력 계약을 정의한다. |
| 공통 처리 방식을 정한다. | 보안, 영속성, 통신과 로그 등 여러 부분이 함께 사용하는 기준을 마련한다. |
| 결정의 결과를 설명한다. | 선택 이유뿐 아니라 포기한 대안, 비용과 위험을 전달한다. |
| 합의와 기록을 유지한다. | 이해관계자가 필요한 정보를 이해할 수 있도록 설명하고 문서화한다. |
| 구현 과정에 참여한다. | 코드와 설계의 차이를 확인하고 개발 과정의 피드백을 반영한다. |
| 분석하고 검증한다. | 실제 요구사항 충족 여부와 남은 위험을 확인한다. |

- 이 활동은 한 번씩 수행하고 끝내는 순차 단계가 아니다.
- 요구사항이 바뀌거나 검증에서 문제가 발견되면 이전 판단을 다시 살펴본다.
- 문서 작성 여부보다 개발과 운영에서 결정을 사용할 수 있는지가 중요하다.

## 3. 이해관계자의 요구를 설계 판단에 반영한다

- 설계가 기술적으로 가능해도 업무 목표나 운영 조건과 맞지 않으면 적용하기 어렵다.
- 개발팀뿐 아니라 제품, QA와 운영 관점의 제약을 초기에 확인한다.

| 상대 | 받아야 할 정보 | 설명하고 합의할 내용 |
| :--- | :--- | :--- |
| 제품 담당자·업무 담당자 | 업무 목표, 우선순위와 허용 가능한 동작이다. | 기술 대안이 사용자 경험과 업무 결과에 미치는 영향이다. |
| 프로젝트 관리자 | 일정, 예산과 인력 제약이다. | 위험, 필요한 역량과 범위 조정의 영향이다. |
| 개발팀 | 구현 난도, 코드의 제약과 기술 경험이다. | 책임 경계, 인터페이스와 선택의 이유이다. |
| QA | 결함 유형과 검증 결과이다. | 확인할 품질 조건과 테스트 가능한 구조이다. |
| 운영팀 | 배포 제약, 장애 이력과 운영 부담이다. | 배포·복구 방식과 관측할 지표이다. |
| 전사 아키텍처 담당자 | 조직의 표준과 공통 기술 방향이다. | 시스템 설계의 정합성과 예외가 필요한 이유이다. |

- 같은 결정을 설명하더라도 상대가 판단해야 하는 비용과 영향을 중심으로 전달한다.
- 반대 의견은 설계를 방해하는 요소가 아니라 놓친 요구사항이나 위험을 확인할 근거가 될 수 있다.
- 설계 권한이 일정·예산 관리나 인사 권한까지 자동으로 포함하는 것은 아니다.
- 실제 책임 범위는 조직의 역할 분담에 맞춰 합의한다.

## 4. 기술의 너비와 필요한 깊이를 함께 갖춘다

- 아키텍트에게는 여러 해법을 비교할 수 있는 기술적 너비가 필요하다.
- 익숙한 기술만 선택하면 더 적합한 대안이나 새로운 제약을 놓칠 수 있다.
- 동시에 중요한 결정의 실현 가능성과 비용을 판단할 만큼 구현을 이해해야 한다.
- 모든 기술을 같은 깊이로 알 필요는 없지만, 핵심 위험은 전문가와 함께 확인하거나 직접 검증한다.

| 역량 | 설계 판단에 필요한 이유 |
| :--- | :--- |
| 기술 이해 | 기술이 제공하는 기능, 한계와 운영 비용을 비교한다. |
| 도메인 이해 | 반드시 지켜야 할 업무 규칙과 허용할 수 있는 실패·지연을 구분한다. |
| 소통과 조율 | 서로 다른 요구를 드러내고 선택의 근거와 결과에 합의한다. |

- 새로운 기술을 많이 아는 것보다 문제에 맞는 대안을 찾고 검증하는 능력이 중요하다.
- 과거에 성공한 해법도 현재의 요구사항, 제품 동작과 팀 환경에서 다시 판단한다.

## 5. 구현 참여의 범위는 위험에 맞춰 정한다

- 모든 코드를 직접 작성하거나 모든 변경을 승인할 필요는 없다.
- 불확실성이 큰 기술, 중요한 인터페이스와 공통 기능에 우선적으로 관여한다.
- 작은 검증 구현으로 실현 가능성을 확인하거나 공통 기능의 구현 예시를 만들 수 있다.
- 중요한 코드 경계와 의존 관계를 리뷰하고 부하·장애 테스트 결과를 함께 해석한다.
- 구현이 어려운 이유를 듣고 필요하면 설계와 원칙을 수정한다.
- **설계를 지키게 하는 것과 설계가 틀렸을 때 바꾸는 것 모두 책임에 포함된다.**

## 6. 시스템 단계에 따라 역할의 비중이 달라진다

- CMU SEI의 John Klein은 초기 설계, 확장과 유지 단계에서 필요한 역할을 구분한다.

| 단계 | 주요 역할 | 주의할 점 |
| :--- | :--- | :--- |
| 초기 설계 | 중요한 기능·품질 요구를 식별하고 일관된 책임과 협력 구조를 만든다. | 기능 개발 경험만으로 시스템 수준의 설계와 분석 역량을 가정하지 않는다. |
| 확장 | 새 기능과 외부 연동의 가치를 기존 구조의 변경 비용과 비교한다. | 초기 설계를 고수하느라 필요한 변화를 막지 않는다. |
| 유지 | 환경 변화 속에서 시스템의 가치를 유지하고 개선 필요성을 판단한다. | 기존 시스템을 잘 안다는 이유만으로 새 시스템 설계에도 같은 역량이 충분하다고 가정하지 않는다. |

- 구조적 일관성은 비슷한 문제를 일관된 책임과 규칙으로 다루는 데 도움이 된다.
- 다만 일관성 유지를 위한 추상화와 공통화에도 비용이 든다.
- 맡을 역할은 직급이나 경력 연수뿐 아니라 해당 단계가 요구하는 역량에 맞춰 정한다.
- **아키텍트가 지켜야 하는 것은 처음 만든 설계 자체보다 현재 요구를 충족할 수 있는 구조이다.**
