# Strangler Fig: 레거시를 안전하게 전환하는 방법

## 1. Strangler Fig의 개념

- **Strangler Fig는 기존 기능을 조금씩 새 시스템으로 옮기는 점진적 전환 패턴이다.**
- 아직 옮기지 않은 기능은 레거시가 계속 처리한다.
- 새 시스템이 맡는 범위를 늘리면서 레거시의 책임을 줄인다.
- 전환 대상의 기능과 의존 관계를 정리한 뒤 레거시를 제거한다.
- 새 기능을 기존 시스템 옆에 추가하는 것만으로 전환이 완료되지는 않는다.
- **핵심은 운영을 이어가면서 기존 시스템의 책임을 실제로 줄이는 것이다.**
- 새 시스템이 반드시 마이크로서비스일 필요는 없다.

### 이름의 의미

- Martin Fowler가 교살무화과의 성장 과정에 빗대어 이름을 붙였다.
- 기존 나무를 발판으로 자란 식물이 독립하듯 새 시스템이 레거시의 자리를 대신한다.
- 특정 제품이나 프레임워크보다 시스템을 바꾸는 접근 방식에 가깝다.

## 2. 한 번에 바꾸기 어려운 이유

- 오래 운영한 시스템의 실제 동작을 모두 파악하기는 어렵다.
- 문서에 없는 업무 규칙과 예외 처리가 코드와 운영 절차에 남아 있을 수 있다.
- 전체를 다시 만드는 동안에도 현업은 새로운 기능을 요구한다.
- 기존 기능을 모두 복제하면 더 이상 필요하지 않은 기능까지 다시 만들 수 있다.
- 마지막에 한 번에 전환하면 많은 변경의 위험이 같은 시점에 집중된다.

| 비교 항목 | 빅뱅 전환 | 점진적 전환 |
| :---: | :--- | :--- |
| 전환 단위 | 전체 시스템을 한 번에 바꾼다. | 분리 가능한 기능과 흐름부터 바꾼다. |
| 효과 확인 | 전체 전환까지 기다려야 할 수 있다. | 먼저 옮긴 기능부터 운영 효과를 확인한다. |
| 위험 범위 | 전체 변경이 한 시점에 집중된다. | 개별 전환 단위로 위험을 나누기 쉽다. |
| 공존 비용 | 장기간의 기능별 공존 구조가 덜 필요할 수 있다. | 두 시스템을 연결하고 함께 운영하는 비용이 든다. |

- 규모가 작고 업무가 단순하면 빅뱅 전환이 더 간단할 수 있다.
- 점진적 전환도 복잡한 의존 관계와 운영 위험을 없애지는 않는다.

### 현행 기능을 그대로 옮기는 목표를 재검토한다

- 현행 기능의 정의와 합의 자체가 큰 작업이 될 수 있다.
- 기존 기능을 모두 복제하는 것을 성공 기준으로 삼지 않는다.
- 유지할 기능, 개선할 기능과 폐기할 기능을 구분한다.
- 변경 비용 감소나 처리 시간 개선처럼 전환으로 얻으려는 결과를 먼저 정한다.

## 3. 흐름을 나눌 경계를 찾는다

- Seam은 기존 흐름을 분리하거나 다른 구현으로 연결할 수 있는 경계이다.
- 이 경계에서 요청이나 데이터 흐름을 가로채 새 시스템으로 보낸다.
- 기존 연결 지점을 활용하거나 필요한 경계를 새로 만든다.

| 경계의 위치 | 활용할 수 있는 수단 | 적용 상황 |
| :--- | :--- | :--- |
| 외부 요청의 앞단이다. | 프록시와 API Gateway를 사용한다. | 기능별 요청을 기존 시스템과 새 시스템으로 나눈다. |
| 시스템 사이의 연계 지점이다. | 메시지 큐, DB 트리거와 변경 데이터 캡처 등을 검토한다. | 배치와 데이터 연계의 처리 주체를 바꾼다. |
| 코드 내부의 모듈 경계이다. | 인터페이스와 추상화 계층을 둔다. | 기존 구현을 새로운 구현으로 점진적으로 교체한다. |

- 코드 내부의 구현 교체에는 Branch by Abstraction을 함께 활용할 수 있다.
- 앞단의 API Gateway만이 유일한 구현 방법은 아니다.
- 단순히 요청 경로를 나눌 수 있는지뿐 아니라 업무와 데이터의 경계도 확인한다.

## 4. 퍼사드로 요청을 점진적으로 전환한다

- 퍼사드는 요청을 받아 레거시와 새 시스템 중 처리할 곳을 선택한다.
- 클라이언트가 내부의 전환 상황을 직접 추적하지 않게 한다.
- 옮긴 기능의 요청만 새 시스템으로 보내고 나머지는 기존 경로를 유지한다.

| 단계 | 요청 흐름 | 확인할 사항 |
| :---: | :--- | :--- |
| 1. 퍼사드를 배치한다. | 대부분의 요청을 레거시로 전달한다. | 기존 동작과 호출 계약이 유지되는지 확인한다. |
| 2. 기능을 하나씩 옮긴다. | 전환한 기능의 요청을 새 시스템으로 보낸다. | 기능, 성능과 연계 결과를 검증한다. |
| 3. 레거시를 제거한다. | 전환 대상의 요청을 새 시스템이 처리한다. | 남아 있는 호출과 데이터 의존성이 없는지 확인한다. |
| 4. 전환용 구조를 정리한다. | 불필요한 중간 경로를 제거한다. | 계속 필요한 기능과 임시 기능을 구분한다. |

- 전환만을 위해 만든 퍼사드는 역할이 끝나면 제거할 수 있다.
- 기존 클라이언트의 호환성 유지가 필요하면 어댑터로 남길 수 있다.
- 공통 인증과 라우팅을 담당하는 API Gateway까지 반드시 제거해야 하는 것은 아니다.
- 퍼사드가 단일 장애 지점이나 처리 병목이 되지 않게 운영한다.

## 5. 반복해야 할 네 가지 활동

| 활동 | 핵심 질문 |
| :--- | :--- |
| 원하는 결과를 이해한다. | 무엇을 개선하기 위해 전환하는가? |
| 문제를 작게 나눈다. | 독립적으로 옮길 수 있는 업무와 연결 경계는 어디인가? |
| 나눈 조각을 운영에 전달한다. | 실제 환경에서 효과와 동작을 확인했는가? |
| 조직의 일하는 방식을 바꾼다. | 작은 전환을 계속 수행할 수 있는가? |

- 이 활동들은 한 번씩 끝내는 순차 단계가 아니다.
- 전환 결과를 확인하면서 범위와 우선순위를 계속 조정한다.
- 작은 단위를 자주 배포할 수 있는 개발과 승인 절차가 필요하다.
- 팀의 책임도 기존 시스템 구분뿐 아니라 업무 기능의 경계를 고려해 정한다.
- 기술만 바꾸고 같은 방식으로 일하면 새 시스템도 다시 변경하기 어려워질 수 있다.

## 6. Anti-Corruption Layer로 모델을 보호한다

- 전환 중에는 새 시스템이 아직 남아 있는 레거시 기능을 호출할 수 있다.
- 이때 레거시의 코드값과 데이터 구조가 새 모델에 그대로 퍼질 수 있다.
- Anti-Corruption Layer는 두 시스템 사이에서 모델과 용어를 번역한다.
- 새 시스템이 자신의 업무 모델을 유지하도록 경계를 만든다.

| 위치 | 고객 유형 표현의 예시 |
| :--- | :--- |
| 레거시는 기존 표현을 유지한다. | `CUST_GB = '01'`을 사용한다. |
| 번역 계층은 의미를 변환한다. | `'01'`과 개인 고객 유형을 대응시킨다. |
| 새 시스템은 자신의 모델을 사용한다. | `CustomerType.INDIVIDUAL`을 사용한다. |

- 퍼사드는 주로 어디로 보낼지를 결정한다.
- Anti-Corruption Layer는 서로 다른 모델의 의미를 어떻게 연결할지 담당한다.
- 단순한 경로 전달과 업무 의미의 번역은 서로 다른 책임이다.
- 번역 계층은 레거시 전환 외에 외부 시스템 연동에도 사용할 수 있다.
- 역할이 계속 필요하다면 전환 이후에도 유지할 수 있다.

## 7. 과도기 아키텍처의 비용을 계획한다

- 과도기 아키텍처는 두 시스템이 공존하도록 만드는 임시 구조이다.
- 전환이 끝나면 제거할 코드도 위험을 줄이는 데 필요한 비용이다.
- 새 기능 개발뿐 아니라 연결, 운영과 제거 작업도 일정에 포함한다.

| 구성 요소 | 공존 기간의 역할 | 전환 이후의 판단 |
| :--- | :--- | :--- |
| 퍼사드를 둔다. | 기능별 요청의 목적지를 나눈다. | 전환용 분기와 호환성 요구가 남았는지 확인한다. |
| 번역 계층을 둔다. | 두 시스템의 모델과 호출 방식을 연결한다. | 레거시와의 번역 책임이 종료되었는지 확인한다. |
| 데이터 동기화 코드를 둔다. | 공존에 필요한 데이터를 전달한다. | 원본과 소비 경로를 정리한 뒤 제거한다. |

- 임시 구조마다 담당자와 제거 조건을 정한다.
- 새 시스템이 생겼는데 기존 의존성은 그대로인 상태가 장기화되지 않게 한다.

## 8. 숨은 데이터 흐름과 복귀 조건을 확인한다

### 화면과 API 밖의 연결도 옮긴다

- 배치, 저장 프로시저와 리포트가 레거시 데이터에 의존할 수 있다.
- 화면 기능을 옮겼어도 데이터 웨어하우스로 전달되는 흐름이 빠질 수 있다.
- 이 경우 새 시스템의 상품이 업무 리포트에서 누락될 수 있다.
- **옮길 대상은 기능뿐 아니라 그 기능에 기대고 있는 데이터 흐름까지이다.**
- 누가 데이터를 쓰고 누가 소비하는지 함께 조사한다.
- 누락된 연계는 대체 경로나 과도기 연결을 마련해 검증한다.

### 요청 경로만 되돌린다고 복귀가 완료되지는 않는다

- 전환 단위별로 데이터의 원본과 쓰기 책임을 명확히 한다.
- 두 시스템이 같은 데이터를 수정한다면 충돌과 동기화 실패를 처리해야 한다.
- 새 시스템에서 발생한 변경을 레거시가 읽을 수 있는지 확인한다.
- 데이터 구조와 업무 규칙의 호환성이 깨지면 라우팅만 바꿔 복귀하기 어렵다.
- **기존 경로를 유지하는 것과 실제로 복귀 가능한 것은 다르다.**
- 전환 전에 복귀 조건, 데이터 보정과 검증 방법을 함께 정한다.

## 9. 장점과 트레이드오프

### 장점

- 기능별로 변경 범위를 줄여 전환 위험을 나누기 쉽다.
- 먼저 옮긴 기능부터 효과를 확인할 수 있다.
- 운영에서 배운 내용을 다음 전환에 반영할 수 있다.
- 필요한 조건을 갖추면 기존 경로로 복귀할 여지를 남길 수 있다.
- 전체 교체를 기다리지 않고 업무 개선을 진행할 수 있다.

### 비용과 한계

- 일정 기간 두 시스템을 함께 운영해야 한다.
- 요청 분기, 모델 번역과 데이터 동기화가 복잡해질 수 있다.
- 과도기 구조에도 배포, 모니터링과 장애 대응이 필요하다.
- 퍼사드의 장애가 여러 기능에 영향을 줄 수 있다.
- 책임을 나눌 경계를 만드는 작업 자체가 어려울 수 있다.
- 점진적 전환만으로 무중단이나 안전한 복귀가 자동 보장되지는 않는다.

## 10. 적용 기준과 완료 조건

### 적용을 검토할 상황

- 오래 운영해 전체 동작을 한 번에 파악하기 어렵다.
- 서비스를 계속 운영하면서 기능을 바꿔야 한다.
- API, 메시지와 업무 기능 등 나눌 경계가 있거나 만들 수 있다.
- 일부 기능부터 개선 효과를 확인해야 한다.
- 전체 교체의 위험이 크고 병행 운영을 감당할 수 있다.

### 다른 방법을 먼저 검토할 상황

- 시스템이 작고 전체 교체가 단순하다.
- 기존 시스템을 빠르게 종료해야 해 공존 기간을 확보하기 어렵다.
- 요청을 가로채거나 책임을 나눌 지점을 만들기 어렵다.
- 소스 코드뿐 아니라 데이터베이스 등 대체 연계 지점도 변경할 수 없다.
- 소스 수정이 불가능하더라도 다른 경계를 활용할 수 있는지는 먼저 확인한다.

### 기존 책임이 사라졌는지 확인한다

- 전환 대상의 기능과 데이터 연계를 새 구조에서 처리한다.
- 레거시를 호출하는 클라이언트, 배치와 외부 연계가 남아 있지 않다.
- 불필요해진 전환용 분기와 동기화 코드를 정리한다.
- 운영 책임과 새 구조의 변경 절차를 확립한다.
- **전체 교체가 목표라면 새 시스템의 출시가 아니라 레거시의 종료가 완료 기준이다.**
