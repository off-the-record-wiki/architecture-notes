# 문제로 찾는 24가지 패턴

## 1. 문제를 기준으로 패턴을 찾는다

- **패턴은 해결하려는 문제를 기준으로 찾는다.**
- 먼저 현재의 문제가 어떤 영역에 속하는지 파악한다.
- 해당 영역의 패턴을 비교해 해결 후보를 좁힌다.
- 실제 적용 전에는 구조와 트레이드오프를 별도로 검토한다.
- 하나의 패턴이 여러 문제 영역에 걸칠 수 있다.

| 문제 영역 | 핵심 질문 | 패턴 수 |
| :---: | :--- | :---: |
| 데이터·상태 관리 | 데이터를 어떻게 나누고 저장하며 일관성을 유지하는가? | 6 |
| 복원력 | 장애와 과부하가 다른 영역으로 번지는 것을 어떻게 제한하는가? | 5 |
| 연동·통신 | 클라이언트, 서비스, 외부 시스템을 어떻게 연결하는가? | 4 |
| 구조 | 코드의 역할과 의존 관계를 어떻게 나누는가? | 4 |
| 전환·레거시 | 기존 시스템을 어떻게 점진적으로 바꾸는가? | 2 |
| 성능·확장성 | 데이터와 요청이 늘어날 때 어떻게 처리하는가? | 3 |

## 2. 데이터·상태 관리

- **데이터의 소유권, 변경 이력, 서비스 간 정합성을 다룬다.**

| 패턴 | 해결할 문제 | 핵심 아이디어 |
| :--- | :--- | :--- |
| CQRS | 하나의 모델로 읽기와 쓰기의 요구를 모두 만족하기 어렵다. | 읽기 모델과 쓰기 모델을 분리한다. |
| Transactional Outbox | DB 변경과 이벤트 발행을 하나의 로컬 트랜잭션으로 묶기 어렵다. | 업무 데이터와 발행할 이벤트를 함께 저장하고 별도로 전달한다. |
| Idempotent Consumer | 같은 메시지가 두 번 이상 도착할 수 있다. | 중복 메시지를 받아도 한 번 처리한 것과 같은 결과를 유지한다. |
| Saga | 여러 서비스의 작업을 하나의 트랜잭션으로 처리하기 어렵다. | 서비스별 트랜잭션을 실행하고 실패 시 필요한 보상 작업을 수행한다. |
| Event Sourcing | 현재 상태만으로는 상태가 만들어진 과정을 알기 어렵다. | 상태를 변경한 이벤트의 이력을 원본 기록으로 저장한다. |
| Database per Service | 공유 DB의 변경이 여러 서비스에 영향을 준다. | 서비스별로 데이터를 소유하고 다른 서비스의 직접 접근을 제한한다. |

- Saga의 보상 트랜잭션은 결제 취소처럼 앞선 작업의 효과를 보상하는 업무 처리이다.
- Event Sourcing은 단순히 이벤트를 전달하는 것을 넘어 이벤트 이력을 원본으로 사용한다.

## 3. 복원력

- **호출 실패, 자원 고갈, 과부하가 전체 장애로 이어지는 것을 제한한다.**

| 패턴 | 해결할 문제 | 핵심 아이디어 |
| :--- | :--- | :--- |
| Circuit Breaker | 실패하는 서비스를 계속 호출해 호출자까지 영향을 받는다. | 실패가 이어지면 호출을 잠시 차단하고 빠르게 실패를 반환한다. |
| Bulkhead | 한 영역의 장애가 스레드나 커넥션을 모두 소모한다. | 자원을 영역별로 나눠 장애의 영향을 격리한다. |
| Retry | 일시적인 오류 때문에 요청이 실패한다. | 잠시 기다린 뒤 다시 시도한다. |
| Timeout | 응답 없는 호출을 계속 기다리며 자원을 점유한다. | 대기 시간을 제한하고 초과하면 실패로 처리한다. |
| Rate Limiting | 요청이 몰려 처리 가능한 용량을 초과한다. | 일정 시간 동안 보내거나 받는 요청 수를 제한한다. |

- Retry는 같은 요청을 다시 보내므로 수신 측의 멱등 처리를 함께 검토한다.

## 4. 연동·통신

- **서비스의 진입점, 클라이언트별 요구, 데이터 조합과 이벤트 전달을 다룬다.**

| 패턴 | 해결할 문제 | 핵심 아이디어 |
| :--- | :--- | :--- |
| API Gateway | 클라이언트가 여러 서비스의 주소와 호출 규칙을 알아야 한다. | 하나의 진입점에서 요청을 받아 각 서비스로 전달한다. |
| BFF (Backends for Frontends) | 웹과 앱 등 클라이언트별로 필요한 API가 다르다. | 클라이언트 종류별로 전용 백엔드를 둔다. |
| API Composition | 한 화면에 필요한 데이터가 여러 서비스에 흩어져 있다. | 여러 서비스의 호출 결과를 모아 반환한다. |
| Publish-Subscribe | 발신자가 모든 수신자를 알고 직접 호출해야 한다. | 이벤트를 발행하면 관심 있는 구독자가 받아 처리한다. |

## 5. 구조

- **코드의 책임을 나누고 기술과 구현 사이의 결합을 줄인다.**

| 패턴 | 해결할 문제 | 핵심 아이디어 |
| :--- | :--- | :--- |
| Ports and Adapters (Hexagonal Architecture) | 도메인 로직이 DB나 프레임워크에 종속된다. | 도메인에 포트를 정의하고 외부 기술을 어댑터로 연결한다. |
| Dependency Injection | 객체가 의존 객체를 직접 생성해 구현에 강하게 결합한다. | 필요한 객체를 외부에서 주입한다. |
| Plugin | 기능을 추가할 때마다 핵심 코드를 수정해야 한다. | 확장 지점을 정의하고 구현을 연결한다. |
| MVC 계열 (MVC·MVVM 등) | 화면 코드와 업무 로직이 뒤섞인다. | 화면, 입력 처리, 데이터 관련 역할을 분리한다. |

- Ports and Adapters에서는 도메인과 외부 기술 사이의 의존 관계를 분리한다.
- Dependency Injection은 필요한 구현을 외부에서 제공하는 방식에 초점을 둔다.
- MVC 계열은 패턴마다 역할을 나누는 구체적인 방식이 다르다.

## 6. 전환·레거시

- **기존 시스템을 점진적으로 교체하고 새 시스템의 모델을 보호한다.**

| 패턴 | 해결할 문제 | 핵심 아이디어 |
| :--- | :--- | :--- |
| Strangler Fig | 레거시를 한 번에 교체하면 위험이 크다. | 기능을 하나씩 새 시스템으로 옮기고 전환이 끝나면 레거시를 제거한다. |
| Anti-Corruption Layer (ACL) | 레거시의 모델과 용어가 새 시스템에 영향을 준다. | 두 시스템 사이에 번역 계층을 두어 새 모델을 보호한다. |

- Strangler Fig는 시스템을 교체하는 방식에 초점을 둔다.
- Anti-Corruption Layer는 서로 다른 모델 사이의 경계를 보호하는 데 초점을 둔다.

## 7. 성능·확장성

- **반복 조회, 데이터 증가, 순간적인 요청 집중에 대응한다.**

| 패턴 | 해결할 문제 | 핵심 아이디어 |
| :--- | :--- | :--- |
| Cache-Aside | 같은 데이터를 매번 DB에서 읽어 지연과 부하가 발생한다. | 캐시를 먼저 조회하고 없으면 DB에서 읽어 캐시에 저장한다. |
| Sharding | 하나의 DB로 데이터 규모를 감당하기 어렵다. | 기준 키에 따라 데이터를 여러 저장소로 분산한다. |
| Queue-Based Load Leveling | 순간적으로 몰리는 요청을 즉시 처리하기 어렵다. | 요청을 큐에 쌓고 소비자가 감당할 수 있는 속도로 처리한다. |

## 8. 패턴을 조합하는 이유

- **패턴을 적용하면 새로운 문제가 생기거나 문제의 형태가 바뀔 수 있다.**
- 후속 문제에 대응하기 위해 다른 패턴을 함께 사용한다.
- 모든 조합이 필수인 것은 아니며 적용 방식과 요구사항에 따라 판단한다.

| 적용한 패턴 | 추가로 다룰 문제 | 함께 검토할 패턴 |
| :--- | :--- | :--- |
| Transactional Outbox | 재시도로 같은 이벤트가 중복 발행될 수 있다. | Idempotent Consumer로 중복을 안전하게 처리한다. |
| 이벤트 기반 Saga | 각 단계의 DB 변경과 이벤트 발행 사이에 정합성이 필요하다. | Transactional Outbox로 상태 변경과 발행 대상 기록을 함께 저장한다. |
| CQRS | 저장소를 분리하면 읽기 모델을 동기화해야 한다. | 이벤트 기반 동기화에서는 Outbox와 Idempotent Consumer를 검토한다. |
| Retry | 같은 요청이 수신 측에 여러 번 도착할 수 있다. | 수신 측의 멱등 처리를 적용한다. |
| Strangler Fig | 전환 도중 레거시 모델이 새 시스템에 영향을 줄 수 있다. | Anti-Corruption Layer로 모델 사이의 경계를 보호한다. |

## 9. 패턴마다 적용 범위가 다르다

- 24개 패턴이 모두 같은 크기의 설계 문제를 다루는 것은 아니다.
- 시스템 전체의 구조를 바꾸는 패턴과 개별 호출을 제어하는 패턴이 함께 포함된다.

| 적용 범위 | 예시 | 특징 |
| :---: | :--- | :--- |
| 시스템 구조 | Saga, CQRS, API Gateway, Strangler Fig가 있다. | 여러 서비스나 시스템 전체에 영향을 준다. |
| 호출 제어 | Retry, Timeout, Rate Limiting이 있다. | 개별 요청의 재시도, 대기 시간, 허용량을 제어한다. |
| 코드 설계 | Dependency Injection, Plugin, MVC 계열이 있다. | 코드의 역할과 의존 관계를 구성한다. |
| 데이터 분할 | Sharding이 있다. | 데이터를 여러 저장소에 나누는 기법을 다룬다. |

- 코드 설계 수준의 패턴은 디자인 패턴과 경계가 겹칠 수 있다.
- Sharding은 패턴이면서 데이터 분할 기법으로도 다룬다.
- **적용 범위는 달라도 반복되는 문제에 대한 해법이라는 공통점이 있다.**
